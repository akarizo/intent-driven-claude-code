Why · 01为何而做

#54（0.10.0，起飞待命与按下即起飞）合入时留下 25 条未修的 MEDIUM / LOW。其中三组关系到正确性或规格： - 起飞并发：三个起飞入口（命令、批准带按键、待命自动重试）之间仍有窗口，会产生「回复已取消却静默起飞」「无关轮次白耗预算」「卡住的飞行被误拒续飞」；续飞按钮的基线阶段还会并发跑两个基线。 - 文档残留：几处仍写「按批准起飞后再发 /opsx-apply」。 - 规格缺口：「正在飞」拒飞出口没有 scenario。

另外，用户在本会话里遇到过：按「批准修订并续飞」后，基线在后台跑 2–3 分钟，界面上看不到任何进度。

决策见决策页 docs/flight-armed-followups.html。2026-10-13 用户全按推荐（Q1–Q6），代替 grill-me 访谈。

What · 02变更范围

  • 起飞锁与 abort：
  • 三个入口共用的锁（现在的 armBusy），拒绝原文改为「正在起飞，稍候」；
  • 自动重试进行中收到 /flight abort，回复「正在自动起飞，结束后再 /flight abort」，不动待命（Q2）；
  • 重试结束时即使待命已变，起飞成功也照样通知。
  • 交模型对准：调用 prompt.submit 之前记下时刻 T0，提交成功后才置 awaitingModel。只认开始时刻（结束时的 clock.now 减 durationMs）不早于 T0 的主会话轮次。提交失败则放弃待命。
  • 旧待命与状态行：
  • 人再次起飞被拒为 human / human-key 时，清掉同一 change 的旧待命；
  • 放弃或取消待命时，只在没有别的在飞 change 或待命时清空状态行。
  • 「正在飞」判得更准（Q4）：在飞集合之外，还要求 drive 正在跑这个 change，或本 attempt 有活 agent；否则视为卡住，照常续飞。拒绝原文补上下一步。
  • 看门狗：
  • 诊断员在「已派发、dispatch 未写入」窗口里的请求也计时；
  • tick 处理前复查请求仍然超时（不按陈旧快照停 agent）。
  • 批准带（Q3、Q5）：
  • 从按下到起飞返回、包括续飞的基线阶段，该项显示「起飞中…」或「基线运行中（已 N 分钟）」，不渲染按钮；
  • 状态行显示基线进度；
  • 去重分支的提示改为「已批准，直接起飞」。
  • 小修：
  • land.ts 识别已暂存删除时改用 git status --porcelain -z（中文路径不再失效）；
  • 放弃待命的做法提示保留 --takeover 等参数；
  • 补几处测试缺口；
  • scenarioFiles 不再在两个文件各写一份。
  • 文档与规格：三处文档残留照实改；补「正在飞」与「重启后可续飞」的规格；插件 0.10.1（Q6）。
插件：template/plugins/flight/hooks/ 的 orchestrator.tsx、register.tsx、armed.ts、land.ts，以及 types/index.d.ts；对应的 TS 测试与 pytest 包装；plugin.json 升到 0.10.1。文档：opsx-propose 与 opsx-apply 的命令和 skill、README.md、docs/WORKFLOW_zh.md。不改：判定器与账本事件。

flight-armed-takeoff ADDED

Requirement: 交模型那一轮按提交时刻对准

插件 SHALL 在 clock.after(0) 的回调里，先取 T0 = clock.now()，再调用 $.prompt.submit： - 成功后，把待命的 awaitingModel 置真，并记 submittedAt = T0； - 失败时，放弃待命并通知。

主会话 turn.complete 时，插件 SHALL 以 clock.now() - durationMs 作为这一轮的开始时刻。只有开始时刻不早于 submittedAt 时，才以 main-turn 推进；早于时 SHALL 忽略这一轮，不计入预算。

Feature: PR #54 MEDIUM：awaitingModel 在提交前就置真，正在进行的无关轮次一结束就触发重试，白耗预算。实测（CLI 2.1.296）：提交的那一轮开始得比 prompt.submit 完成还早 7–20 ms，所以必须在调用前记 T0。

Scenario: model-turn-aligned

  • GIVENdemo 因 lint 红进入 model 类待命；插件提交修复请求之前，主会话已有一轮在跑
  • WHEN那一轮先结束（开始时刻早于 T0）；之后提交的那一轮结束（开始时刻不早于 T0）
  • THEN前一轮结束时不重试，已计入预算的次数不变
  • AND后一轮结束时自动重试起飞
  • AND另一个世界里 prompt.submit 抛错时，待命被放弃，ui.notify 收到含「放弃」的通知

Requirement: 人再次起飞被拒为只能人时清掉旧待命

人发出的起飞被拒、分类为 human 或 human-key 时，插件 SHALL 先清除同一 change 的旧待命，再通知。状态行 SHALL 不再显示该 change 的待命。

Feature: PR #54 LOW：现在旧待命仍留着，之后自动重试又被拒，同一原因通知两次。

Scenario: human-refusal-drops-old-arm

  • GIVENdemo 因「基线仍在跑」处于待命
  • WHEN人再发 /opsx-apply demo，被拒为「计划已变」；之后推进时钟 60 秒
  • THENdemo 的待命被清除，状态行不含 demo 的「起飞待命」
  • AND推进时钟后没有重试，也没有第二条通知

Requirement: 放弃或取消待命时不误清别人的状态行

放弃或取消某个待命时，插件 SHALL 按以下顺序处理状态行： - 还有别的待命：显示其中一个的 armedLine； - 本进程有在飞的 change：重画它的状态； - 都没有：清空状态行。

Feature: PR #54 LOW：现在无条件清空，会把另一个在飞 change 的状态行一起清掉。

Scenario: status-line-kept-for-others

armed.ts 的 giveUpText 给出的做法 SHALL 保留原起飞参数里 change 之外的参数（如 --takeover）：resume 类为 /flight resume <change> <其余参数>，其余为 /opsx-apply <原参数>。

flight-flying-check ADDED

Requirement: 只有确实在驱动的飞行才判「正在飞」

/opsx-apply 与 /flight resume 遇到以下情形时 SHALL 拒绝：本会话起飞、最新 attempt 既未落地也未停飞、且 change 在本进程的在飞集合里，并且满足以下任一条： - drive 正在跑这个 change； - 本 attempt 至少有一个派出的 agent 在引擎里仍在运行。

flight-takeoff-lock ADDED

Requirement: 起飞锁被占用时如实回复

同一 change 正在起飞时（/opsx-apply、/flight resume、批准带按键或待命自动重试中的任一个持有起飞锁），另一路起飞 SHALL 被拒，回复「flight：<change> 正在起飞，稍候」，SHALL NOT 追加 takeoff 事件。

Feature: PR #54 评审：锁已存在，但拒绝原文写成「正在自动重试起飞」，人工起飞期间再按批准带也会收到这句，容易误读。

Requirement: 自动重试进行中收到 abort 时请人稍后再试

自动重试持有起飞锁时，/flight abort <change> SHALL 回复「flight：<change> 正在自动起飞，结束后再 /flight abort」，SHALL NOT 清除待命。重试结束时，若起飞成功，SHALL 通知「已起飞」，即使待命在此期间已被替换或清除。

Feature: 用户定 Q2 A。PR #54 MEDIUM：现在 abort 会先清待命并回复「已取消」，而这次重试成功起飞后，结果被静默丢掉。

flight-watchdog-hardening ADDED

Requirement: 诊断员登记窗口里的请求也计时

诊断员已派发、dispatch 尚未写入账本时，看门狗 SHALL 也开始跟踪它的模型请求：在诊断中（diagnosing）的 change 下，登记中的 agent 就是诊断员。dispatch 写入后，超时 SHALL 照常 TaskStop。

Feature: PR #54 MEDIUM：登记中的 owner 不带 role，而停飞后 change 已移出在飞集合，诊断员的首个请求从不计时。

Scenario: diagnostician-pending-timed

  • GIVENdemo 已停飞，诊断员 d1 已派发、dispatch 尚未写入；d1 在此期间发出一个模型请求，之后再也没有结束
  • WHENdispatch 写入账本；时钟推进到该请求开始后 10 分钟零 1 秒，看门狗 tick
  • THEN对 d1 恰好调用一次 TaskStop

Requirement: tick 处理前复查请求仍然超时

看门狗在一次 tick 里处理某个 agent 之前，SHALL 复查：该 agent 当前请求的起点仍是快照里的那个，且仍超过阈值。不满足时 SHALL 跳过，SHALL NOT 停它，也不记 heal。

Feature: PR #54 LOW：tick 取快照后有 await，其间旧请求结束、新请求开始，会按陈旧快照停掉一个刚开始请求的 agent。

Scenario: tick-rechecks-staleness

  • GIVEN执行体 a1 的请求已超时，被 tick 取进快照；tick 在查归属时卡住，其间 a1 的旧请求结束、又开始了一个新请求
  • WHEN放行 tick
  • THEN没有对 a1 调用 TaskStop，账本没有追加 heal

Requirement: 两个计时器并存时同一超时 agent 只处理一次

两个看门狗计时器同时存活、各 tick 一次时，被两个计时器都取到的那个超时 agent SHALL 只被处理一次：一条 heal、一次 TaskStop。

Design · 05技术设计

Context

- 起因：#54 合入时的 ship 评论有 25 条未修的 MEDIUM / LOW，另有用户在会话里遇到的「基线进度不可见」。决策页 docs/flight-armed-followups.html，Q1–Q6 全按推荐（2026-10-13）。 - 现状（main a495374，orchestrator.tsx）： - takeoffArmed（约第 808 行）与自动重试 advanceArm（约第 881 行）已经共用 armBusy 互斥（#54 S4 评审 HIGH 的修复）。连按两次批准带不会重复起飞，但第二次的拒绝原文是「正在自动重试起飞」，容易误读。 - runStep 重试回来后，只要待命的 since 变了就直接 return（约第 869 行），起飞成功的结果也一起被丢掉。 - /flight abort 取消待命（约第 1097 行）不看 armBusy。 - runStep 的 submit 分支先置 awaitingModel，再在 clock.after(0) 里提交。 - 「正在飞」拒飞（约第 665 行）只看 active.has(name)。 - 批准带的续飞按钮（register.tsx 的 startResume）先跑 2–3 分钟基线再调 takeoffNow。这段时间批准带不加锁，再按一次会并发启动第二个基线进程。 - 实测（CLI 2.1.296，临时 mod，不进仓库）： 1. 插件提交的那一轮，开始时刻（turn.complete 时的 clock.now 减 durationMs）比 prompt.submit 完成的时刻早 7–20 ms。所以「开始晚于提交完成」这条判据会挡掉正确的轮次；要在调用 submit 之前记下 T0。 2. Button 没有禁用属性。「不可按」的做法是不渲染按钮，只显示文字。 - 约束：铁律 7、10 不变；插件里 $ 不出文件；测试与插件是隔离实例。

Goals / Non-Goals

Goals - 三个起飞入口之间不再有「回复与事实不符」或「白耗预算」的窗口；卡住的飞行可以直接续飞。 - 批准带从按下到起飞返回，全程可见、不可重复按。 - 文档与规格跟上 0.10.0 的行为。

Non-Goals - 不改「被拒即待命」的分类与预算（#54 已定）。 - 批准带每次刷新读三遍账本的性能问题，留 backlog。 - 起飞（takeoff）与批准带工件计数里不带 -z 的 porcelain 解析，留 backlog；本 change 只修 land.ts 的已暂存删除识别。

架构（轻量 C4 · Mermaid）

  • 两层互斥：
  • 批准带层（register.tsx）只管自己按下的那一项，覆盖续飞的基线阶段，并据此显示进度；
  • 起飞层（orchestrator.tsx 的锁）管三个入口。
  • 假设：锁都在进程内，进程重启即释放；账本仍是唯一事实来源。

Risks / Trade-offs

[批准带进行中表只在进程内] → 进程重启后表就空了；但重启也会打断后台基线，与现状一致。账本与 gate-baseline.json 的运行标记仍是事实来源。
[durationMs 是墙钟时长] → 主会话轮次被人中断（aborted）也会有 turn.complete，按同一规则判断；被中断的那一轮若是提交的那轮，会触发一次重试。这是可以接受的。
[「正在飞」放宽] → drive 两轮之间可能出现短暂的「无活 agent、drive 不在跑」。此时人发续飞会被放行，再次起飞走 takeoff 的全套检查（指纹、跨会话等），最坏是续飞同一 attempt，不会重复派发已合回的切片。
