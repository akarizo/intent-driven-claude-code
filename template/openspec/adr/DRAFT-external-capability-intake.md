# DRAFT. 从外部 prompt 工程吸收能力的判据

- Status: accepted
- Date: 2026-09-13
- 关联：DRAFT-gate-evidence-not-self-reported（本决策是它在"外部能力吸收"方向的补充，不 supersede）· DRAFT-apply-as-flight（吸收落点在其实现段）

## Context

外部 AI 编码规则产品会持续出现，而且传播力远高于本体系：`DietrichGebert/ponytail`（@ `356918e`，136,912 star，9,649 行仓库，核心主张 120 行 SKILL.md）就是一例。它们诊断的问题往往是真的——AI 的默认失败模式确实是过度构建——所以每次出现都会有"要不要装"的压力。

2026-09-13 对它做了一次以本仓库 11 条铁律为判据的审查，结论是**症状端强、机制端弱**：

- 三个 hook 全是 `SessionStart` / `SubagentStart` / `UserPromptSubmit`，只做注入与状态标记，**没有一个 `PreToolUse` / `PostToolUse`**；它自己定的规则（`ponytail:` 注释要带 ceiling 与升级路径、非平凡逻辑要留可跑的 check）零机械校验，而这些恰好都是脚本可判的。
- CI 三步（`check-rule-copies` · `check-versions` · `npm test`）守的是 8 份规则副本与 13 份平台清单不漂移；6,042 行测试与 benchmark 里，**进 CI 的行为验证是 0 行**——`behavior.yaml` 需要 API key 不在 CI，`tests/behavior.test.js` 那 80 行测的是 grader 自己。CI 全绿不等于技能还有效。
- 它的规则里真正有效的那几条（先搜已有 · 根因修复 · 不加无谓依赖 · 拒投机抽象），本质是**可维护性规则伪装成懒规则**——"懒"只是更容易被模型服从的指令形式。
- 同时它带着与本体系正面冲突的条款：`YAGNI applies to tests too`、"解释比代码长就删掉解释"、`ultra` 档"挑战剩下的需求"、`no drift` 的常驻人格。

如果没有一套判据，这类产品只有两种处理方式：整包装上（连冲突条款一起吸收），或整包拒绝（连有效条款一起丢掉）。两种都错。

## Decision

**外部能力按「同向性 + 判据归属」逐条吸收，不按产品整包取舍。** 具体：

1. **三道闸门，逐条过**（顺序即优先级，任一道判出即停）：
   - **Q1 这是本仓库的真缺口吗？** 需要指向具体文件与具体缺失条目的证据；"看起来有用"不算。无证据 → 不做，并记下**观察判据**（何种事件出现几次才重开）。
   - **Q2 已有机制覆盖了吗？** 覆盖即砍。示例：初版规划要加"依赖新增门禁"，读过切片 `owns` 白名单（G6 拒绝非 owns 写入）与 `intent-gate` 的中级+ 触发条件（"引入新抽象或依赖"）后判定已被两层覆盖。
   - **Q3 能机械判定吗？** 能 → 落 hook / 门禁脚本（铁律 9）；不能 → 落角色契约文本（执行体纪律 + 评审维度），**不得**落成"要求模型自述做过"（那违反判据禁自证）。
2. **吸收的落点按时点选择**：能在动手前解决的放实现段（`slice-executor.md`），需要语义判断的放评审段（`code-reviewer.md`），可机械判的放门禁（`slice-gate.py`）。**不放常驻记忆**——阶段性纪律常驻会在一半时刻是错的，且 `CLAUDE.md` 的辖区是"不写会静默做错"的事。
3. **永久拒绝以代码长度为判据的任何机制**（LOC 阈值、diff 行数上限、"能一行就一行"的硬性要求）。理由：长度分不清**压缩**与**简化**——200 行分层清晰的实现比 40 行挤进一个函数的更好维护。ponytail 自己的 `benchmarks/agentic/run.py` 注释坦白过度工程只能用 source LOC 做 proxy、真要测得另起 LLM judge。
4. **拒绝的条款要留档**（本 ADR 的清单），使"为什么不装那个"不必每次重新论证：
   - 测试 YAGNI / trivial 免测 → 冲突铁律 2、3。
   - "解释比代码长就删解释" → 冲突铁律 8；本体系反向处理（把简化的天花板钉在代码旁）。
   - `ultra` 档挑战需求 → 冲突铁律 1，范围由意图工件定。
   - 常驻人格与 `no drift` → 阶段切换不是故障。
5. **反向吸收对方的方法学，不只是规则**：ponytail 在"度量"这条上比本仓库硬——`--selftest` 先证明 scorer 能区分 good / bad 参考实现才允许消费 API，`--rescore` 让改指标不重复付费，README 主动把自己旧的 80–94% 降级为"均值 54%、94% 是天花板"，并照登了一份对自己不利的第三方复现。**据此定规：每条新门禁判据必须带一对 good / bad fixture**——合规样本必过、每种违规必被抓且点名位置、非目标必须有守卫测试。

## Consequences

- **更易**：下一次遇到同类产品（cursor rules 集、agent 人格插件），有一张可复用的闸门表，逐条过即可，不必整包辩论。
- **更易**：吸收物天然带执行器或带评审维度，不会变成"写在文档里的好意"——这正是 ponytail 那条 `ponytail:` 注释规范失效的原因。
- **更难**：每条吸收项都要先拿出"本仓库确实缺"的文件级证据，规划成本上升。这是刻意的：Q2 那一刀在本次直接砍掉了一个已被覆盖的候选。
- **更难**：拒绝清单是硬约束。将来若有人要引入长度类判据，需要 supersede 本 ADR，而不是打个例外。
- **代价**：Q1 的"观察判据"需要有人真的去看（本次记录的是：连续 3 个切片被 `code-reviewer` 报重复实现，才重开 reuse 预搜 hook 的 change）。没有机制保证有人看——这一条目前靠 ADR 与 Open Questions 留痕，是已知的薄弱处。
