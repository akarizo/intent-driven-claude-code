Why · 01为何而做

2026-10-14 人反馈批准带「一直弹出」flight-review-followups 与 flight-hardening。查明： - flight-review-followups 在 2026-10-11 批准后从未起飞。批准带对「已批准、尚未起飞」的项永远显示「起飞」，没有任何撤下入口；它的计划基于 #45，落后 main 12 个 PR，误按会在旧代码上起飞。人只能手动删 change 目录。 - flight-hardening 只在 0.9.0 及更早的插件下显示（先判停飞、后判落地），0.10.x 已不显示，不在本 change 范围。

删掉的 flight-review-followups 里有 3 个问题在 main（ed53487）上仍未修（其余 2 项已由 #47 做掉或已过时）：

| # | 来源 | 问题 | |---|---|---| | 1 | #44 评审 MEDIUM | classifyDirty 把 porcelain 改名行（a -> b）当成工件：git add 失败后报「提交工件失败」。flight-dispatch-followups 记进 backlog 的「Y 位改名」是同一类 | | 2 | #44 评审 MEDIUM | 人要「确认无误」，却只看得到工件个数：手打命令的拒绝信息、起飞回复、批准带说明行都只写「N 个」 | | 3 | #45 评审 MEDIUM | 基线已有预存红时，pytest-cov 覆盖率未达标会被放过：它把退出码改成 1，失败用例数不变，差分后判绿 |

人在 2026-10-14 选定：四项合成一个 change；撤下入口做成批准带上的「搁置」按钮，在账本记事件；与 flight-dispatch-followups 并行，从当前 main 切。

What · 02变更范围

  • 批准带「搁置」（新）：
  • 可操作的项（没有问题、不在进行中）在主按钮旁多一个次要按钮「搁置」；
  • 按下后，插件在账本记一条 shelve 事件，带当前计划指纹；
  • 搁置后：这个指纹不再出现在批准带上，此前的批准作废，起飞守卫拒飞并说明「已搁置」；
  • 计划一改（指纹变化），批准带重新显示「批准起飞」（停飞的显示「批准修订并续飞」）；
  • 主检出的判定器不认识 shelve 时拒绝搁置，不写账本，避免旧判定器把账本判成损坏。
  • 批准带读账本改用主检出的判定器：与起飞一致；主检出没有判定器时沿用 change 所在 worktree 的（同现状）。这样，基于旧 main 的陈旧 worktree 被搁置后，账本不会被它自带的旧 ledger.py 判成损坏。
  • 改名行归为工件之外（问题 1）：路径含 -> 的一律归为工件之外（X 位、Y 位都算），起飞按「工件之外」拒绝，不提交任何文件。
  • 逐行列出工件（问题 2）：
  • 手打 /opsx-apply <change> 因只有工件而拒绝时，逐行列出工件；
  • 经「授权提交」起飞的回复逐行列出已提交的工件；
  • 批准带说明行之下逐行列出将被提交的工件，最多 5 行，其余写「…另 N 个」。
  • 覆盖率未达标不可度量（问题 3）：gate.test 的输出含 pytest-cov 的覆盖率失败标记时，判不可度量、按退出码判红，理由写「覆盖率」并提示 --no-cov。
  • 文档：opsx-apply 命令与 openspec-apply-change skill 同改，写明「搁置」与「已搁置」。
  • ADR：新增 DRAFT-approval-revocable-by-shelve，supersede DRAFT-approval-bound-to-plan-fingerprint（批准判据加上「其后未被搁置」）。
  • 插件补丁版本 +1（不写死版本号；与 flight-dispatch-followups 的 0.10.3 后合者解冲突）。
判定器：template/.claude/hooks/ledger.py（shelve 事件、latest_decision）、takeoff-gate.py（「已搁置」）、slice-gate.py（run_test_gate）。插件：template/plugins/flight/hooks/register.tsx（搁置按钮与按键、读账本的判定器、列工件）；io.ts（事件表加 shelve）、land.ts（classifyDirty）、orchestrator.tsx（拒绝信息与起飞回复）、types/index.d.ts；.claude-plugin/plugin.json（补丁版本 +1）。文档：template/.claude/commands/opsx-apply.md、template/.claude/skills/openspec-apply-change/SKILL.md。ADR：template/openspec/adr/DRAFT-approval-revocable-by-shelve.md。测试：新增 5 个 pytest 文件；TS 测试追加在 flight.test.tsx、orchestrator.test.tsx；io.test.ts 的事件类型清单、test_dispatch_origin_docs.py 的版本断言随之更新。与 flight-dispatch-followups（待批准）重叠：都改 register.tsx、orchestrator.tsx、types/index.d.ts、plugin.json、test_dispatch_origin_docs.py；后合入的一方预合并 main 时解冲突并重跑 baseline。

Specs · 04行为规范 (Gherkin)

flight-band-shelve ADDED

Requirement: 搁置撤销批准，起飞守卫拒飞「已搁置」

账本 SHALL 认识 shelve 事件（必需字段 fp，64 位十六进制）。起飞批准的判据 SHALL 为：账本里最后一条 approve 或 shelve（「最新决定」）是 approve，且其 fp 等于当前计划指纹。最新决定是 shelve 时，takeoff-gate.py SHALL 以 3 退出，stderr 含「已搁置」与搁置的指纹前 8 位，SHALL NOT 含「未批准」或「计划已变」；ledger.py approved SHALL 不输出指纹。

Feature: 2026-10-14 人反馈批准带一直挂着已批准、从未起飞的 change，没有撤下入口；撤下必须让此前的批准作废，否则手打 /opsx-apply 仍会起飞。起飞待命（armed.ts classifyRefusal）把含「未批准」「计划已变」的拒绝归为「等人按批准带」，而搁置后批准带不显示该项，所以提示文字须避开这两个词，归为「只能人处理」、只通知。

Scenario: shelve-revokes-approval

  • GIVENdemo 的账本依次有 approve（当前计划指纹 F）与 shelve（指纹 F）
  • WHEN运行 takeoff-gate.py --change-dir <demo> 与 ledger.py approved --change-dir <demo>
  • THENtakeoff-gate 以 3 退出，stderr 含「已搁置」与 F 的前 8 位，不含「未批准」与「计划已变」
  • ANDledger.py approved 以 0 退出、stdout 为空

Scenario: later-approve-after-shelve-passes

  • GIVENdemo 的账本依次有 approve（指纹 F）、shelve（指纹 F）；之后计划改动、当前指纹为 G，账本再追加 approve（指纹 G）
  • WHEN运行 takeoff-gate.py --change-dir <demo>
  • THEN以 0 退出，stdout 含 G 的前 8 位

Requirement: 批准带「搁置」按钮

批准带顶部那一项可操作（没有问题、不在进行中）时，SHALL 在主按钮之后显示次要按钮「搁置」，其 key 为 shelve:<change>:<指纹>。按下且核对通过后，插件 SHALL 在账本追加一条 shelve 事件（fp 为当前指纹，by.plugin 为 flight，by.surface 为按下的绘制面），toast 含「已搁置」，并刷新批准带。账本里最新决定是 shelve、且其指纹等于当前指纹的 change，SHALL NOT 出现在批准带上。

Feature: 搁置适用于全部四种模式（批准起飞、起飞、批准修订并续飞、续飞）。

Scenario: shelve-press-writes-event-and-hides

  • GIVENdemo 已批准（最近 approve 晚于最近 takeoff，指纹 F），批准带显示 demo 的「起飞」
  • WHEN按下 key 为 shelve:demo:<F> 的按钮
  • THEN账本追加了一条 ev 为 shelve、fp 为 F、by.surface 为 terminal 的事件；有一条 toast 含「已搁置」
  • AND刷新后批准带上没有任何按钮；起飞守卫没有因这次按键运行

Scenario: shelve-hides-halted-flight

  • GIVENgamma 的最新 attempt 以 kind 为 blocked 的 halt 结束，计划未改，批准带显示 gamma 的「续飞」
  • WHEN按下 key 为 shelve:gamma:<F> 的按钮
  • THEN账本追加了一条 fp 为 F 的 shelve 事件
  • AND刷新后批准带上没有 gamma；没有发生续飞（没有跑基线、起飞守卫没有运行）

Requirement: 改动计划后重新出现

最新决定是 shelve 但其指纹不等于当前计划指纹时，批准带 SHALL 按现有规则显示该 change：未停飞时为「批准起飞」，已停飞时为「批准修订并续飞」。

Scenario: replanned-shelved-change-reappears

  • GIVENdemo 的账本依次有 approve（指纹 F）与 shelve（指纹 F）；计划改动后当前指纹为 G
  • WHEN批准带刷新并绘制
  • THEN出现 key 为 approve:demo:<G>、label 为「批准起飞」的按钮

Requirement: 判定器不认识 shelve 时拒绝搁置

按下「搁置」时，插件 SHALL 先用批准带读账本所用的判定器运行 ledger.py events。退出非 0 或输出里没有 shelve 时，SHALL toast 含「不认识 shelve」与「未搁置」，SHALL NOT 写账本。

Feature: 读取方不认识的事件写进账本，会让整条账本判损坏、起飞被永久拒绝（PR #39 评审 HIGH 的同类问题）。

Scenario: shelve-refused-when-judges-unaware

  • GIVENdemo 未批准（指纹 F），批准带显示 demo 的「批准起飞」与「搁置」；ledger.py events 的输出不含 shelve
  • WHEN按下 key 为 shelve:demo:<F> 的按钮
  • THEN有一条 toast 含「不认识 shelve」与「未搁置」
  • AND没有任何写账本的 git 调用；批准带仍显示 approve:demo:<F>

Requirement: 批准带读账本用主检出的判定器

批准带对 ledger.py 的全部调用（approved、show、events）SHALL 使用主 worktree 的判定器目录（有 plan_fp.py 的 .claude/hooks 或 template/.claude/hooks）；主 worktree 没有判定器时，SHALL 回退到该 change 所在 worktree 的目录。plan_fp.py 与 slice-gate.py baseline 的来源不变。

Feature: 账本是共享的 git 引用；起飞已用主检出的判定器读它。基于旧 main 的 worktree 自带的旧 ledger.py 不认识 shelve，会把搁置后的账本判成损坏。

Scenario: band-reads-ledger-with-main-judges

  • GIVEN主 worktree /repo 的判定器在 /repo/template/.claude/hooks；/repo/.worktrees/demo（分支 worktree-demo）里有未完成的 demo，也自带一份 template/.claude/hooks
  • WHEN会话启动、批准带刷新
  • THEN每次 ledger.py 调用的脚本路径都是 /repo/template/.claude/hooks/ledger.py
  • ANDplan_fp.py 的调用仍是 /repo/.worktrees/demo/template/.claude/hooks/plan_fp.py

takeoff-dirty-reporting ADDED

Requirement: porcelain 改名行归为工件之外

插件对 change worktree 未提交路径分类时，路径含 -> （porcelain 的改名行，X 位与 Y 位改名都是这个形状）SHALL 归为工件之外，即使源或目标路径在 change 目录内。起飞因此 SHALL 按「工件之外」拒绝，SHALL NOT 提交任何文件（含遗留飞行记录）。

Feature: #44 评审 MEDIUM：改名行被当成工件，git add 失败后报「提交工件失败」，之前可能已单独提交了记录；flight-dispatch-followups backlog 的「Y 位改名」同属此类。

Scenario: rename-refused-before-any-commit

  • GIVENdemo 已批准、账本为空；git status --porcelain 有三行：R <change 目录>/a.md -> <change 目录>/b.md、 R <change 目录>/c.md -> <change 目录>/d.md、?? <change 目录>/proposal.md
  • WHEN人发出 /opsx-apply demo 授权提交
  • THEN回复含「工作区不干净」「工件之外」与这两条改名行（去掉 XY 两列后的原文）
  • AND没有任何 git add 或 git commit；账本没有 takeoff

Requirement: 拒绝信息与起飞回复逐行列出工件路径

未提交改动只有工件、且没有「授权提交」而拒绝起飞时，回复 SHALL 逐行列出这些工件路径。经「授权提交」提交工件后起飞时，回复 SHALL 写明已提交的工件个数，并逐行列出这些路径。有工件之外改动时，拒绝信息仍只列工件之外的路径。

Feature: #44 评审 MEDIUM：插件让人「确认无误」，却只给个数，人无法核对。

Scenario: refusal-lists-artifact-paths

  • GIVENdemo 已批准、账本为空；未提交的只有 <change 目录>/proposal.md、template/openspec/adr/DRAFT-x.md 与 scenario 测试文件 tests/test_s1.py
  • WHEN人发出 /opsx-apply demo
  • THEN回复含「工作区不干净」、/opsx-apply demo 授权提交，并且这三个路径各占一行

Scenario: takeoff-reply-lists-committed-artifacts

  • WHEN人发出 /opsx-apply demo 授权提交
  • THEN回复含「✈ 起飞」、「已提交工件 3 个文件」，并且这三个路径各占一行

Requirement: 批准带逐行列出将被提交的工件

批准带显示「批准起飞」「起飞」或「批准修订并续飞」且有未提交工件时，说明行「按下会提交本 change 的 N 个工件…」之下 SHALL 逐行列出工件路径，至多 5 行；超过 5 个时，第 6 行 SHALL 为「…另 K 个」（K = N − 5）。

Scenario: band-lists-artifact-paths

  • AND有一行文字为「…另 2 个」；没有含 f6.md 或 f7.md 的文字

test-gate-coverage-failure ADDED

Requirement: 覆盖率未达标时全量测试不可度量

gate.test 的输出（去掉 ANSI 后）任一行含 pytest-cov 的覆盖率失败标记（Coverage failure: total of 或 FAIL Required test coverage of）时，本次全量测试结果 SHALL 判为不可度量、按退出码判。理由 SHALL 写明「覆盖率」，并提示门禁不判覆盖率时在 gate.test 加 --no-cov。

Feature: pytest-cov（7.1.0 源码核实）在 fail-under 未达标时把 session.testsfailed 加 1、退出码变 1，失败用例计数不变；基线有预存红时，原先会被当成「失败全是预存红」判绿（#45 评审 MEDIUM）。

Scenario: final-red-on-coverage-failure

  • GIVENgate.test 为 pytest；基线已生成：test_old 失败（预存红），其余通过
  • AND之后提交了 tests/conftest.py：按 pytest-cov 的做法，在测试跑完后打印两行覆盖率失败标记，并把 session.testsfailed 加 1
  • WHEN运行 slice-gate.py final
  • THENok 为 false
  • ANDfailed 有一项以「G2 test」开头，含「按退出码判」与「覆盖率」

Scenario: baseline-red-on-coverage-failure

  • GIVENgate.test 为 pytest；test_old 失败，且 tests/conftest.py 同上
  • WHEN运行 slice-gate.py baseline
  • THEN退出 1
  • ANDreasons 有一项含「覆盖率」与 --no-cov

Context

Goals / Non-Goals

Goals： - 人能在批准带上把「不打算飞」的计划撤下，撤下后不能误起飞； - 前 3 个遗留问题各有 scenario 测试； - 正常路径（干净工作区、未搁置、无覆盖率门槛）的行为不变。

事件

{"ev": "shelve", "fp": <64 位十六进制>} + 公共字段（v / change / at / by.plugin），by 里带 surface 与 session（同 approve）。ledger.py 与 io.ts 的 EVENTS 同时加这一项。

取账本里最后一条 approve 或 shelve，称为「最新决定」：

Risks / Trade-offs

[插件升级后，使用方的主检出判定器仍是旧版] → 起飞被 checkJudges 拒绝，提示判定器不认识 shelve（与以往新增事件相同）；搁置也拒绝、不写账本。迁移说明见下。
[主检出没有判定器，回退到 change worktree 的旧 ledger.py] → 搁置前的 events 核对会发现它不认识 shelve 而拒绝，账本不会被写坏。
[批准带的 plan_fp.py 仍取 change worktree 的，与起飞的主检出不同] → 两边算法不同时，批准带显示的指纹会与起飞时重算的不一致，起飞报「计划已变」。这是现状就有的问题，本 change 不扩大；记作后续。
[误按「搁置」] → 只会收回放行；改动计划任一文件即可重新出现、重新批准。
[pytest-cov 将来改了提示文字] → 识别失效，退回原行为（放行），这一项不是 fail-closed。缓解

两行标记任一命中即可；scenario 测试按 7.1.0 的原文构造，升级时对照。

[基线已有预存红时，conftest 或其他插件自己把退出码改成 1，而失败用例不变] → 仍判可度量并放行。从退出码与计数上无法区分，只能识别具体工具的输出；本 change 只覆盖 pytest-cov。
[与 flight-dispatch-followups 同改 register.tsx（按键入口）、orchestrator.tsx、类型与版本] → 后合入的一方预合并 main 时解冲突、重跑 baseline；计划文件不变则指纹不变。

Migration Plan

  • 本仓库：合入后在主仓库根执行 claude plugin update flight@intent-driven -s project，再 /reload-plugins，确认插件版本为本 change 升出的版本；主检出的 template/.claude/hooks/ 随同一次合入更新。
  • 插件使用方：升级插件的同时更新主检出的 .claude/hooks/（install.sh --upgrade），否则起飞被拒、搁置被拒。
  • 门禁判红：使用 pytest-cov fail-under、且覆盖率当前不达标的仓库，下一次 baseline 会判红，按提示在 gate.test 加 --no-cov。
  • 不需要数据迁移：旧账本没有 shelve，判据结果不变。回滚即回退提交；回滚前已写入 shelve 的账本会被旧判定器判损坏，须先确认没有搁置过。
