每个 change 一个独立 worktree —— 所有产物落在 worktree 内，主仓库工作区永远干净

你提出两条规避规则。我把它们提炼成一条贯穿 intent-driven 生命周期的「隔离纪律」，并定位到 template 里最精确的落点。请审阅意图，确认后我再动手。

回执你已拍板的三项决策

worktree 粒度
每个 change 一个 worktree —— 不推翻「逐 task 在同一区串行累积」的设计，只是把整个 change 的工作区从 main 挪到独立 worktree。
worktree 权威路径
${workspace}/.worktrees/（复数，仓库根下）—— 沿用 bulk-apply 已用的约定，统一三处不一致的旧写法。
工件约束范围
所有产物（5 工件 + spec.html + 实现代码）都必须落在 worktree 内，主仓库工作区不落任何产物。

1为什么要改

现状 · 问题

整个 opsx 生命周期（propose → continue → apply → verify）默认在当前工作区（通常是 main）里产生所有工件与实现代码。

  • main 工作区被半成品工件 + 未完成实现污染
  • 并行推进多个 change 时互相踩踏
  • worktree 只在 bulk-apply（多 change 并行）时才用，单 change 完全裸奔在 main
目标 · 隔离纪律

一个 change 从 propose 起手就进入 .worktrees/<change>/ 的独立 worktree + branch。

  • 该 change 的一切产物都落在这个 worktree 内
  • 主仓库工作区（main）永远只剩已合并的历史，随时干净
  • 逐 task 仍在同一个 worktree 内串行累积（task 依赖前序产出，不受影响）

2核心机制：切 CWD，不改路径常量

关键洞察 —— 为什么这个改动很小 所有 skill / hook / openspec CLI 用的都是相对路径（openspec/changes/<change>/…）。只要把 worktree 根设成当前工作目录（CWD），这些相对路径就自然落在 worktree 内。因此无需改写每个 skill 的路径常量 —— 只需在生命周期入口建立「进 worktree」这一步。 
主仓库根 (main, 始终干净)
  intent-driven-claude-code/
  ├─ .claude/  openspec/  CLAUDE.md          ← 已合并的历史
  └─ .worktrees/                             ← gitignore, 每 change 一间
       ├─ add-user-auth/   [branch: worktree-add-user-auth]
       │    └─ openspec/changes/add-user-auth/
       │         ├─ proposal.md specs/ design.md  ← 工件落这里
       │         ├─ tasks.md  spec.html              ← HTML 面板也落这里
       │         └─ …
       │    └─ src/…                          ← apply 实现代码也落这里
       └─ fix-cache-ttl/   [branch: worktree-fix-cache-ttl]  ← 并行不踩踏

生命周期时序
  /opsx-propose add-user-auth
     │  ① git worktree add .worktrees/add-user-auth -b worktree-add-user-auth
     │  ② cd 进该 worktree (CWD = worktree 根)
     │  ③ openspec new change → 工件写入 worktree 内 openspec/changes/…
     ▼
  /opsx-continue → 后续工件 + spec.html 全在同一 worktree
     ▼
  /opsx-apply → 逐 task subagent 在同一 worktree串行累积实现代码
     ▼
  /pr-ship → 从 worktree-add-user-auth 发 PR，合回 main（你授权）
     ▼
  worktree remove（在主仓库根执行）→ 该 change 收尾

4一处必须点破的既有冲突

「逐 task 守门」曾写「不开 worktree」—— 与新规则字面打架，实则可调和

openspec-subagent-apply-change 现在明确写着「为什么不开 worktree：逐 task 是串行累积，Claude Code 原生 isolation:worktree 每次派发都新建独立 worktree、看不到前序产出」。

调和方式（与你「每 change 一个 worktree」的决策完全一致） 那段话反对的是「给每个 task 各开一个 worktree」——这仍然错，不改。新规则要的是「整个 change 一个 worktree」。两个粒度不冲突：change 级开一间 worktree，change 内逐 task 在这一间里串行累积。改动只是把该 skill 里「当前工作区」的措辞澄清为「本 change 的 worktree」，并在 subagent prompt 里把「不要新建 worktree」改成「在本 change worktree 内操作、不要再嵌套子 worktree」。逐 task 累积机制、commit 锚点、门禁豁免全部零改动。

5边界：这次不碰什么

  • 不改 intent-gate.py 门禁 —— 它用相对路径判断，CWD 切到 worktree 后行为不变，零改动生效。
  • 不改 spec-html-render 输出路径常量 —— openspec/changes/<change>/spec.html 是相对路径，CWD 在 worktree 内即自然落对。
  • 不改 install.sh 拷贝逻辑 —— 它拷 template 的静态文件，与运行期 worktree 无关；仅 .gitignore 随 template 分发。
  • 不自动 commit / branch / merge / 清理 worktree —— 建 worktree 是工作区准备（非 lifecycle 状态推进），但 merge / 删分支 / worktree remove 仍交你授权（守 CLAUDE.md git 铁律）。
  • 不走完整 5 工件 opsx 流程 —— 本次产物全是规则文档（.md / .snippet / .gitignore，门禁豁免路径），且是对工作流规则自身的元修改；用 HTML 面板审批意图更合适。

  • 规则自洽：git-discipline 新节 与 各 skill 指针互指无悬空；grep -rn '\.worktrees\?' template/ 全部指向复数 .worktrees/，无残留单数写法。
