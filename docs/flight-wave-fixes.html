3 · 修法设计（按推荐范围）

A · expectHead 只取一次

修法比对值来源谁判定放到这次飞行里结论
① 脚本维护 currentHead，取 integrator / gate 返回的 commit模型自报执行体w2 报的是 6bc66a7，实际 tip 是 f1e6b95 → wave 3 仍然误红不推荐
② 执行体 prompt 里比对分支实时 tip（git rev-parse <branch>）git执行体（由模型比对）通过可用
③ slice-gate.py start --expect-branch <branch> 做祖先校验git脚本（零 token）通过推荐
脚本参数：expectHead → branch（起飞时 git branch --show-current；分支名不变，tip 会变）
执行体第一步：slice-gate.py start S3 --change-dir … --expect-branch worktree-<change>
  start：git merge-base --is-ancestor <branch> HEAD
    是 → 写 marker，照常开工
    否 → 打印 {"slice":"S3","ok":false,"commit":"","failed":["G0 base: …"]}，exit 1，不写 marker
执行体：start 非 0 → 原样返回它打印的 JSON，不做任何改动
gate：没有 marker 就没有 base → 拒绝（失败即关，不依赖模型自觉）
  • 用「祖先」不用「相等」：重试会先 cherry-pick 上一轮的 commit，HEAD 比分支 tip 多一个 commit，相等比较在这里会误判；祖先关系在首轮和重试时都成立。
  • 单切片 wave 也覆盖：不开隔离时执行体就在 change worktree 里，HEAD 就是 tip，自然通过。#32 的 S3 就是在这种情况下被误判的。
  • G0 失败时 commit 置空：上一轮没有产出，重试按首轮处理，不再 cherry-pick。现在 G0 的 JSON 填的是「实际 HEAD」，如果基点真的错了，重试会把一个无关的 commit 接进来。
  • 验证：test_slice_gate.py 覆盖 start 的三种情况（是祖先、不是祖先、重试时 HEAD 超前）；test_agents_workflow.py 覆盖脚本不再按 expectHead 比对、start 命令带 --expect-branch。

B · integrator 合回时自跑 final

修法改动取舍
① 合回用独立返回结构 {ok, merged, failed, warnings}，prompt 明令「不要运行第 3 项」；integrator.md 第 3 项改为「prompt 点名才跑」；integ.ok 只看合回和 record 是否成功脚本 + integrator.md推荐。切片门禁已经各自跑过 verify；wave 级全量测试改变不了后续决策（Fix 本来就在所有 wave 之后），只会增加耗时
② 在 ① 的基础上，每个 wave 合回后跑 final --slices <已完成>（新模式）再改 slice-gate.py每个 wave 多一次全量测试，收益只是早一点知道
③ 保留共用的 GATE schema，只在 prompt 里禁止跑 final最小GATE 要求的 slice / commit / failed 字段仍会诱导 integrator 去填；三个 wave 三种返回形状就是这么来的
  • 效果：stc 那次会少 2 行 final red、少 2 条 infra 误报，收口时的「门禁红次数」从 4 回到 2。
  • 验证：test_agents_workflow.py 覆盖合回派发不再使用 GATE schema、prompt 含「不要运行第 3 项」、integrator.md 第 3 项带条件。
  • 更彻底的方向（不在本次范围）：把合回整段脚本化，integrator 只跑一条命令，可以先进 backlog。

D · ship 要求 final 对齐 HEAD

  • 现状：slice-gate.py:873 要求 final 行的 commit 等于 HEAD。收口顺序是 final → 勾 tasks.md → 写 review-findings.json → 提交飞行记录，HEAD 必然前进，于是每次都要重跑 final；PR 转 ready 之后再提交飞行记录，又会超前。
  • 改法：final 与 HEAD 不相等时，看 git diff --name-only <final> HEAD：改动全部落在 change 目录的 5 个记账文件（timeline.md、gate-report.md、evidence.log、review-findings.json、tasks.md）里，仍判 final 有效；源码、测试、specs、slices.json 只要改过一个，照旧判过期。final 不是 HEAD 的祖先（比如被 rebase 过）也判过期。
  • 白名单依据：stc 的 3be9fd9..8fa0e50 和 8fa0e50..ac2158d 两段实际改动，都是这 5 个文件的子集。
  • 验证：test_ship_verdict.py 三个场景：只改记账文件 → ready；改源码 → final 过期；改 slices.json → final 过期。

F · 评审取 diff：拉不到 ≠ 无变更

  • 现状：pr-ship.md 第 8 步与 code-reviewer.md:32 把「为空」和「拉不到」合在一起处理：报告无变更并停止。
  • 改法：分开处理。为空 → 无变更；gh pr diff 失败（例如 diff 过大返回 HTTP 406）→ git fetch origin <target> 后用 git diff origin/<target>...HEAD；两种都失败 → 报告「取 diff 失败」并停止，不得报告无变更。
  • 验证：test_template_docs.py（pr-ship.md）和 test_agents_workflow.py（code-reviewer.md）的文案断言。

H · .flight 忽略

  • 改法：template/openspec/.gitignore 加一行 changes/*/.flight；install.sh 在安装和 --upgrade 时，像处理 .worktrees/ 那样对 openspec/.gitignore 幂等追加这一行。install.sh:346 对 openspec/ 从不覆盖，只改模板文件到不了已安装的仓库。
  • 验证：追加两次后该行只出现一次；测试落点 propose 时定。
