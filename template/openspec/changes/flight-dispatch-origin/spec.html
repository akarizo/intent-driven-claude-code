Why · 01为何而做

flight-armed-followups 是第一次用批准带按键起飞，首轮 S1–S3 的执行体全都调不到 measure，每片都重派了一次。用 spike 复现后（CLI 2.1.296）查清了原因：插件在已经返回的 hook 里、或在定时器回调里调用 $.agent.spawn，引擎把这次派发算作插件自己发起。之后这个 agent 的工具调用 origin 都记成 flight，flight 自己的 tool.call / tool.check hook 一律按 re-entry 跳过。于是能力包络、账本守卫、measure 应答对这些 agent 全部失效。0.10.x 的按下即起飞、续飞、待命定时重试、看门狗派诊断员，这四个入口都是这种写法。

决策页：docs/flight-dispatch-origin.html（主检出，未跟踪），Q1–Q7 全按推荐。按键 hook 长时间挂起时界面不卡，已在交互会话实测通过。

What · 02变更范围

  • 定时器到点不直接派发（唤醒轮）：
  • 起飞待命的定时重试（等待类的 60 秒 tick、偶发类的 10 秒重试）到点时，不再直接起飞。条件满足时，插件提交一轮简短对话，请模型只回复「收到」；这一轮结束时，在主会话 turn.complete 里重试。
  • 等待类先零 token 检查条件（基线是否跑完、上一次的 agent 是否结束），没满足就不提交。
  • 看门狗停飞后的诊断员同样经唤醒轮派出。
  • agent 结束、主会话一轮结束这些现成触发，照旧直接重试。
  • 批准带按键在 hook 内起飞：按「起飞 / 批准起飞」「续飞 / 批准修订并续飞」后，在按键 hook 里 await 起飞或续飞，不再经 clock.after(0) 转到回调里。顺带修 #56 留下的三项：
  • 进行中再按会被拒；
  • 重绘失败不再留下「起飞中」；
  • 基线结束后状态行会恢复。
  • 派发凭证：所有派发都须持有「活帧凭证」。凭证只在处理外部事件的 hook 里取得，hook 返回即失效。不持有活凭证的派发当场拒绝，并按铁律 10 停飞、如实记录。
  • 交模型 / 唤醒的提交绑定待命：提交的结果只作用于安排它的那次待命；待命换新后，旧提交成功不会把新待命标为已提交，失败也不会放弃新待命（#56 MEDIUM）。
  • 文档：
  • opsx-propose 命令的 description 去掉「起飞需人类自己发 /opsx-apply」（#56 MEDIUM）；
  • opsx-apply 命令与 skill、README、WORKFLOW 补写唤醒轮。
  • 插件版本 0.10.2。
插件代码：template/plugins/flight/hooks/：orchestrator.tsx、register.tsx、armed.ts，新增 lease.ts；template/plugins/flight/types/index.d.ts；对应的 TS 测试与 pytest 包装。不改判定器（.claude/hooks/*.py），账本事件类型不变。可见行为变化：定时重试与看门狗诊断会以插件身份发一轮「只回复收到」的对话，每次多一轮主会话；按键后起飞在按键处理中完成，按键 hook 会挂起到起飞或续飞结束（实测不影响输入）。测试边界：测试世界模拟不出 origin，单测只能断言结构（定时器只提交唤醒、按键内起飞、无活凭证被拒）。真引擎上的验证靠合入后冒烟。

flight-dispatch-lease ADDED

Requirement: 派发须持有活帧凭证

插件每次派发 agent（执行体、解冲突、评审员、修复体、诊断员）都 SHALL 持有活帧凭证。凭证只在处理外部事件的 hook 里取得：/opsx-apply、/flight resume、批准带按键、子 agent 结束、主会话一轮结束。取得凭证的 hook 处理返回（或抛错）后，凭证 SHALL 失效。没有凭证或凭证已失效时，派发 SHALL 被拒，拒绝原文含「派发须在处理外部事件的 hook 里」，且 SHALL NOT 调用引擎的派发。各调用点按原有的被拒分支处理：执行体与解冲突记 blocked，进而停飞（铁律 10）。

Feature: 在已返回的 hook 或定时器回调里派发的 agent，插件的包络与 measure 对它无效，而且不报错。凭证让这类写法当场暴露，而不是悄悄绕过。

Scenario: dispatch-refused-after-hook-returns

  • GIVEN在 withLease 的 body 里取得凭证并保存下来，body 已经返回；另有一次请求不带任何凭证
  • WHEN分别用失效的凭证和「没有凭证」请求派发（guardedSpawn）
  • THEN两次都得到含「派发须在处理外部事件的 hook 里」的拒绝
  • AND派发函数一次都没有被调用

Scenario: dispatch-allowed-in-live-hook

  • GIVENwithLease 的 body 正在执行
  • WHENbody 里用它的凭证请求派发
  • THEN派发函数被调用恰一次，并原样返回它的结果

Requirement: hook 入口的派发照常

/opsx-apply 起飞派出首个 wave，以及子 agent 结束时派出下一步（评审员等），SHALL 照常派发，不因凭证要求被拒。

Scenario: command-takeoff-dispatches

  • WHEN处理该执行体的结束（turn.complete）

flight-wake-turn ADDED

Requirement: 定时到点只唤醒，在唤醒那一轮结束时重试起飞

起飞待命的定时到点（等待类的 60 秒 tick、偶发类的 10 秒重试）SHALL NOT 直接起飞或派发 agent。条件满足时，插件 SHALL 以自己的名义提交一轮唤醒对话：正文含 change 名与「只回复「收到」」，且不要求模型做任何别的事。提交时刻之后开始的主会话那一轮结束时，插件 SHALL 重试起飞。等待类在唤醒前 SHALL 先零 token 检查条件：基线仍在跑、或上一次的 agent 仍在运行时，不唤醒。同一待命已唤醒、尚未重试时，后续的定时到点 SHALL NOT 再次唤醒。

Feature: 插件只有在处理外部事件、尚未返回的 hook 里派发，派出的 agent 才经过包络与 measure。定时器回调里派发会绕过它们（flight-armed-followups 实测）。

Scenario: transient-timer-wakes-then-retries

  • AND第二次 tick 之后恰提交一次唤醒，第三次 tick 之后仍只有这一次

Requirement: 看门狗停飞后经唤醒轮派诊断员

看门狗在定时器里停飞时，SHALL NOT 在定时器回调里派诊断员。它 SHALL 记下待派的诊断，并提交一轮唤醒对话（正文含 change 名、「诊断员」与「只回复「收到」」）。提交时刻之后开始的主会话那一轮结束时，插件 SHALL 派出只读诊断员。唤醒提交失败时 SHALL 通知人，SHALL NOT 重试。

  • AND那一轮结束之后：账本有 role diagnostician、slice triage 的 dispatch

Requirement: 交模型与唤醒的提交只作用于安排它的那次待命

提交修复请求或唤醒文本之后，插件 SHALL 先核对当前待命是否仍是安排这次提交的那一次（同一 since）。成功时，只给那一次标记已提交；失败时，只放弃那一次。待命已被替换时，SHALL NOT 改动或放弃新的待命。

Feature: PR #56 MEDIUM：提交在安排它的待命之外运行，成功或失败后都按 change 重读待命，可能误标或误弃新待命。

Design · 05技术设计

Context

### 实测事实（CLI 2.1.296，spike 插件 probespike 与热重载插件 pressspike，2026-10-13）

  • 会失效的情形：插件的 $ 调用如果不在「处理外部事件、尚未返回的 hook」的异步链里，引擎就把它算作插件自己发起。这样 $.agent.spawn 出的 agent，后续工具调用的 origin 都是插件，插件自己的 hook 一律按 re-entry 跳过（含 .catch）。
  • 被跳过的 hook：tool.call、tool.check、turn.step、classic.SubagentStop。只有 turn.complete 照常到达。
  • debug 日志原文：tool.call skipped: re-entry (the plugin's own code raised it; origin probespike)。
  • agent 拿到的错误：<plugin> registered the tool X but no tool.call hook answered this call。
  • 坏的写法（都已复现）：
  • 在 clock.after 回调里调用另一个 hook 造的闭包（= 批准带按键起飞）；
  • session.start 的 $ 在它自己排的定时器里派发（= 看门狗、待命 tick）；
  • 在 hook 里不 await 地调用，等派发时 hook 已返回。
  • 好的写法（都已复现）：
  • 在活着的 hook 里直接派发，或 await 一条链路再派发（中途 sleep、跨文件闭包都不影响）；
  • 在 agent 结束的 turn.complete 里派发（= drive 现状）；
  • 定时器先 $.prompt.submit 一轮，在那一轮主会话的 turn.complete 里派发。
  • 交互实测：
  • ui.press hook 用 process.run 挂起 120 秒，期间人照常输入、发消息；
  • 期间按别的按钮也照常处理，说明按键是并发的；
  • 挂起结束后派出的 agent，Bash 守卫与插件工具都生效。
  • 没有现成的判据区分好坏 agent：
  • $.agent.list() 的 spawnedBy 在两种 agent 上都是插件名；
  • turn.complete 的 usage 里没有工具调用次数。

Goals / Non-Goals

Goals: - 插件派出的每个飞行 agent，工具调用都经过插件的包络、账本守卫与 measure。 - 定时到点的重试与看门狗诊断仍然无人值守，只是改走唤醒轮。 - 以后新增的派发如果写在回调里，当场被拒并留证据，不会悄悄绕过包络。 - 顺带修 #56 留下的 5 项 MEDIUM（见 D6）。

Non-Goals: - 不改判定器与账本事件类型。 - 不做「agent 结束后再对账」的事后检测（见 D5 的否决理由，记入 backlog）。 - 不修「排队中的 drive 不算正在飞」（#56 MEDIUM，与本缺陷无关，留后续）。 - 不改批准语义（铁律 7）：唤醒轮只请模型回复「收到」，模型仍然没有起飞入口。

Risks / Trade-offs

[唤醒轮多一轮主会话对话] → 只在定时到点、且条件已满足时才发，而且每个待命同一时间只有一次。重试预算不变（transient / model 最多 3 次）。正文要求模型只回复「收到」、不要发 /opsx-apply。
[主会话正忙时唤醒排队] → 重试推迟到那一轮结束；待命 30 分钟有效期不变，到期照旧放弃并通知。
[按键 hook 挂起数分钟] → 已实测输入不受影响；按键并发由 inFlight 拦住。
[测试世界模拟不出 origin] → 单测断言结构，包括按键返回前已起飞、定时器只提交不派发、无活凭证被拒。真引擎验证放在合入后冒烟
