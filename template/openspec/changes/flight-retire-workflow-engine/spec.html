Why · 01为何而做

阶段 3 的状态机已经接管飞行（#39 起），测量协议与包络也已就位（#40–#48）。旧的 Workflow 引擎却还完整留在仓库里，并且仍有两条入口： - 人显式加 --engine=workflow； - 插件没拦下命令时，模型照着 /opsx-apply 的 step 0–7 走下去，等于一条隐式回退。

这和已接受的 DRAFT-flight-control-plane-in-mod 第 4 条冲突：控制面缺席即停飞，不维护一条语义可能漂移的第二实现。仓库铁律也和实际做法不一致： - 铁律 10 还写着「回退必存在（Workflow → Agent 派发）」； - 铁律 3 的「回退路径 = hook 写 evidence.log」指向旧引擎； - 铁律 11 的「收口 --expect-models」也指向旧引擎，插件早已从账本对账。

DRAFT-flight-orchestrator-state-machine 与 DRAFT-flight-measure-protocol 都约定：旧引擎、integrator、门禁结论 ref、evidence.log 回退路径在 3c 删除，届时改写铁律 10。本 change 就是那一步（3c 的前半，交互与 abort 另立 change）。

  • 删除旧引擎本体：template/.claude/workflows/opsx-apply.js、agents/integrator.md、agents/slice-executor.md、hooks/session-decompose.py，以及专测它们的测试。
  • slice-gate 只留插件在用的部分（用户定：G5 只留账本判据）：

  • 已注册的旧 hook 保持安全：
  • 兼容：slice-gate.py checkpoint、不带参数的 takeoff-gate.py（hook 模式）、stop-gate.py 都改为什么都不做、退出 0 的兼容入口；
  • 原因：已安装项目与本仓库根的 settings 仍注册着它们，stop-gate.py 还是不带存在保护直接调用的，直接删除会让 Stop hook 报错、卡住会话；

  • 改写铁律 3、10、11（仓库根 CLAUDE.md、template/CLAUDE.md.snippet）：
  • 第 10 条改为「失效即停飞、不回退第二实现」；

  • 新写一份 ADR 记录这次删除与改写，取代相关旧条款。
  • 插件：/opsx-apply <change> --engine=workflow 明确拒绝并说明旧引擎已删除；--gate=per-task 照旧交给模型（护栏 scenario）。插件版本 0.5.0。
判定器与 hook：template/.claude/hooks/ 下的 slice-gate.py、takeoff-gate.py、test-evidence.py、stop-gate.py、hooks.json；删除 session-decompose.py。模板：删除 workflows/opsx-apply.js、agents/integrator.md、agents/slice-executor.md；改写 commands/opsx-apply.md、commands/pr-ship.md、agents/code-reviewer.md，以及 skills openspec-apply-change、openspec-git-discipline；改写 install.sh、template/CLAUDE.md.snippet。仓库：改写根 CLAUDE.md、README.md、docs/WORKFLOW_zh.md；新增 ADR template/openspec/adr/DRAFT-flight-single-implementation.md。插件：orchestrator.tsx 与其测试；版本 0.5.0。测试：删除 tests/test_agents_workflow.py，其中 code-reviewer 相关的用例迁出；test_slice_gate.py、test_evidence_timeline.py、test_approval_gate.py、test_template_docs.py、test_docs_iron_rules.py、test_opsx_apply_engine.py、test_ship_verdict.py、test_install.py、test_flight_orchestrator.py 相应删改。本仓库根的 .claude/settings.json 不改：主检出有未提交的本地改动，改了会挡住快进。其中已退役的 hook 靠兼容空壳安全空转，由人自行清理。

Design · 05技术设计

Context

  • 插件已是飞行唯一的执行者：插件接管 /opsx-apply（command.run），派发 flight:* agent，自己跑判定器，并把一切写进账本 refs/flight/<change>/ledger。
  • 旧 Workflow 引擎仍完整存在，入口有两条：
  • --engine=workflow（orchestrator.tsx:21 的 PASS_THROUGH 原样交给模型）；
  • 命令文档里的 step 0–7（插件没拦下命令时模型会照做）。
  • 只为旧引擎服务的机制（2026-10-12 盘点，origin/main 36d91c3）：
  • slice-gate 的 checkpoint 快照、--resume-checkpoint、门禁结论 ref、waves 别名、G5 的 evidence.log 模式与 hooks_missing、red_count；
  • takeoff-gate 的 hook 模式（拦 Workflow / slice-executor / integrator 派发）；
  • stop-gate.py（让执行体自己跑门禁）；
  • session-decompose.py：--expect-models 依赖 Workflow 的 journal，其 --session 模式没有调用方。
  • 插件仍在用的：slice-gate 的 start、record、--expect-branch、--base、gate --evidence ledger；takeoff-gate 的 CLI 模式（--change-dir）。
  • 已注册的 hook：
  • 已安装项目和本仓库根的 .claude/settings.json，都注册了 slice-gate.py checkpoint、不带参数的 takeoff-gate.py 和 stop-gate.py；
  • 其中 stop-gate.py 是不带存在保护直接调用的；
  • install.sh 的 merge_settings 只追加、不删除。
  • evidence.log 的现状：
  • 唯一的机器读者是 G5 的 log 模式，而插件一律走账本模式；
  • 飞行外（主会话修复）test-evidence 照写，供评审参考。

Goals / Non-Goals

Goals - 飞行只有一套实现：删除旧引擎及只为它服务的机制，文档只讲插件路径；插件缺席即停飞。 - 铁律与 ADR 跟实际做法一致：铁律 10 不再要求回退，铁律 3、11 不再指向旧引擎。 - 已安装项目升级、本仓库根 settings 不改的情况下，都不会因退役 hook 而出错。
