Why · 01为何而做

阶段 3 完成后，插件已是飞行的唯一执行体。但飞行的入口与出口仍依赖项目里装好的文件：

- 入口：插件只拦截名为 opsx-apply 的命令，自己不注册这个名字。项目里没有 .claude/commands/opsx-apply.md 时，/opsx-apply 报「Unknown command」。2026-10-12 本仓库就因此起飞失败：#49 删掉模板里的旧引擎文件后，根目录提供命令名的软链悬空了。 - 出口：落地后插件用 $.command.run('pr-ship') 交接给 /pr-ship，命令文件同样要由项目提供。本仓库每次飞行都失败（「no command named /pr-ship」），只能由主会话手动走。 - 来源：#50 的 D8 规定 /flight abort 与 resume 只认人发出，但 /opsx-apply 起飞不查来源，同类缺口留到了本阶段。 - 评测：阶段 5 要用 claude plugin eval 对照有插件与无插件。只有插件能独立提供入口与出口，这个对照才有意义；评测靠无头运行，来源规则也要认可宿主程序（sdk）。

2026-10-12 实测（CLI 2.1.296，无头模式，scratchpad/mods/entry-spike、handoff-spike）：

- 注册同名命令：插件 $.command.register 一个与项目命令文件同名的命令时，引擎拒绝（「refused: it is the user's /filecmd」）。插件的 command.run hook 仍能拦截这个文件命令。 - context 不触发作答：插件命令返回的 context 不会让模型接着作答。 - prompt.submit 的时机：在 command.run 里调 $.prompt.submit 被拒，引擎提示从之后的事件里提交。 - 插件 markdown 命令带命名空间：插件自带的 markdown 命令名为 <插件>:<名>，例如 /entry-spike:shipdoc。直接发 /shipdoc 找不到这个命令。 - 交接可行：在子 agent 的 turn.complete 里，经 $.command.run('<插件>:<名>') 跑插件 markdown 命令，或者 $.prompt.submit 交一段话，主会话都会在当前一轮结束后由模型接着执行。

What · 02变更范围

  • 入口由插件提供（用户定：注册加拦截两手）：
  • 会话开始时，插件注册 opsx-apply；
  • 项目已有同名命令文件时注册被引擎拒绝，忽略，照旧靠拦截接管。
  • 写账本的入口只认人或宿主程序（用户定）：
  • 涉及 /opsx-apply 起飞、/flight abort、/flight resume；
  • 来源须为 composer（终端）、bridge（Remote Control）或 sdk（claude -p / Agent SDK 宿主）；
  • 定时任务、别的会话的消息、插件代发等其他来源一律拒绝，不写账本；
  • --gate=per-task 透传与 --engine=workflow 拒绝不写账本，不受此限。
  • pr-ship 迁入插件（用户定）：
  • 搬进插件，单一来源：pr-ship.md 进 template/plugins/flight/commands/，即 /flight:pr-ship；它派发的 code-reviewer 进 template/plugins/flight/agents/，即 flight:code-reviewer。模板不再提供这两个文件。
  • /flight:pr-ship 接受 --worktree、--change-dir、--judges 三个参数。缺省依次为当前目录、openspec/changes/<name>、.claude/hooks。
  • 落地交接改为 /flight:pr-ship：
  • 落地后插件调用 /flight:pr-ship --worktree <change worktree> --change-dir <change 目录> --judges <判定器目录>；
  • 交接失败的提示也改为这个命令。
  • 派发守卫放行评审员：主会话可以派发 flight:code-reviewer（仍须显式 model）。其余 flight:* 仍只能由控制面派发，飞行中的 agent 仍不得再派发子 agent。
  • 安装器与文档：
  • 安装器不再安装这两个文件；升级时若发现旧副本，列为「已迁入 flight 插件」，不代删；
  • README、WORKFLOW、命令与 skill（含 legacy）、仓库 CLAUDE.md 第 6 条改为 /flight:pr-ship 与 flight:code-reviewer；
  • /opsx-apply 命令与 skill 写明来源规则，补上 #50 的文档遗留。
  • 版本：插件 0.7.0。
  • /pr-ship 改名为 /flight:pr-ship，code-reviewer 改为 flight:code-reviewer。已装项目里的旧副本仍可用，但不再更新。
  • 不标明来源的 /opsx-apply（例如定时任务触发）不再起飞。
插件：hooks/ 下的 orchestrator.tsx、landing.tsx、envelope.ts；新增 commands/pr-ship.md 与 agents/code-reviewer.md，由模板迁入；版本 0.7.0。模板：移除 .claude/commands/pr-ship.md 与 .claude/agents/code-reviewer.md；/opsx-apply 命令与 skill、legacy skill 改引用。安装器与文档：install.sh、README.md、docs/WORKFLOW_zh.md、仓库 CLAUDE.md。测试：读取这两个文件的 6 个测试改路径；插件测试世界里 58 处 /opsx-apply 调用补上来源。本 change 自己的飞行：在插件 0.6.0 上飞，入口靠本仓库根目录的 .claude/commands/opsx-apply.md 软链；落地交接照旧失败，由主会话手动走 pr-ship；合入后由人快进主检出、更新插件到 0.7.0；之后根目录软链可删。

Design · 05技术设计

Context

  • 入口现状：orchestrator.tsx 用 on('command.run', { command: 'opsx-apply' }) 接管命令。命令名本身由项目的 .claude/commands/opsx-apply.md 提供：
  • 下游项目由 install.sh 装上这个文件；
  • 本仓库靠根目录 .claude/commands/opsx-apply.md 软链提供，这个软链是 2026-10-12 补的，未跟踪。
  • 出口现状：landing.tsx 落地后调用 ctx.runCommand('pr-ship', f.change)，最终是 $.command.run。
  • 本仓库根目录没有 pr-ship，每次都失败，只记一条提示。
  • 传的参数是 change 名，而 pr-ship.md 把参数当作 target branch，两边口径本就不一致。
  • 来源现状：
  • #50 的 HUMAN_ORIGINS = ['composer', 'bridge'] 只用于 /flight abort 与 resume；
  • /opsx-apply 起飞不查来源；
  • 无头运行（claude -p、Agent SDK）的来源是 sdk，现在会被 abort / resume 拒绝。
  • pr-ship 与 code-reviewer：两者在 template/.claude/ 下，由安装器复制到项目。
  • pr-ship.md 里的判定器路径写死为 .claude/hooks/…，change 目录写死为 openspec/changes/<name>。本仓库实际是 template/.claude/hooks 与 template/openspec/changes/<name>，主会话每次都要手动换算。
  • 第 8 步派发 subagent_type=code-reviewer。
  • 派发守卫：envelope.ts 的 spawnVerdict 规定，flight:* 只能由 flight 控制面派发。主会话派发 flight:code-reviewer 会被拒。
  • 实测（2026-10-12，CLI 2.1.296，无头模式）：
  • $.command.register 与项目或用户命令文件同名时，引擎拒绝，原话是「$.command.register: "/filecmd" refused: it is the user's /filecmd」。此时 command.run hook 仍能拦截该文件命令，来源为 sdk。
  • 插件命令返回 { text, context } 后，模型不会接着作答。
  • 在 command.run hook 里调 $.prompt.submit 被拒，原话是「called from a command.run hook, it would wait on the turn this hook is holding; submit from a later event (turn.complete)」。
  • 插件自带的 commands/<名>.md 注册为 <插件>:<名>，$.command.list() 里的来源为 plugin。不带前缀直接发 /<名>，找不到这个命令。
  • 在子 agent 的 turn.complete 里调 $.command.run({ command: '<插件>:<名>' })，来源为 { kind: 'plugin' }。命令在当前主轮结束后运行，模型照正文作答。$.prompt.submit 同样可行。
  • skill 与命令在调用时，参数会以「ARGUMENTS: …」附在正文后，本会话的 skill 调用即如此。

Goals / Non-Goals

Goals - 不依赖项目里装的命令文件，插件就能提供 /opsx-apply 入口和 /flight:pr-ship 出口。 - 会写账本的入口只认人或宿主程序，模型够得着的间接途径（定时任务、跨会话消息、插件代发）一律拒绝。 - 落地交接在任何项目里都能接上，判定器与 change 目录由插件给出，不再靠模型猜。

Non-Goals - 模板整体改为插件分发：skills、其余命令、hooks 的迁移另立 change。本 change 只迁入口与出口直接需要的 pr-ship 与 code-reviewer。 - ship 机械步骤由插件执行：提交、预合并、push、建 PR 仍由模型按 /flight:pr-ship 文档执行（用户定：先迁入插件，机械化以后再做）。 - 判定器收口：takeoff-gate、session-model 等另立 change。 - #50 遗留的 MEDIUM：abort 两段停、动作内查停飞等另立 change。只在这里补上「来源规则」的文档。

Decisions

注册

在带 { cwd: /^/ } matcher 的 session.start hook 里，与 flight 一起调用 $.command.register({ name: 'opsx-apply', description: '飞行模式 apply：由 flight 插件状态机执行（批准后起飞）', argumentHint: '<change>' })。

被拒即忽略

项目或用户已有同名命令文件时，引擎拒绝注册，异常吞掉、不提示，command.run hook 照旧接管那个文件命令。其他注册失败同样忽略。

项目里没有命令文件、注册又失败时，入口不存在，/opsx-apply 报 Unknown command。这时等于插件缺席，按铁律 10 不起飞。
命令文件保留

模板仍安装 .claude/commands/opsx-apply.md，插件缺席时它告诉模型「即停飞」，--gate=per-task 也要读它。

认可的来源

HOST_ORIGINS = ['composer', 'bridge', 'sdk']，取代 #50 的 HUMAN_ORIGINS。

sdk 是 claude -p 或 Agent SDK 宿主自己发起的一轮，由引擎盖章，模型造不出来。阶段 5 的无头评测要靠它。
适用范围
/opsx-apply 在走起飞路径之前查来源；
--engine=workflow 的拒绝回复与 --gate=per-task 透传不写账本，不查来源；
/flight abort、/flight resume 照旧查来源，只是加上了 sdk；
status 与 panel 不查来源。
拒绝文案

统一为 flight：<命令> 会写账本，只接受人或宿主程序发出（终端、Remote Control、SDK；本次来源：<kind，未标明时写「未标明」>），不读写账本、不停 agent。

插件注册的斜杠命令

项目里没有同名命令文件时，恰为 flight 与 opsx-apply；有同名文件时只有 flight。

模型可调用的工具仍恰为 submit_findings 与 measure。
任何工具或命令在任何输入下都不写 approve。
本要求取代 flight-interaction 中「插件注册的命令恰为 flight」与「只接受人在终端发出」两处约束。flight.test.tsx 的两条守卫测试随之改为期望 ['flight', 'opsx-apply']。
调用

landing.tsx 落地后调用 ctx.runCommand('flight:pr-ship', args)，args = --worktree <f.changeTree> --change-dir <f.changeDir> --judges <f.hooksDir>。

三个值都由插件给出

worktree 是 change worktree 的绝对路径，change 目录相对 worktree，判定器目录是主检出副本的绝对路径。

判定器与飞行门禁用同一份，即 f.hooksDir。
失败
log

落地完成，但接 /flight:pr-ship 失败：<原因>；

toast

flight：<change> 已落地，但接 /flight:pr-ship 失败：<原因>；请手动运行 /flight:pr-ship <args>；

照旧不停飞。
时机

Risks / Trade-offs

命令改名

/pr-ship 改为 /flight:pr-ship，用户要改习惯；已装项目的旧副本仍可用，但不再更新。安装器会列出旧副本。

来源盖章依赖引擎
若真实引擎给终端命令标的不是 composer，人发出的起飞也会被拒。拒绝语写出看到的来源，第一次起飞即可核对。
sdk 在本仓库按文档认定为宿主程序，未做更多实测。
参数靠模型读取

/flight:pr-ship 的三个参数由模型从「ARGUMENTS」读出再代入命令。读错时，判定器或 change 目录找不到，命令会报错停下，不会静默跑错。

本 change 自己的飞行

插件 0.6.0 没有注册 opsx-apply，起飞靠根目录软链；落地交接照旧失败，由主会话手动走。
