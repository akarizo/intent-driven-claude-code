# DRAFT. 门禁判据不得由被门禁的一方提供

- Status: accepted
- Date: 2026-09-10
- 关联：DRAFT-apply-as-flight（本决策补强其"评判用机械门禁"一条）· DRAFT-model-routing-defaults-for-template

## Context

飞行模式落地后，两条铁律在 2026-09-10 同一天各被实测破了一次，破法相同——**判据由被门禁的一方提供**：

1. **铁律 11（模型显式路由）**：`/opsx-apply` 让模型自己回答"当前会话主模型是什么"（命令原文"看 `/model`"）。一次真实起飞里模型答 `fable`，而转录显示主循环模型 08:19 起已是 `claude-opus-5`——模型的依据是上下文里 05:25 那条旧 `/model` 输出与两次 compact 后的摘要。整场飞行的执行体与评审员因此错配，收口"对账"由同一个模型肉眼做，拦不住。
2. **铁律 7（两处人类审批）**：批准的全部实现是"propose 收尾提示一句 + apply step 4 由模型自己 `timeline.py record approve`"。模型在同一轮里从 propose 直冲 apply，飞行记录里照样有一条 `approve`；用户实测"现在几乎没有在 apply 前停下来问我"。

这与铁律 9（能用脚本 / hook 判定的不交给模型）、铁律 1（intent-gate 只能加严不能绕过）是同一条原则的不同侧面，值得升为长期约束。

## Decision

**凡门禁判据，必须来自被门禁方之外的可核验来源。** 具体：

1. **真值源**只认四类：会话转录（`~/.claude/projects/*/<sid>.jsonl`）· 文件系统（mtime / 内容）· git（commit / diff）· hook 留痕（evidence.log / gate-report.md）。模型的叙述只能用于**展示**，不能用于**判定**。
2. **强制点尽量放 hook**（`PreToolUse` / `Stop`），命令与 skill 的文本只是给人看的解释与兜底自检；一条判据若只写在命令文本里，视为未强制。
3. **判定不出时 fail-closed**（停下交人，给出补救方式）；**hook 自身异常时 fail-open**（坏门禁不能锁死能力）——两者不矛盾：前者是"证据不足不放行"，后者是"工具坏了不绑架用户"。
4. **人类审批的证据是人自己发出的消息**（转录里的 `type: "user"` · 非 meta · 非 tool_result），且必须**晚于**被批准物的最后一次改动；模型代记的批准事件无效。

## Consequences

- **更易**：铁律 7 / 9 / 11 从"要求模型自觉"变成"脚本判定 + hook 强制"，违规当场红，不必事后靠人复盘转录才发现。
- **更易**：判据统一到转录 / 文件系统后，测试可用 fixture 直接锁语义（喂一份转录，断言判定结果）。
- **更难**：任何新门禁在设计时必须先回答"判据从哪来、谁能伪造"，写不出可核验来源的门禁不许上。
- **更难**：会话中途换模型、计划改后再起飞这类场景会多一次显式确认；这是刻意的成本。
- **代价**：判定依赖 Claude Code 转录 JSONL 的字段（`message.model` · `type` · `isSidechain` · `timestamp`）。字段变更会让门禁 fail-closed 停飞而非静默放行，需要跟版本；换来的是不可伪造。
