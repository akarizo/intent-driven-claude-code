# DRAFT. 起飞批准可由人在批准带「搁置」撤销

- Status: accepted, supersedes DRAFT-approval-bound-to-plan-fingerprint
- Date: 2026-10-14
- Supersedes: DRAFT-approval-bound-to-plan-fingerprint（该 ADR 在 main 上尚未编号，按文件名引用）
- 关联：DRAFT-flight-control-plane-in-mod、DRAFT-flight-armed-takeoff

## Context

`DRAFT-approval-bound-to-plan-fingerprint`（2026-10-09）规定：起飞批准的证据是人在批准带按下按钮，插件写入的 `approve` 事件；起飞门禁只比对「账本最新批准指纹 == 当前计划指纹」。

2026-10-14 实际使用中暴露缺口：批准是只增不减的。
- 一份计划批准之后若不打算飞了（被别的 PR 覆盖、基于的 main 已过时），批准带会对它永远显示「起飞」，没有撤下入口。
- `flight-review-followups` 于 2026-10-11 批准，三天未起飞；其间 main 前进了 12 个 PR，人只能手动删 change 目录来让它消失。
- 删目录之外，任何人手打 `/opsx-apply` 仍会以这份旧批准起飞。

需要一个由人触发、写进同一本账、能让旧批准失效的动作。本 ADR 修订原第 4 条的判据；原 ADR 其余各条不变，在此重述，使本 ADR 自足。

## Decision

1. **凡门禁判据，必须来自被门禁方之外的可核验来源**（原第 1 条保留）。真值源：git（提交、引用、diff）· 文件系统内容 · 控制面插件观测到的引擎事件 · hook 留痕。模型的叙述只能用于展示，不能用于判定。
2. **强制点放在机械层**（hook / 插件），命令与 skill 的文字只是解释与兜底自检（原第 2 条保留）。
3. **证据不足 fail-closed，门禁自身故障 fail-open**（原第 3 条保留）；「没有批准记录」与「已搁置」都属于证据不足，必须拒绝。
4. **（修订）批准与撤销都是人在批准带上的按键，由插件写进 `refs/flight/<change>/ledger`**：
   - 「批准起飞」等按键写 `approve` 事件，带当时的计划内容指纹；
   - 「搁置」写 `shelve` 事件，带当时的计划内容指纹；
   - 起飞门禁取账本里最后一条 `approve` 或 `shelve`（最新决定）：它是 `approve` 且指纹 == 当前计划指纹，批准才成立；它是 `shelve` 则拒绝；
   - 搁置作废此前全部批准；之后只有新的 `approve` 能恢复。批准带对「最新决定是同指纹的 shelve」的计划不再显示，计划改动（指纹变化）后重新显示「批准起飞」。
   - 计划指纹只覆盖定义计划的内容（proposal、design、specs、slices.json、切片包），执行记账不计入（原条款保留）。
5. **写账本的入口只存在于插件进程内、只由按钮按压触发**；判定器只读；不提供任何模型可调用的写入或撤销命令、工具（原第 5 条保留，扩展到 `shelve`）。
6. **写入方不得写读取方不认识的事件**：插件写 `shelve` 前，先核对读取账本的判定器（`ledger.py events`）认识它，不认识就拒绝写入。

## Consequences

- **更易**：不打算飞的计划能在批准带一步撤下，并且撤下后无法误起飞；撤销与批准同在一本账里，飞行记录与审计都看得到。
- **更难**：账本多一种事件类型，读写两侧的事件表须同步；插件起飞要求判定器认识全部事件类型，升级插件须同步升级主检出的判定器。没有「取消搁置」按钮，恢复要靠改动计划。
- **威胁模型不变**：防走捷径的模型（自记批准、自撤批准、直接改证据）；搁置只会收回放行，模型即使能触发也不会造成未经批准的起飞，但它与批准一样只由按键触发。不防蓄意伪造 git 对象的对抗者。
- **被取代者**：`DRAFT-approval-bound-to-plan-fingerprint` 的文件保持原样作为历史记录；其第 1–3、5 条由本 ADR 继承，第 4 条由本 ADR 第 4、6 条取代。
