0 · 结论

撤回上一轮的「门禁本体别迁」。那条理由是迁移成本和双实现漂移，属于成本论证，不是正确性论证。

真正的问题：现在的编排器（Workflow 脚本）按设计不能有副作用（opsx-apply.js:19：「脚本本身不碰文件系统，全部由 agent 执行」）。于是 git 合回、跑门禁、记账这些机械动作只能派模型去做，机械事实也只能经模型之口传回来；飞行状态则散在标记文件、gate-report.md、evidence.log 里，被多个脚本各自推导。过去一个月的飞行缺陷，多数是这一个结构错位的不同症状（第 1 节逐条对照）。

Mod 是 Claude Code 里第一个同时具备四项条件的宿主：① 跑在进程内，能直接拿到引擎事实（会话模型、子 agent 实际模型、prompt 来源）；② 有副作用权（$.process.run、$.fs、$.agent.spawn）；③ 看得到所有 loop（子 agent、Workflow agent 的 tool.call 都带 agentId）；④ 能和人直接交互（按钮、状态行、面板、系统通知）。

正确设计：把控制权（编排、状态、证据、路由、审批）整体迁进 mod，构成可信执行面（TCB）；判定器一行不搬，仍是纯 Python CLI；模型只做创造性工作，返回值只作信息、不作判据。

2 · 第一性原理

P1
信任边界：模型是不可信的执行者。可信执行面（TCB）= 引擎 + 控制面代码 + 判定器 + git + 人。任何判据都在 TCB 内算出、在 TCB 内落盘，不经模型之口。
P2
单一写者：飞行状态只有一个写者（状态机），其余都是读者；读者不推导状态。
P3
判定与强制分离：判定器是纯函数（事实 → 裁决），不依赖宿主，CI 可跑，pytest 覆盖；强制点只是薄适配层。宿主 API 变动只波及适配层。
P4
token 只花在创造上：合回、跑门禁、记账、开 PR、渲染正文都是代码；模型只负责写代码、评审、修复、解冲突。
P5
批准绑定内容：人批准的是计划的内容指纹，而不是「某个时刻之后」。计划一变，批准自动失效。
P6
能力随状态收放：每个飞行状态 × 每个角色对应一个工具包络（可写路径、可用工具、可派发对象），越界即拒。
P7
回退 = 失效即停：控制面不在时不能起飞，而不是走一条语义可能漂移的第二实现；与飞行无关的护栏照常工作。
P8
度量来自引擎事件：时间、用量、实际模型都从事件流记账，不从转录事后重建。
P9
方法论本身要被评测：用带「无插件」对照臂的评测证明流程有效，这是铁律 8 的根。

可信不可信（模型）实线 = 控制 / 写入　虚线 = 被观测的事件或受限写入

5 · 飞行状态机

每次转移由控制面执行，守卫是判定面的纯函数，每次转移都写一条账本。

PLANNED工件齐 · 指纹 fp
→
APPROVED人按批准 · fp 一致
→
PREFLIGHTbaseline + preflight 绿
→
WAVE i切片循环（见下）
→
INTEGRATE代码合回；冲突才派模型
↺ i+1
REVIEW并行，离关键路径
→
FIXCRITICAL/HIGH 汇总一次修
→
FINALslice-gate final
→
SHIPship 裁决 · push · 开 PR · 贴评审
→
PR_OPEN等第二处人类审批
HALTED（任何状态都可进入）计划指纹变化 · 人按中止 · 版本低于下限 · 派发的实际模型与路由表不符 · 越权写入

切片内循环（WAVE i 中每个切片）

DISPATCH控制面建 worktree，$.agent.spawn
→
RUNNINGtool.call 按包络放行或拒
→
MEASUREturn.complete 或超时 → 控制面跑 gate
→
GREEN

MEASURE 为红且未到上限 → 带 checkpoint 重新 DISPATCH；达到上限 → BLOCKED。「未返回」和「返回了但红」走同一条路：控制面不看 agent 说了什么，只看测出来的结果，所以不需要识别 maxTurns。

工具包络（状态 × 角色）

状态主会话模型slice-executor（Sx）code-reviewerfixer
PLANNED / APPROVED只写 openspec 工件———
WAVE源码只读（D5）只写 Sx.owns；不得派发子 agent；不得写工件 / 账本——
REVIEW只读—只读—
FIX只读——写 owns 并集
FINAL / SHIP只读———

Bash 写文件（sed -i、cat >）只能尽力预拦；精确保证来自 MEASURE 时 git diff --name-only base.. 对 owns 的核对，越界即红（与现有 G 系门禁同源）。

7 · 关键设计

7.1 账本：git 引用上的提交链

位置：refs/flight/<change>/ledger，每个事件一个 commit（树里一份 JSON）。命名空间与 slice-noreturn-resume 已在用的 refs/flight/<change>/<S> 快照一致。

为什么放这里：不在工作区，所以不与 merge 冲突、不会被 .gitignore 吞、Write/Edit 碰不到（直接对应 R5）；commit 链本身就是哈希链，改动可被检测；push 时连同 refs/flight/* 推送，审阅者可以 fetch 下来复核。

完整性：控制面每次追加后把 tip 记入 $.store；SHIP 前比对，不一致即红。PR 正文是账本的投影，任何时候都能重放生成，被手改也能检出。

写入（S4 实测）：plumbing 单次追加 p50 67ms；并发追加时 update-ref 的旧值校验会拒绝后来者（8 并发只成 1，链长不分叉不丢失）。所以控制面用单写者队列，CAS 失败就重读 tip 再追加。

写入口不外露：账本追加（尤其 approve）只在 mod 进程内做，不做成模型能调的 CLI 或工具——历史教训正是模型自己跑 timeline.py record approve。另在 tool.call 上拒绝提到 refs/flight/ 的 Bash 命令（尽力而为）。$.store 是明文文件，tip 比对只防走捷径，不防蓄意伪造。

威胁模型（明说）：防的是走捷径的模型（直接改证据文件、自己记批准、绕开门禁），不防蓄意伪造 git 对象的对抗者。

7.2 批准：按钮 + 计划指纹

指纹：fp = sha256（规范化后的 proposal + specs + design + tasks + slices.json + 路由表）。spec.html 顶部和批准带显示同一个 fp 前 8 位，人眼可对。

判据：账本里有一条由 ui.press 写入的 approve{fp}，且 fp 等于当前计划指纹。任一工件改动都会让 fp 变化，飞行转入 HALTED，需要重新批准。claude -p 没有界面所以批准不了，这是正确行为；可以在交互会话里批准，再无头起飞。

7.3 路由：随计划批准，派发时实时对账

路由表是计划的一部分，随 fp 一起批准。渲染计划时 <main> 已由 $.session.model() 解析成具体模型 id，所以人批准的是具体模型，而不是一个别名。

控制面派发一律显式带 model。agent.spawn 守卫负责：飞行中模型自发的派发（Agent 工具）按路由表改写，或直接拒绝；派发结果里的实际 model 与路由表不符时，$.turn.abort 中止该 agent、写违规记录、门禁转红。--expect-models 由此退化为一次账本查询。

7.4 测量协议：模型请求，TCB 测量

执行体不汇报结论。TDD 的 RED 节点由执行体调用 mod 注册的工具 mcp__flight__measure 发起「请测一下」，控制面自己跑该切片的 scenario 测试并把结果写入账本；GREEN 在 turn.complete 后由控制面跑 gate 判定。铁律 3「测试运行由 hook 留痕」由此升级为「测试由可信方执行」。

7.6 兼容与稳定

9 · 风险与对策

风险影响对策
mod API 处于 early access，跨版本会变控制面失效判定器不依赖 API；版本下限检查不过即停飞；每个新版本 CI 跑 validate / test；类型文件随版本重新生成
并行、重试、续跑原本是 Workflow 白送的，现在要自建实现量事件驱动状态机 + 账本重放；先用 spike 验证 S1 / S4 / S8
Bash 写文件绕过包络越权写入预拦只是尽力；MEASURE 用 git diff 精确核对 owns，越界即红
只能在 Claude Code 里用平台锁定仓库本来就叫 intent-driven-claude-code；判定器在 CI 里仍可独立跑
项目级 plugin 的安装与信任队友没装就飞不了classic 地板 hook 明确提示安装命令；S6 实测
改控制面的 change 由控制面自己执行自举失真飞行跑已安装的稳定版；新版本仅由测试验证，合并后再升级
重构期间新旧并存两套语义分阶段推进，每阶段一个 change；新路径评测通过后一次性删除旧路径，不长期并存
