/opsx-apply 一小时架构：把 apply 变成一次「飞行」

第 2 版实测证明：慢在逐 task 的 review→fix 循环（子 agent 时间 64–80%）、冷启动轮次、主会话上下文膨胀，与等人无关。本版不再修补现有流程，而是从「1 小时」这个预算反推每个环节的硬上限，重建 apply：规格可执行 · 切片有所有权 · 调度用确定性脚本 · 执行体带预算 · 评审离开关键路径。模板的能力原则一条不丢，多条反而变硬。

Git 纪律：每 change 一间 worktree，不自动 merge / push main保留；wave 内并行切片各用临时 worktree，由 integrator 合回 change 分支（本地、可 reset）；PR 仍是 feature 分支等价
ADR 不可改、spec.html 审批、PR 闭环、verify / archive、CLAUDE.md 记忆层不动；verify 的三维检查机械化并入门禁与收口检查；spec.html 改脚本渲染并增加飞行计划等价
人类审批两处：批准飞行计划（= 运行 /opsx-apply）与 PR review；merge 永远是人等价

1一小时的物理学：从预算反推上限

不可约分量（实测下限）
  • 每轮模型延迟：上下文 <100k 时约 5–7s，100–200k 时 7–11s，>400k 时 23–41s。→ 上下文是延迟的一阶变量。
  • 一个小切片的实现：low-code-opt 会话里无回灌时均 6.3 min / 42 轮；大切片 12–28 min / 60–84 轮。→ 轮次是第二变量。
  • 测试：多数仓库单次秒级；个别仓库全量 >5 min。→ 全量只跑一次，切片只跑子集。
  • 一次独立评审：不重跑测试时 5–8 min（实测 review 里模型时间 4–8 min，其余是自己跑测试和轮询）。
今日的乘数（实测）
  • r = 1.3–3.1：每 task 的 review→fix 轮数（fix 子 agent 数 ≥ impl 数）。
  • 冷启动 + 一命令一轮：实现类 42–84 轮，工具执行不到 1 min。
  • 回报 4.5k 字符 × 30–100 次灌回主会话 → 619–847k 上下文。
  • 完全串行：子 agent 区间并集 = 累加。

2六个结构性改变

① 规格可执行：scenario → 测试骨架，批准即批准验收测试

tasks 阶段（design 之后）为每个 Gherkin scenario 生成一个测试骨架：GWT 三段注释来自 scenario 原文，断言按 THEN 写出，整体标记为待通过（xfail(strict) / test.todo）。spec.html 把「scenario ↔ 测试文件:函数」映射表摆给人看；批准飞行计划 = 批准验收测试。

apply 的完成判据从此是机械的：全部 scenario 测试由 xfail 变 pass、无遗留 todo。

删掉了什么
  • reviewer 的「spec compliance」核对（1:1 映射由构造保证）
  • verify 的 scenario 覆盖抽查
  • 贴 RED 证据（骨架在实现前必失败）
  • 执行体读全部 spec 的成本（只读自己的 scenario）

② 切片有所有权：tasks.md 升级为 slices.json

{
  "change": "add-user-export",
  "gate": { "test": "pytest -q", "lint": "ruff check .", "full_suite_sec": 95 },
  "slices": [
    { "id": "S1", "title": "导出任务数据模型",
      "scenarios": ["data-export#1", "data-export#2"],
      "owns": ["app/models/export_job.py", "migrations/0042_*.py", "tests/test_export_model.py"],
      "deps": [], "verify": "pytest -q tests/test_export_model.py" },
    { "id": "S3", "title": "POST /v1/exports",
      "scenarios": ["data-export#4"],
      "owns": ["app/api/exports.py", "tests/test_api_exports.py"],
      "deps": ["S1", "S2"], "verify": "pytest -q tests/test_api_exports.py" }
  ]
}
它带来的机械保证
  • 并行安全：同 wave 内切片 owns 不相交（规划 lint 校验），临时 worktree 合回零冲突。
  • 范围控制：intent-gate 新增所有权检查，执行体写 owns 之外的文件直接 DENY，零 token 防「顺手改进」。
  • 切片大小：3–7 片、DAG 深度 ≤ 3、每片 ≤ 6 个文件；超了规划器必须再切。
  • 向后兼容：tasks.md 由 slices.json 生成（保留 - [ ] 供门禁与 openspec CLI）。

③ 切片包（slice packet）：冷启动没关系，冷得小才行

实测的 42–84 轮里，大量轮次是执行体自己重读 spec / design / 代码、再拼命令。改为规划器一次生成 slices/S3.md：本切片 scenario 原文、测试骨架路径、owns 清单、design 里标注给 S3 的段落、verify 命令、依赖切片的公开接口摘要（integrator 在每个 wave 合回后用 cx symbols 抽出写进 slices/_interfaces.md）。

执行体 prompt 只有一句：「按 slices/S3.md 实现 S3，收尾跑门禁并返回 JSON」。起步上下文 ≤ 25k，主会话不再手写 5k 字符 prompt。

执行体纪律（写进 agent 定义，不靠主会话转述）
  • 一轮多动作：并行发出全部 Read；测试与实现能一起写就一起写；verify 与 lint 一条 Bash。
  • 不加 cd && 前缀（cwd 已是 worktree）；不为一行脚本先 cat > 再执行。
  • maxTurns: 40、model: inherit、permissionMode: acceptEdits；到顶即返回「partial」而非硬撑。
  • 只回 JSON：{slice, ok, commit, failed[], summary≤300字}。不写报告。

④ 调度用确定性脚本：.claude/workflows/opsx-apply.js

编排从「主会话逐个派发、逐个读回报」改为 Claude Code 原生 Workflow：脚本持有 DAG 与循环，agent 输出留在脚本变量里，主会话只收最终 JSON；运行在后台、/workflows 可视、可续跑。模板把它作为命名工作流随 install.sh 下发，/opsx-apply 命令读 slices.json 算出 wave 后以 args 调用。

export const meta = {
  name: 'opsx-apply',
  description: '按 slices.json 逐 wave 并行实现，切片门禁，评审离关键路径，一次批量修复',
  phases: [{ title: 'Implement' }, { title: 'Review' }, { title: 'Fix' }, { title: 'Finalize' }],
}
const { change, waves } = args                        // /opsx-apply 读 slices.json 推导 waves 后传入
const GATE = { type: 'object', required: ['slice', 'ok', 'commit', 'failed'],
  properties: { slice: { type: 'string' }, ok: { type: 'boolean' }, commit: { type: 'string' },
                failed: { type: 'array', items: { type: 'string' } }, summary: { type: 'string' } } }
const FINDINGS = { type: 'object', required: ['findings'], properties: { findings: { type: 'array', items: {
  type: 'object', required: ['severity', 'file', 'line', 'summary', 'fix'],
  properties: { severity: { enum: ['CRITICAL', 'HIGH', 'MEDIUM', 'LOW'] }, file: { type: 'string' },
                line: { type: 'integer' }, summary: { type: 'string' }, fix: { type: 'string' } } } } } }

const reviews = [], results = []                      // 评审只发起不 await：离开关键路径
for (const [i, wave] of waves.entries()) {
  phase('Implement')
  const iso = wave.length > 1 ? 'worktree' : undefined // 单切片 wave 直接在 change worktree 里做
  const done = await parallel(wave.map(s => () =>
    agent(`按 openspec/changes/${change}/slices/${s}.md 实现切片 ${s}；收尾运行 python3 .claude/hooks/slice-gate.py ${s} 并原样返回其 JSON。`,
          { label: s, agentType: 'slice-executor', isolation: iso, schema: GATE })
      .then(r => (r && !r.ok)                          // 门禁红：同切片只重试一次，仍红即 blocked
        ? agent(`切片 ${s} 门禁未过：${JSON.stringify(r.failed)}。只修门禁项，重跑门禁并返回 JSON。`,
                { label: `${s}:retry`, agentType: 'slice-executor', isolation: iso, schema: GATE })
        : r)))
  results.push(...done.filter(Boolean))
  if (wave.length > 1)
    await agent(`把切片 ${wave.join(', ')} 的 commit 合回 change 分支（文件所有权不相交，应无冲突），用 cx symbols 刷新 slices/_interfaces.md。`,
                { label: `integrate:w${i + 1}`, agentType: 'integrator', effort: 'low' })
  for (const s of wave)
    reviews.push(agent(`评审切片 ${s} 的 commit（git show），输入：slices/${s}.md + gate-report；不重跑测试。`,
                       { label: `review:${s}`, agentType: 'code-reviewer', phase: 'Review', schema: FINDINGS }))
}
phase('Fix')
const blocking = (await Promise.all(reviews)).filter(Boolean).flatMap(r => r.findings)
  .filter(f => f.severity === 'CRITICAL' || f.severity === 'HIGH')
if (blocking.length)
  await agent(`一次性修复以下 ${blocking.length} 条 CRITICAL/HIGH，逐条 commit，末尾跑全量门禁：${JSON.stringify(blocking)}`,
              { label: 'fix', agentType: 'slice-executor', schema: GATE })
phase('Finalize')
const final = await agent(`跑全量门禁（全部测试 + lint + scenario↔test 映射全部 pass）并返回 JSON。`,
                          { label: 'final-gate', agentType: 'integrator', effort: 'low', schema: GATE })
return { slices: results, blocking, final }
为什么它对应「1 小时」
  • wave 内 parallel，wave 间按 DAG；评审 push 不 await，到 Fix 才汇合。
  • 失败是数据不是对话：门禁 JSON 决定重试 / blocked，评审 JSON 决定修什么；无人可问，也无需问。
  • 主会话只收返回的 JSON（几百字），上下文回到几十 k。
  • 脚本可读、可 diff、可续跑；每次 apply 的编排完全一致，度量才可比。
回退路径（Workflow 不可用时）

Pro 计划需在 /config 打开 Dynamic workflows；组织可禁用。/opsx-apply 检测到不可用时走同一套 slices.json / 切片包 / 门禁，只是 wave 由主会话用 Agent 工具并行派发、回报同样只收 JSON。语义一致，只是主会话多几轮。

⑤ 评审离开关键路径 + 一次批量修复

reviewer 仍是干净、只读、不带主会话立场的 code-reviewer，但：每切片一个，随 wave 完成即发起，与下一 wave 并行；输入是切片包 + 门禁报告 + evidence.log，禁止重跑测试与轮询；输出结构化 findings。所有 CRITICAL/HIGH 汇总后一个执行体一次修完（逐条 commit），再跑全量门禁。MEDIUM/LOW 贴 PR 评论。

与今日对比（实测）
  • 今日：每 task review 6–33 min × (1.3–3.1 轮) 全在路径上。
  • 新：路径上只有最后一个 wave 的评审 ≤ 6 min + 一轮修复 ≤ 8 min。
  • 「全量一次」的独立性由收口整合检查补：scenario↔test 全 pass + 跨切片一致性由 final-gate 的 reviewer 抽查（可选，见 D3）。

⑥ 度量内建：每次 apply 自带飞行记录

Workflow 的 journal.jsonl + 子 agent 转录 + hook 写的 timeline.md，收口时由 session-decompose.py（本页 §1 用的三份脚本合一）打印：批准→PR 用时 · 每切片轮次与 wall · 评审是否在路径上 · 门禁红次数 · 主会话峰值上下文。spec.html 的飞行计划区读它渲染。目标不是写在文档里，是每次跑完打印出来和 47 分钟比。

4地基核实（官方文档 · 2026-09-10 · 本机 Claude Code 2.1.267）

Workflow（code.claude.com/docs/en/workflows） 付费计划通用（Pro 需 /config 打开）；脚本为纯 JS：agent()（label / phase / schema / model / effort / isolation:'worktree' / agentType）、parallel()、pipeline()、phase()、log()、args、workflow()；无中途人工输入（只有权限提示能暂停）；脚本本身无 shell / 文件访问，全部由 agent 执行；并发 ≤ 16；可保存到项目 .claude/workflows/ 作为 /<name> 命令随仓库分发，也可打进插件；args 以结构化 JSON 传入；bypass 模式不弹确认，其它模式可「不再询问」；agent 与主会话共享权限规则，需提前 allow 测试/lint 命令；同 run 内同类 agent 共享 prompt cache；可续跑。
Subagent / Hooks / Worktree（sub-agents.md · hooks.md · worktrees.md） agent 定义支持 model / permissionMode / maxTurns / tools / skills / hooks / isolation / effort；模型顺序自 v2.1.251：参数 > frontmatter > env > 主会话（本会话实测一致），强制需 _FORCE=1；Stop 支持 decision: "block"；PostToolUse 有 tool_response，hook 定义支持 if: "Bash(pytest *)" 与 async；子 agent worktree 默认从默认分支分叉，worktree.baseRef: "head" 才从当前 HEAD 分叉（wave 并行的前提）。
待实证（自举时第一批验证项） ① Workflow 里 isolation: 'worktree' 是否遵守 worktree.baseRef: "head"（文档写在 subagent 章节，未单列 workflow）；② integrator 用 commit SHA 合回是否零冲突（所有权不相交时应当如此）；③ maxTurns 到顶返回 partial 时 schema 输出如何表现；④ 权限提示在 bypass 之外的模式下会不会让 wave 卡住（需 allow 规则）。这四项都在自举的第一个 wave 里就能验掉。

5风险与取舍

风险
  • 规划器写不好切片（所有权漏文件、DAG 太深）→ 执行体被所有权 DENY 或 wave 数超 3。缓解：规划 lint 当场报；DENY 时执行体返回 failed: ["ownership: path"]，主会话把该文件加进 owns 重跑该切片，不是绕过。
  • 验收测试写早了（design 之后接口仍变）。缓解：骨架只锁 THEN 的可观测结果，不锁内部签名；执行体可改骨架但必须在 JSON 里申报，reviewer 核对申报。
  • 一次批量修复漏修。缓解：final-gate 必须全绿；未绿则 PR 以 draft 打开并列出 blocked 项，人决定。
  • Workflow 与权限提示：非 bypass 模式下一条未 allow 的测试命令就会让 wave 停在提示上。缓解：install 时把 gate 命令写进项目 allow 规则；apply 启动前自检。
  • token 上升：执行体与 reviewer 用主模型、并行度提高。对照：冷启动从 30–100 次降到 ≈ 8 次，回报不灌主上下文；用 timeline 与账单对账一轮再定。
明确不做
  • 不自动 merge、不推 main、不删 change worktree。wave 临时 worktree 由运行时清理。
  • 不放松 intent-gate；只加所有权与修定根。
  • 不改 ADR 不可改、不改 openspec 归档契约。
  • 不用 ultracode 会话级开关（每个任务都起 workflow 太重）；只让 /opsx-apply 命令调用命名工作流。
