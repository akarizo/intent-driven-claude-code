Why · 01为何而做

#57（0.10.2）与 #56 的评审各留下一项会造成重复起飞的 MEDIUM： - 批准带按键先查后登记：连按时第二次也能通过「进行中」检查； - 排队中的 drive 不算「正在飞」：这时发 /flight resume 会在 attempt 未结束时再写一次 takeoff。

另有一处会让待命卡住：唤醒（或交模型）那一轮结束时，若恰好撞上同一 change 的起飞锁，推进会被直接丢掉，待命停在「已唤醒」直到 30 分钟过期。此外还有一批便宜的 LOW、缺测与残留。

0.10.2 的修复在测试世界里模拟不出 origin，这次起飞同时用作真引擎冒烟。

决策页：docs/flight-dispatch-followups.html（主检出，未跟踪），Q1–Q6 全按推荐。

What · 02变更范围

  • 按键在入口同步登记：解析出 change 后、任何 await 之前，就登记该 change 正在处理；已登记的再按一律拒绝；处理结束（含异常）时删除。
  • 排队中的 drive 计入「正在飞」：drive 入队即计数，跑完减一；「正在飞」= drive 在跑、或在排队、或本 attempt 有活 agent。
  • 错过的那一轮不丢：
  • 唤醒或交模型那一轮结束时撞上起飞锁，先记下这个 change；
  • 锁释放时，若待命仍在等那一轮，就标为「错过一轮」；
  • 下一次 tick 立即补发唤醒；重试仍在唤醒那一轮结束时、在活的 hook 里做。
  • 便宜的 LOW：
  • 看门狗唤醒失败也记一行日志；
  • 唤醒正文的尾句只保留一份；
  • Arm 类型补上 submittedAt，去掉强转；
  • abort 撞锁时区分人工起飞与自动重试；
  • 批准修订并续飞时如果已批准（指纹相同），toast 写「直接续飞」并真的续飞；
  • 续飞结束恢复状态行时，不冲掉另一个 change 正在显示的基线进度。
  • 测试与残留：
  • 补测：交模型提交成功时待命已换新、唤醒提交失败时待命已换新、「drive 在跑而 agent 都已结束」时的「正在飞」；
  • 清理：无用的 import pytest、过时的「骨架」标题、孤立注释；refresh-failure-clears-busy 不再吞掉按键异常。
  • 插件版本 0.10.3。
插件：template/plugins/flight/hooks/：orchestrator.tsx、armed.ts、register.tsx；types/index.d.ts；对应的 TS 测试与 pytest 包装。不改判定器与账本事件类型，不建 ADR。D 组罕见问题记入 backlog，本 change 不改：land.ts Y 位改名；tick 同毫秒；非首项的进行中显示。冒烟：基线还在跑时按「批准起飞」，一次飞行验证两项：首轮执行体的 measure 正常；唤醒轮能走通。

Specs · 04行为规范 (Gherkin)

flight-band-press-guard ADDED

Requirement: 按键在入口同步登记，连按被拒

批准带按键处理 SHALL 在解析出 change 之后、任何 await 之前，就登记「该 change 正在处理」。已登记时再按，SHALL 立即回 toast「flight：<change> 正在起飞，稍候」并返回，SHALL NOT 再核对指纹、写 approve 或起飞。处理结束（含异常）时 SHALL 删除登记。

Feature: PR #57 MEDIUM：现在先查后登记，查与登记之间隔着读批准带、算指纹、写 approve 几次 await。并发的第二次按键能通过检查，走到去重分支后又起飞一次。

Scenario: rapid-second-press-refused

  • GIVENdemo 未批准，批准带显示「批准起飞」；计划指纹的计算（plan_fp.py）要等放行后才作答
  • WHEN按「批准起飞」，等到 plan_fp.py 已被调用、尚未作答时，再按一次同一按钮；随后放行。期间都不推进时钟
  • THEN第二次按键在放行之前就已返回，并得到含「正在起飞」的 toast
  • ANDplan_fp.py 只因按键运行一次，账本只追加一条 approve，起飞守卫只以 demo 运行一次

Requirement: 批准修订已批准时直接续飞

按「批准修订并续飞」时，若账本里同指纹的 approve 已经存在（例如另一次按键刚写入），插件 SHALL 回 toast「flight：<change> 已批准（指纹相同），直接续飞」，并按已批准的修订续飞（含基线），SHALL NOT 只提示而不做。

Feature: PR #56 LOW：这时 toast 说「直接起飞」，实际什么也不做。

Scenario: replan-duplicate-resumes

  • GIVENalpha 已停飞、计划已改，批准带显示 alpha 的「批准修订并续飞」（当前指纹 G）；按下前，账本在停飞之后已有一条指纹为 G 的 approve；基线立即以 0 退出
  • WHEN按下「批准修订并续飞」并等它返回
  • THEN有一条 toast 含「已批准（指纹相同），直接续飞」
  • AND基线已对 alpha 运行一次，起飞守卫已以 alpha 运行一次

Requirement: 恢复状态行不冲掉别的 change 的基线进度

某 change 的续飞结束、恢复状态行之后，若批准带上还有别的 change 正处于基线相位，插件 SHALL 立即把状态行写回那个 change 的基线进度行（「续飞准备中 <change> · 基线已跑 N 分钟」），SHALL NOT 等到它下一次 60 秒刷新。

Feature: PR #57 LOW：restoreStatusNow() 只看待命与在飞的 change，不认批准带自己的基线相位。

Scenario: other-baseline-line-kept

  • GIVENalpha 与 beta 都已停飞；按下 beta 的「批准修订并续飞」后，beta 的基线迟迟不结束（处于基线相位）；alpha 计划未改，批准带显示 alpha 的「续飞」
  • WHEN按下 alpha 的「续飞」并等它返回
  • THEN最后一次状态行含「续飞准备中 beta」

flight-dispatch-hardening ADDED

Requirement: 排队中的 drive 计入「正在飞」

本进程里某 change 的 drive 正在跑或已排进队列尚未结束时，/opsx-apply 与 /flight resume SHALL 回复「正在飞」，SHALL NOT 写新的 takeoff。这一条不看该 change 当前有没有活 agent。

Feature: PR #56 MEDIUM。drive 走全局单一队列，另一个 change 跑全量门禁时，这个 change 的 drive 可能排几分钟；这期间它既不在 driving 里，也没有活 agent，被误判为卡住。

Scenario: queued-drive-counts-as-flying

  • GIVEN本会话先后起飞了 e2 与 demo；e2 的 drive 正在跑、卡在门禁上；demo 的最后一个执行体刚结束，它的 drive 排在 e2 之后；demo 已没有活 agent
  • WHEN发 /flight resume demo
  • THEN回复含「正在飞」
  • ANDdemo 的账本没有新的 takeoff

Requirement: abort 撞上人工起飞时如实回复

/flight abort <change> 撞上起飞锁时：持锁的是自动重试，就回复「正在自动起飞，结束后再 /flight abort」；持锁的是人工起飞（命令或按键），SHALL 回复「flight：<change> 正在起飞，结束后再 /flight abort」，SHALL NOT 说「自动」。

Feature: PR #56 LOW：措辞与事实不符。

Scenario: abort-while-manual-takeoff

  • GIVENdemo 因「基线仍在跑」处于起飞待命；人又发了 /opsx-apply demo，这次起飞卡在起飞检查中
  • WHEN发 /flight abort demo
  • THEN回复含「正在起飞，结束后再 /flight abort」
  • AND回复不含「正在自动起飞」

Requirement: 看门狗唤醒失败留日志

看门狗停飞后提交唤醒失败时，插件 SHALL 在通知人之外再记一行日志，含 change 名与「唤醒失败」。

Feature: PR #57 LOW：design 写的是「只记一行、通知人」，实现只通知，事后从日志查不到。

Scenario: triage-wake-failure-logged

  • GIVEN账本预置 3 条 heal（自愈预算已用尽）；demo 起飞，agent-1 的请求不结束；prompt.submit 会抛错
  • WHEN时钟推进 661 秒（看门狗停飞），随后推进到唤醒提交
  • THENui.log 有一行含 demo 与「唤醒失败」
  • ANDui.notify 收到含「未能派诊断员」的通知

Requirement: 错过的那一轮在下一次 tick 补发唤醒

唤醒或交模型那一轮结束时，若同一 change 的起飞锁被占用，插件 SHALL 记下这次错过。锁释放后，待命若仍在等那一轮，SHALL 标为「错过一轮」，并清掉已唤醒、已提交两项。之后的第一次 tick 或计时到点，SHALL 对它补发唤醒（任何类别，包括交模型）；已补发、尚未重试时给出等待；重试之前 SHALL 清掉「错过一轮」。

Feature: PR #57 LOW：撞锁时推进被直接丢掉，待命停在「已唤醒」直到 30 分钟过期。

Scenario: missed-turn-rewakes-on-tick

  • GIVEN一个已唤醒的 wait-baseline 待命，和一个已提交交模型的 model 待命
  • WHEN对两者分别调用 afterMissedTurn；然后各遇一次 tick；对已补发唤醒的再遇一次 tick；最后对其中之一调用 beforeRetry
  • THENafterMissedTurn 之后两者的已唤醒、已提交都为假，「错过一轮」为真
  • AND各遇 tick 时都给出 wake，正文含 change 名与「只回复「收到」」
  • AND补发后（已唤醒）再遇 tick 给出 wait；beforeRetry 之后「错过一轮」为假

Design · 05技术设计

Context

  • 约束：派发只在处理外部事件、尚未返回的 hook 里发生（DRAFT-flight-dispatch-live-frame）。定时器回调与已返回的回调里派发会被凭证拒绝（0.10.2）。
  • 按键是并发处理的（#57 交互实测）。register.tsx 的 ui.press 在 await read($, band) 之后才查 inFlight，登记又要再等 fingerprint、写 approve、clock.now 之后。
  • drive 走模块内单一 Promise 队列串行。driving 只在排到队首时登记（orchestrator.tsx 约第 560 行），「正在飞」判据（约第 675 行）看 driving 与活 agent。
  • advanceArm 遇 armBusy 直接返回（约第 983 行）。主会话 turn.complete 推进 awaitingWake / awaitingModel 的待命时，如果撞锁，这一轮就丢了；之后的 tick 对已唤醒的待命只给 wait。
  • armBusy 同时被人工起飞（takeoffArmed）与自动推进（advanceArm）持有，abort 撞锁却一律回复「正在自动起飞」（约第 1228 行）。
  • deferTriage 的唤醒正文第二行与 armed.ts 的 wakePrompt 重复（约第 1191 行），失败时只通知不记日志。
  • Arm 没有 submittedAt，orchestrator 用 as Arm 与 Arm & { submittedAt?: number } 绕过类型检查。

Goals / Non-Goals

Goals: - 连按批准带、drive 排队时，都不会重复起飞。 - 撞锁错过的那一轮不再让待命卡到过期。 - 收掉便宜的 LOW 与测试残留。 - 借本次飞行完成 0.10.2 的真引擎冒烟。

Non-Goals: - D 组：land.ts 的 Y 位改名、tick 同毫秒、非首项的进行中显示。记入 backlog。 - 不改判定器与账本事件，不建 ADR。

Decisions

新增模块级 pressing: Set<string>。登记与检查都在第一个 await 之前完成，并发的两次按键里只有一次能通过。
inFlight 仍负责批准带上「起飞中 / 基线运行中」的显示，不变。
否决的方案

每个 change 一把 promise 锁、让后到的按键排队。排到时计划可能已变，还得再核一次指纹，复杂度不值。

模块级 queued: Map<string, number>。drive() 入队时加一，这次 drive 的 Promise 结束时减一（含异常）。
「正在飞」判据改为

driving.has(name) || (queued.get(name) ?? 0) > 0 || 活 agent 非空。

否决的方案

每个 change 一条队列。不同 change 的合回会并发，需要重新论证合回互斥。

决策页 Q4 选「锁释放时补推一次」。按「派发只在活 hook 里」的约束，补推不能在释放锁的地方直接重试

持有者可能是 tick，手上没有活凭证。所以补推改为下一次 tick 补发唤醒，重试仍在唤醒那一轮结束时、在活的 hook 里做。最多晚一个 tick（60 秒），不会卡到过期。

Risks / Trade-offs

[错过的那一轮要等下一次 tick]

最多晚 60 秒 → 可以接受；之前会卡到 30 分钟过期。

[pressing 让连按一律被拒]

第二次按键得到「正在起飞，稍候」→ 与 #57 的语义一致，不排队。

[测试世界模拟不出撞锁的微小窗口]

afterMissedTurn 是纯函数，用 armed.test.ts 直接测；orchestrator 的接线只是几行。

[冒烟要求人在基线跑完前按键]

错过窗口就只验证冒烟 1，冒烟 2 留到以后碰上再看。
