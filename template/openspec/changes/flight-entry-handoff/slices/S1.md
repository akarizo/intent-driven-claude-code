## 测试世界先做的两件事（只改测试，不算生产代码）
- **补来源**：`orchestrator.test.tsx` 里有 58 处 `$.command.run({ command: 'opsx-apply', ... })`，都不带来源。实现之后，不带来源的起飞会被拒，所以要逐处改成人发出的：`$.command.run({ command: 'opsx-apply', args: ..., ...HUMAN } as never)`。
  - `HUMAN` 已在文件中定义，即 `{ origin: { kind: 'composer' } }`。
  - 专门测来源的新用例除外。
  - 改完跑一次 verify，确认现有用例仍绿，再按测量协议往下走。
- **注册可被拒绝**：给 `World` 加一个字段 `registerRefuses?: string[]`。世界的 `command.register` hook 遇到列表里的名字时，抛出 `new Error(\`$.command.register: "/${e.name}" refused: it is the user's /${e.name}\`)`，模拟引擎拒绝与项目命令文件同名的注册。

## 做什么（`template/plugins/flight/hooks/orchestrator.tsx`，design D1–D3）

### 1. 来源常量与拒绝文案
- `HUMAN_ORIGINS` 改为 `HOST_ORIGINS = ['composer', 'bridge', 'sdk']`。
- 新增一个函数，生成统一的拒绝文案：`flight：${cmd} 会写账本，只接受人或宿主程序发出（终端、Remote Control、SDK；本次来源：${kind ?? '未标明'}）`。
- `/flight abort` 与 `/flight resume` 改用 `HOST_ORIGINS` 与这句文案。

### 2. `/opsx-apply` 查来源
`command.run { command: 'opsx-apply' }` hook 的检查顺序：
1. `--engine=workflow` 照旧拒绝；
2. `--gate=per-task` 照旧 `next(e)`；
3. 然后才检查 `e.origin?.kind`，不在 `HOST_ORIGINS` 里就返回上面的拒绝文案（`cmd` 为 `/opsx-apply`），不调用 `takeoff`。

### 3. 注册 `opsx-apply`
在带 `{ cwd: /^/ }` matcher 的 `session.start` hook 里，`flight` 注册之后，再注册 `opsx-apply`，参数为 `{ name: 'opsx-apply', description: '飞行模式 apply：由 flight 插件状态机执行（批准后起飞）', argumentHint: '<change>' }`。
- 放在 `try` 里，异常一律忽略。项目已有同名命令文件时引擎会拒绝，这时照旧靠拦截接管。
- 两次注册各自独立 `try`：一个失败，不影响另一个。
