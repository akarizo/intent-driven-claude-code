Why · 01为何而做

2026-10-14 在 afa 起飞 dlib-post-hooks-root-to-data-dir，人连发三次命令都被同一句拒绝挡回：

| 输入 | 插件回复 | |---|---| | /opsx-apply dlib-post-hooks-root-to-data-dir | 工作区不干净，不起飞（工件之外的未提交改动）：executor/tests/af_dlib/post_hook_helpers.py、openspec/adr/INDEX.md | | /opsx-apply dlib-post-hooks-root-to-data-dir 授权提交（两次） | 同上 |

第四次改用自然语言「授权提交」，模型才在 change 分支上手动提交这两个文件，之后起飞通过。

两个文件都是 propose 阶段的正当产出：前者是 scenario 骨架测试 import 的辅助模块，后者是 afa 约定的 ADR 索引（新 DRAFT 要登记一行）。插件只认三类工件（change 目录、adr/DRAFT-*.md、scenario_tests 映射到的测试文件），这类周边文件无处声明，碰到就必然拒飞。拒绝信息又只列路径，没说「授权提交」管不到这些文件，也没给出路，人自然会反复重试。

「工件之外一律拒飞、授权提交也不放行」是 flight-takeoff-commit 有意的 fail-closed 设计，本 change 保留它；要补的是合法周边文件的声明渠道，以及拒绝时可照做的出路。

What · 02变更范围

  • slices.json 新增可选字段 artifact_files：路径数组，相对 change worktree 根（与 scenario_tests 的路径同一基准），精确路径、不支持通配。起飞时列出的文件与三类工件同等对待：随「授权提交」或批准带按键一并提交；未声明的照旧算工件之外。slices.json 在计划指纹白名单内，声明须经人批准。
  • lint 校验 artifact_files：必须是字符串数组；每项非空、不是绝对路径、不含 .. 段、不含通配符（* ? [）、不是已编号 ADR（adr/NNNN-*.md，ADR 不可改）。缺省时行为不变。
  • 审批面板列出 artifact_files：spec.html 飞行计划区单列一表，让人批准时看得到哪些工件之外的文件会被一并提交。
  • 工件之外的拒绝信息给出路：仍只列工件之外的路径，后面补两行：「授权提交」只提交本 change 的工件、不覆盖上面这些文件；处理办法是自行提交或撤销，或者属于本 change 的就列进 artifact_files、重新批准后起飞。起飞待命仍把这条拒绝归为只能人处理。
  • 批准带的工件计数含 artifact_files 中未提交的文件。
  • 文档：opsx-apply 命令与 openspec-apply-change skill、opsx-propose 命令与 openspec-propose skill 同改；schema 的 tasks instruction 写明 artifact_files 的用途；README 的飞行说明同步。
  • 插件补丁版本 +1（0.10.4，见 Impact 的顺序）。
插件：template/plugins/flight/hooks/land.ts（classifyDirty 增加声明文件入参）、hooks/orchestrator.tsx（读 artifact_files、拒绝文案）、hooks/register.tsx（批准带计数）、.claude-plugin/plugin.json。判定器与渲染：template/.claude/hooks/slice-gate.py（lint）、template/.claude/hooks/spec_html.py。schema：template/openspec/schemas/intent-driven/schema.yaml 的 tasks instruction（只改说明文字）。文档：template/.claude/commands/opsx-apply.md、template/.claude/skills/openspec-apply-change/SKILL.md、template/.claude/commands/opsx-propose.md、template/.claude/skills/openspec-propose/SKILL.md、README.md。测试：新增 tests/test_flight_artifact_files.py、tests/test_artifact_files_plan.py、tests/test_artifact_files_docs.py；TS 测试追加在 land.test.ts、orchestrator.test.tsx、flight.test.tsx。顺序：flight-dispatch-followups（正在飞）同样改 orchestrator.tsx、register.tsx、flight.test.tsx 与 plugin.json（0.10.3）。本 change 等它合入 main 后再起飞：起飞前把 main 预合并进本分支并重跑 baseline；S3 届时把它的版本断言 tests/test_dispatch_followups_docs.py 改成 0.10.4。

Specs · 04行为规范 (Gherkin)

flight-takeoff-artifact-files ADDED

Requirement: 计划声明的周边文件按工件起飞提交

插件 SHALL 把 slices.json 的 artifact_files 列出的路径（相对 change worktree 根、精确匹配）在起飞时与 change 目录、DRAFT ADR、scenario 测试文件同等算作本 change 的工件；未声明的路径 SHALL 仍归为工件之外。批准带的工件计数 SHALL 用同一口径。

  • GIVENchange 目录 template/openspec/changes/demo、声明文件 tests/helpers.py 与 openspec/adr/INDEX.md
  • AND未提交的路径为 tests/helpers.py、openspec/adr/INDEX.md、tests/helpers.py.bak、src/x.py
  • WHEN对这些路径分类
  • THEN工件恰为 tests/helpers.py 与 openspec/adr/INDEX.md
  • AND工件之外恰为 tests/helpers.py.bak 与 src/x.py

  • WHEN人发出 /opsx-apply demo 授权提交
  • THEN起飞前有一次提交，加入的路径恰为这些工件与两个声明文件

Requirement: 工件之外的拒绝给出可照做的出路

有未声明的工件之外改动时插件 SHALL 拒绝起飞（带不带「授权提交」都一样）。拒绝信息 SHALL 只列工件之外的路径，并说明「授权提交」不覆盖它们与两种处理办法；起飞待命 SHALL 仍把它归为只能人处理。

Scenario: foreign-dirt-refusal-explains-way-out

  • AND没有提交，账本没有 takeoff
  • AND起飞待命对这条回复的分类为只能人处理

artifact_files 缺省时 lint 行为 SHALL 不变；存在时 lint SHALL 要求它是路径数组，每项非空、相对、不含 .. 段与通配符、不是已编号 ADR，否则判红。

Design · 05技术设计

Context

  • 起飞时脏工作区处理（flight-takeoff-commit D2–D4）：git status --porcelain → classifyDirty（plugins/flight/hooks/land.ts:42）分成记录 / 工件 / 工件之外；工件之外非空即拒（hooks/orchestrator.tsx:685）；工件经「授权提交」或批准带按键由 commitArtifacts 提交。
  • 工件来源只有三类：change 目录、同一 openspec 根下 adr/DRAFT-*.md、scenarioFiles()（orchestrator.tsx:575）从 slices.json.scenario_tests 取的测试文件。批准带计数（register.tsx:176 artifactCount）走同一口径。
  • 计划指纹白名单含 slices.json（.claude/hooks/plan_fp.py:9）：在 slices.json 里写的东西必经人批准（DRAFT-approval-bound-to-plan-fingerprint）。
  • 起飞待命按拒绝文字分类（hooks/armed.ts:44 classifyRefusal）：工件之外的拒绝现归 human（只通知、不重试）。改文案不能让它落进别的类。
  • 跨模块（插件 TS · 判定器 Python · 渲染脚本 · schema 说明）且给 slices.json 契约加字段 → 命中设计触发器。

Goals / Non-Goals

Goals: - 本 change 的周边文件（测试辅助、ADR 索引、conftest 等）可在计划里显式声明，经人批准后随工件一并提交。 - 工件之外的拒绝信息说清「授权提交」管不到它们，并给出可照做的出路。

Non-Goals: - 不放宽 fail-closed：未声明的文件仍拒飞，「授权提交」不扩大范围。 - 不自动推断（如解析测试 import）；不支持通配；不内建 afa 的 adr/INDEX.md。 - 不校验声明文件是否真有改动（人已定：Q3=不要求）；起飞时没脏就不提交，无害。 - 不拒绝与 change 目录或 scenario 测试文件重复的声明：重复无害，少一条判据少一处误报。

Risks / Trade-offs

[模型借 artifact_files 夹带生产代码] → 声明在指纹内、spec.html 单列一节给人看；起飞前只是提交，不绕过 G5/G9 等门禁。
[改 slices.json 让已批准计划失效] → 预期行为

新增声明须重新批准；拒绝文案已写明。

[与 flight-dispatch-followups 改同一批文件] → 等它合入后预合并 main、重跑 baseline 再起飞；S3 更新其版本断言。
[非 ASCII 路径被 git 加引号] → 精确匹配失败、归工件之外（fail-closed，沿用 flight-takeoff-commit 的假设）。

Migration Plan
