Why · 01为何而做

用户目标是无人值守到 PR（2026-10-13）。按同仓同口径实测，Mod 单次飞行并不比 v2.0 慢：每片中位 3.5 min，v2.0 为 5.5 min。体感慢的根源是停飞后要等人：

- 停飞率：Mod 飞过的 15 个 change 里，有 6 个要二次起飞或作废重飞。 - 6 次真实停飞的复盘（来源：账本 + 记忆）： - 不改计划就能自愈的有 2 次： - ledger-guards a1：S9 合回失败，不是冲突，人只发了 /flight resume； - ship-ledger a1：final 红，原因是跨片测试失配，人授权主会话只改测试。 - 已修的有 1 次：measure a3。 - 必须人来的有 3 次： - hardening a1：控制面缺陷，受铁律 10 约束； - measure a1、interaction a1：规划失误，要改计划并重新批准，受铁律 7 约束。 - 看门狗缺口：ledger-guards a1 的 S9 执行体跑完全量 pytest 后 13 分钟没有响应（01:35:17 → 01:48:31），直到被人中断，控制面毫无察觉。 - 人回来后要做的事太多：要自己读账本找原因、改计划、手动重跑基线、按批准、回车起飞。停飞时控制面只发一条终端 toast，人离开电脑就看不到。

用户在 docs/flight-unattended.html 上定了 Q1–Q8： - 合成一个 change； - 从含 #52 的 main（e5551f4）切； - 看门狗 10 min； - 自愈预算：每次飞行合计 ≤ 3，同片同类 ≤ 1； - 整合修复体可改 owns 并集，scenario 测试除外； - 只用终端通知； - PR 开出时也通知； - 停飞派只读诊断 agent。

另外两条已定：final 红在跨片失配时，允许修复体改既有测试，但要加护栏；铁律 7、10 不放宽。

What · 02变更范围

  • 自愈（不改计划、不改规则，均有预算）：
  • A1 合回失败重派：切片合回失败且不是冲突时，记一条 heal（merge-retry）事件，再用新 worktree 重派一次执行体；第二次仍失败才记 blocked。
  • A2 看门狗：控制面跟踪每个飞行 agent 正在等待的模型请求。等待超过 10 分钟，记 heal（watchdog），再用 TaskStop 停掉它，之后按角色处理：
  • 执行体：走现有「未正常收口 → 补跑门禁 → 续派一次」；
  • 评审员、修复体：各重派一次。
  • 预算用尽时停飞（kind watchdog）。
  • A3 预算：每个 attempt 的 heal 合计 ≤ 3；同一（slice, 种类）≤ 1；超出即按原行为 blocked / 停飞，原因写明「自愈预算已用尽」。
  • A4 整合修复体：final 红、没有 blocked 切片、预算允许时，记 heal（integ），派修复体 integ，输入是 final 的失败清单。
  • 收口门禁：slice-gate.py final --integ-base <派发时分支尖端>，新增 G9 整合护栏：
  • 不改 change 工件（specs / design / proposal / tasks / slices.json / 切片包）与 ADR；
  • 不碰 scenario 映射的测试函数；
  • 测试 assert 不净减少、不新增 xfail/skip、不删测试函数；
  • 写入范围另由包络限在全部切片 owns 的并集内。
  • 门禁绿后派评审员专审 integ 的 diff：有 CRITICAL/HIGH 即停飞；否则合回、再跑 final。
  • 每个 attempt 至多 1 轮；再红即停飞。
  • 停飞后最快接上：
  • B1 终端通知：$.ui.notify 走用户自己的通知通道（iTerm2 / kitty / ghostty / 响铃）。以下几种情况各通知一次：
  • 停飞（人工中止除外）；
  • 诊断就绪；
  • PR 开出（链接、ready/draft、blocking 条数）；
  • 交接 /flight:pr-ship 失败。
  • B2 诊断包：
  • halt 事件带 kind：blocked / final / integ / fingerprint / control / watchdog / abort。
  • 除 abort、fingerprint 外，停飞后派只读诊断员 flight:diagnostician（主模型 high）。
  • 它的最终回答记为 triage 事件：根因、该谁动、改计划时附草案。只供展示，不参与任何判定，也不落盘。
  • B3 一键续飞：批准带对已停飞的 change 换成两种按钮：
  • 计划改过：「批准修订并续飞」。按下 = 写 approve（新指纹）→ 停掉仍在跑的诊断员 → 后台重跑 slice-gate.py baseline → 绿则预填 /opsx-apply <change> 授权提交，人回车即续飞（只提交本 change 工件，只重派未合回的切片）；红则通知原因、不预填。
  • 计划未改：「续飞」，直接预填同一条命令。
  • 按下即直接起飞（不用回车）需要 orchestrator.tsx 交出起飞闭包，留给后续 change「起飞待命」（2026-10-13 attempt 2 后修订）。
  • 首次起飞仍是「批准起飞」+ 人回车 /opsx-apply，不变。
  • 记录与核对：
  • 账本新增 heal、triage 事件，dispatch 认 diagnostician 角色，halt 可带 kind；
  • timeline.py report 打印自愈次数与停飞诊断首行（铁律 8）；
  • slice-gate.py features 新增 integ-guard，插件起飞时核对。
  • 文档与版本：/opsx-apply 命令与 skill 同改，README、WORKFLOW 同步；插件 0.9.0。
  • final 红不再一律停飞：满足条件时先派整合修复体。依赖「final 红即停飞」的旧用例要改。
  • 切片合回失败（非冲突）不再立刻 blocked，先重派一次。
  • 主检出须快进到本 change 合入后的 main，否则起飞会因判定器缺 integ-guard 被拒（沿用 #50 的核对机制）。
插件（template/plugins/flight/）：hooks/ 下的 core.ts、envelope.ts、prompts.ts、landing.tsx、ship.ts、io.ts、orchestrator.tsx、versions.ts、register.tsx；新增 hooks/watchdog.ts、hooks/resume.ts、agents/diagnostician.md；types/index.d.ts；.claude-plugin/plugin.json（0.9.0）。判定器（template/.claude/hooks/）：slice-gate.py（G9、integ-guard）、ledger.py（新事件）、timeline.py（自愈与诊断行）。文档：/opsx-apply 命令与 skill、README.md、docs/WORKFLOW_zh.md。ADR：新增两份。DRAFT-flight-bounded-self-heal：自愈只做不改计划的再试，先记后做，有预算，G9 护栏。DRAFT-flight-resume-from-band：部分取代 DRAFT-flight-orchestrator-state-machine 第 1 条「人照旧发 /opsx-apply」，停飞后的续飞可由批准带按键触发。本 change 自己的飞行：在已装的 0.8.0 上飞，判定器用主检出的副本（须先快进到 e5551f4）。本 change 改的是 worktree 里的插件与判定器，不影响这次飞行的控制面。也就是说，这次飞行本身还享受不到自愈。

flight-halt-handoff ADDED

Requirement: 停飞带分类

Feature: 用户定：停飞时机械分类，再交诊断员。

ev.halt SHALL 接受可选的 kind 并写入事件。

Scenario: halts-carry-kind

  • WHEN分别求 next，并构造 ev.halt(b, {attempt: 1, reason: 'x', kind: 'watchdog'})

resumeFlight 的步骤： 1. 停掉该 change 仍在跑的诊断员； 2. replan 时运行 slice-gate.py baseline --change-dir <D>： - 退出 0 → 调用依赖 takeoff(['<change>', '授权提交'], {resume: true})； - 非 0 → 通知「基线红，未续飞」与 reasons 首行，SHALL NOT 调用 takeoff； 3. 不 replan 时跳过基线，直接以同样参数调用 takeoff； 4. 把 takeoff 回复的首行通知出去。

批准带接线时，takeoff 依赖 SHALL 把 /opsx-apply <change> 授权提交 预填进输入框，由人回车续飞，并回复「已预填 /opsx-apply <change> 授权提交，回车续飞」。预填不成时，回复提示人手动输入该命令。

  • AND乙的账本没有追加 approve，乙没有跑基线；输入框被预填为 /opsx-apply 乙 授权提交
  • AND通知含「回车续飞」

  • AND丙没有调用 baseline，调用了 takeoff

Requirement: final 红时先派整合修复体

以下条件同时满足时，closing() SHALL 先返回 heal（kind integ，slice integ）： - 全部计划切片已合回、没有 blocked； - 本 attempt 最新 final 红且 commit 非空； - 本 attempt 没有派过 slice 为 integ 的修复体； - healVerdict 允许。

Feature: 用户定（2026-10-13）：final 红在跨片失配时，允许修复体改既有测试，但要加护栏。ship-ledger a1 就是这样被人工修好的。

账本已有这条 heal 时，SHALL 返回 dispatch fixer，slice: 'integ'、findings: []、failed 为该 final 的失败清单。任一条件不满足时，SHALL 照旧停飞，kind 为 final。

Goals / Non-Goals

Goals

  • 不改计划就能解决的停飞，在飞行内自愈：合回失败重派、看门狗、整合修复体。全部有预算、全部记进账本，人事后看得见。
  • 必须人来的停飞：立刻在终端通知，附只读诊断，人改完计划后按一次键就续飞。
  • 不放宽铁律：
  • 计划变了仍要人按批准（铁律 7）；
  • 控制面异常仍停飞（铁律 10）；
  • 整合修复体照样经机械门禁与独立评审（铁律 4、5）。

Non-Goals

  • 不自动改计划、不自动批准、不重试控制面异常。
  • 不做手机推送与手机批准（用户 Q6 选只用终端通知）。
  • 不做规划期预防 lint（owns 漏守卫测试、改状态机的片与旧用例同 wave）：用户未选，留 backlog。
  • 不治「门禁在未提交工作区判绿」的根因：另有人跟进；A1 只是兜底。
  • 本 change 自己的飞行跑在 0.8.0 上，享受不到自愈。

C4 · 容器视图（轻量 C4 风格，普通 Mermaid）

  • 边界：
  • 一切写账本的动作都在插件进程内：approve 只由按键写，其余事件由状态机、看门狗写；
  • 判定器只读账本；
  • 模型不可调用任何写账本或续飞的入口。
  • 新增：看门狗、resume.ts、诊断员，以及批准带的两种新按钮。整合修复体复用修复体 agent 类型（fixer），只是 slice 名为 integ、门禁多一道 G9。
  • 假设：通知只到终端；人不在电脑前时，靠人自己在 Notification hook 里转发（用户选项 Q6-B）。

Risks / Trade-offs

[看门狗误停正常的长思考] → 阈值 10 分钟

历史回放误停为 0。误停一次的代价只是一次重派，且受预算约束；预算用尽即停飞通知人，不会无限循环。

[真实引擎里计时器周期被拒（"a refused period ends the interval"）] → 每次 turn.step 开始时若计时器已结束就重新起一个（幂等）。实现片须覆盖。
[整合修复体以改弱测试换绿] → 三道防线
[自愈掩盖真实问题] → heal 先记后做，面板、飞行记录、timeline 都打印；每个 attempt 最多 3 次。
[诊断员花 token] → 只在停飞时派（低频），abort、fingerprint 不派；看门狗对已停飞 attempt 的 agent 直接停。
[一键续飞自动提交工件] → 按钮旁写明；只提交本 change 工件（现有 classifyDirty），工件之外有脏改动照旧拒飞。
[基线跑 2–3 分钟期间人以为没反应] → 起跑与结束各 toast 一次；面板显示「续飞准备中

基线运行」。

[turn.step 在 claude plugin test 世界里能否触发未知] → S3 的跟踪逻辑放纯模块单测；S5a 的接线用例若测试世界发不了 turn.step，改为经注入点驱动 StepTracker，并在切片包里写明。attempt 1 已核实

测试一侧可以用 $.turn.step({agentId, model}) 发出（model 必须非空），由测试世界自己应答，写法见 S5a 切片包。
