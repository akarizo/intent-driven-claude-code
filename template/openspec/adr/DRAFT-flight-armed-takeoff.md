# DRAFT. 起飞意图被拒后由插件有界地挂起重试；批准带按键即起飞

- Status: accepted, supersedes DRAFT-flight-resume-from-band 的两处：第 1 条中「首次起飞仍要人回车 `/opsx-apply`」，以及其修订段「按键后预填、人回车续飞」

## Context

- **起飞被拒后必须人再发一句**：
  - `/opsx-apply` 是插件处理的本地命令，输出不开模型对话；
  - 模型没有起飞入口（铁律 7）。

  flight-unattended 一次飞行前后被拒三次（起飞异常、工件未提交、已暂存删除让 `git add` 报错），每次都要人在场。
- **#53 的降级**：插件里 `$` 不能跨文件传，`register.tsx` 调不了 `orchestrator.tsx` 的 `takeoff`。续飞按钮因此降级为预填，首次起飞也一直是「按键 + 回车」。
- **实测**（CLI 2.1.296）：
  - 一个文件在自己 hook 里造的闭包可以交给另一个文件调用；
  - `$.prompt.submit` 不能在 `command.run` 处理中调用（引擎会拒绝），用 `clock.after(0)` 延后可行，且这一轮的 `turn.complete` 插件看得到。
- **用户决策**：2026-10-13，决策页 `docs/flight-armed-takeoff.html` 的 Q1–Q8 全按推荐。

## Decision

1. **起飞意图挂起为待命**：人发出的起飞（命令或按键）被拒时，插件按拒绝原文分五类：
   - **等待**：基线仍在跑、上一次的 agent 仍在运行；
   - **偶发**：起飞异常、账本读不出、指纹算不出等；
   - **交模型**：lint 红、基线缺失或中断、提交工件失败；
   - **人按一次键**：未批准或计划已变、工件未提交；
   - **只能人**：其余全部，认不出的文本也归这一类。

   前三类挂起，自动重试。后两类通知人怎么做，不挂起。
2. **有界**：
   - transient、model 两类计入预算，最多 3 次；
   - 等待类不计入预算；
   - 整个待命 30 分钟内有效；
   - 偶发只重试一次；
   - 人随时可以 `/flight abort <change>` 取消，再发一次起飞则重新计算。
3. **交模型**：
   - 经 `$.prompt.submit` 以插件身份发一轮，在命令处理返回之后提交；
   - 正文写明只修工作区与本 change 工件、改了计划要人重新批准、不要发 `/opsx-apply`；
   - 这一轮结束后插件重试。
4. **待命状态只在会话内**（`$.state`），不进账本；偶发失败只追加既有的 `diag` 事件留证据。
5. **批准带按键即起飞**：
   - 「批准起飞」「批准修订并续飞」「续飞」与新增的「起飞」（已批准未起飞）都直接起飞，起飞一并提交本 change 的工件；
   - 起飞经 `orchestrator.tsx` 在自己 hook 里造好的闭包 `takeoffNow`。
6. **模型仍没有起飞入口**：
   - 不注册新命令、新工具；不以插件来源发 `/opsx-apply`；
   - 模型改了计划，指纹就会变，起飞守卫照旧拦下，必须人按键。

否决的方案：
- **起飞被拒就停，等人再发**：人不在时整个流程停在原地，这正是要解决的问题。
- **待命写进账本（新事件）**：可审计，但要改判定器与版本核对；待命本来就绑在发出它的会话上。
- **拒绝原因结构化（改 20 个出口）**：更稳，但改动面大；按文本分类认不出时退化成通知，是安全的。
- **以插件来源发 `/opsx-apply` 或 `/flight resume`，为 plugin 来源开口子**：任何插件都能借这个口子起飞。
- **首次起飞保持「按键 + 回车」**：多一步，且与续飞按钮行为不一致。

## Consequences

- **更易**：
  - 起飞被拒的常见情形（基线还在跑、lint 小错、偶发异常）不再要人在场；
  - 人的动作从「按键、回车，被拒后再发一句」缩成「按一次键」。
- **更难**：
  - 拒绝文本成了分类依据，改文本要同步 `armed.ts` 的字样表，否则退化成通知；
  - 交模型会花 token（有预算约束）；
  - 按键即起飞少了一道回车确认。
- **中性**：
  - 待命不进飞行记录（不属于 apply 收口的度量）；
  - 跨会话、版本不符等情形照旧只能人处理。
