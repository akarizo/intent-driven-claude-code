Why · 01为何而做

flight-measure（#46）的四次 attempt 暴露了控制面在续飞上的三个缺陷。#45 已修掉第四个（切片阻断仍派修复体）。

1. 续飞复用了过期的切片现场：attempt 1 后计划修订并重新批准，attempt 2/3 的 S7 执行体仍被派进旧 worktree。 - 那里的切片包和 slices.json 都是旧版本，门禁也按旧的 owns 判。 - 结果和 attempt 1 一模一样地红了三次。最后由用户手动跑清理脚本才过去。 2. 修复体复用了旧尖端的 worktree：修复体的 worktree 是从 attempt 1 的分支尖端切出的，里面没有之后合回的切片，全量 final 必然红。 3. 两个会话可以同时起飞同一个 change：attempt 2 来自另一个会话，attempt 3 来自本会话，相隔 1 分钟。起飞前「上一次的 agent 是否还在跑」只查本会话的 agent，所以两个 S7 执行体并发改了同一棵 worktree。

#46 评审还留下几处包络缺口： - /usr/bin/env、"exec" 这类带路径或引号的前缀不会被剥掉，后面的拒绝表与 worktree 限制都绕得过去； - cd "$(…)"、cd ".$X" 这类目录参数里带 shell 展开时，会被当成 worktree 内的相对路径； - 「无法判定」的拒绝理由仍写「相对路径且无绝对基准」，和目录栈旋转等实际原因对不上。

另外两处小问题： - 测量工具的误导理由：在飞账本读不出时，测量工具回复「只有本次飞行的执行体可以请求测量」，执行体可能因此放弃测量。 - /pr-ship 第 4 步的冲突统计恒为 0：它用 grep -c "^<<<<<<<" 统计旧版 merge-tree 的输出，而那里的冲突标记前面带 +。#46 实际有 2 个文件冲突，它报的是 0。

What · 02变更范围

  • 新派发另起 worktree（用户定）：新派发的执行体、修复体、解冲突 agent，如果同名 worktree 已存在，就从当前分支尖端另建 <名>-a<attempt>。
  • 旧 worktree 原样保留，不删、不重置（铁律 6）。
  • dispatch 事件记下分支；合回、解冲突、修复合回都按记下的分支来合。
  • 执行体提示词写明上一次的分支可以用 git show 参考。
  • 续接只限同一份计划：上一次 attempt 的计划指纹与本次不同时，不再续接旧现场、也不补跑门禁，一律按新派发处理。
  • 跨会话起飞默认拒飞（用户定）：最新一次起飞来自另一个会话、并且还没落地或停飞时，拒绝起飞，提示到原会话继续，或用 --takeover 接管。接管会记进 takeoff 事件。
  • 包络余项：
  • 前缀命令按 basename 去引号后再查表；
  • 目录参数（cd / pushd / -C / --git-dir / --work-tree / env -C）中任意位置出现 $、反引号或不配对的引号，一律判为无法判定；
  • 「无法判定」的拒绝理由改成中性措辞。
  • 测量工具：调用者的归属判不出时，回复「暂时无法判定归属，稍后重试」。
  • /pr-ship 第 4 步改用 git merge-tree --write-tree --name-only 的退出码判断冲突。
  • /opsx-apply 命令与同名 skill 写明 --takeover 和新派发另起 worktree 的语义。插件版本升到 0.4.1。
插件：template/plugins/flight/hooks/ 下的 core.ts、io.ts、land.ts、envelope.ts、prompts.ts、orchestrator.tsx、landing.tsx，以及对应的 TS 测试与 pytest 包装；插件版本 0.4.1。文档：template/.claude/commands/pr-ship.md、opsx-apply.md、template/.claude/skills/openspec-apply-change/SKILL.md。本 change 是测量协议的首飞（在已安装的 0.4.0 上飞）：执行体须先让测试红并调用 measure，G5 按账本判定，不满足即判红。首飞中如果发现测量协议本身的问题，如实记录，不绕过。

Specs · 04行为规范 (Gherkin)

flight-envelope-remainders ADDED

Requirement: 带路径或引号的前缀命令照样剥掉

words 判断段首前缀（builtin、command、exec、env）时 SHALL 先去掉一层引号再取 basename；/usr/bin/env、"exec"、'command' 这类写法 SHALL 与裸名同样剥掉，其后的命令照常判定。 Feature: #46 S9 评审 MEDIUM：/usr/bin/env -u FOO git push 放行

Scenario: prefix-path-and-quotes-stripped

  • GIVEN执行体 worktree 为 W，主仓库为 /repo
  • WHEN判定 /usr/bin/env -u FOO git push origin HEAD:main、/usr/bin/env GIT_DIR=/repo/.git git commit -m x、"exec" -a n git push、'command' cd /repo && git commit -m x，以及 /usr/bin/env -u FOO python3 -m pytest -q
  • THEN前四条被拒：第一、三条理由含「git push」，第二条含「GIT_」，第四条含「自己的 worktree」
  • AND最后一条不被拒

Requirement: 目录参数里的 shell 展开判为无法判定

resolveDir 对参数去掉一层引号后，若任意位置仍含 $、反引号、' 或 "，SHALL 返回无法判定；cd、pushd、git -C、--git-dir、--work-tree、env -C 都经此判定。不含这些字符的引号路径（如 'W/a b'）不受影响。 Feature: #46 follow-up 复核的范围外线索：cd "$(printf /repo)"、cd ".$X" 被当成 worktree 内的相对路径

Scenario: expanded-dir-args-undeterminable

  • GIVEN执行体 worktree 为 W
  • WHEN判定 cd W && cd "$(printf /repo)" && git commit -m x、cd W && X=/../../../..; cd ".$X" && git commit -m x、git -C "./$X" commit -m x、` cd echo /repo && git add a ，以及 cd 'W/a b' && git add x、cd W/sub && git add x`
  • THEN前四条被拒，理由含「自己的 worktree」
  • AND后两条不被拒

Requirement: 「无法判定」的拒绝理由用中性措辞

改动类 git 因作用目录无法判定而被拒时，理由 SHALL 写「作用目录无法判定（目录栈旋转、相对路径无基准、变量或命令替换等）」，SHALL NOT 再写「相对路径且无绝对基准」。 Feature: #46 follow-up 评审 LOW：理由与实际原因对不上，执行体会照错误的提示改

Scenario: undeterminable-reason-neutral

  • GIVEN执行体 worktree 为 W
  • WHEN判定 pushd +1 && git commit -m x 与 cd "$X" && git add a
  • THEN两条都被拒，理由含「无法判定」与「目录栈旋转」
  • AND理由都不含「相对路径且无绝对基准」

flight-fresh-worktrees ADDED

Requirement: 新派发遇到同名 worktree 时另起一棵

io.freshWorktree(io, f, name, attempt) SHALL： - flight-<change>-<name> 不存在时，基于 change 分支尖端以 name 建 worktree（分支 flight/<change>/<name>）； - 已存在时，改建 <name>-a<attempt>（分支 flight/<change>/<name>-a<attempt>），SHALL NOT 改动已存在的 worktree； - 两者都已存在时返回错误； - 返回 { path, branch }。 Feature: flight-measure attempt 2/3：S7 被派进计划修订前的旧 worktree，按旧 owns 判门禁

Requirement: 合回、解冲突、修复合回按记下的分支

land.mergeSlice、prepareResolve、finishResolve、mergeFix SHALL 接受调用方给出的分支（解冲突另给 worktree 与分支），并对该分支做合并、已合回判定、越界与空合回检查；不给时沿用旧的分支拼法。解冲突 worktree SHALL 按「新派发另起」的规则命名。 Feature: 另起的 worktree 用的是新分支名，写死的拼法会合错分支

Scenario: merges-use-recorded-branch

core.next 在本 attempt 首次派发某片时，若上一个执行体 dispatch 所在 attempt 的 takeoff 指纹与本次 takeoff 不同，SHALL 给出不带续接说明、不带 base 的新派发，SHALL NOT 给出 regate；指纹相同时行为不变。 Feature: 计划修订后续接旧现场 = 按旧切片包继续做

Design · 05技术设计

Context

flight-measure（#46）飞了四次 attempt，证据都在账本 refs/flight/flight-measure/ledger 和 PR #46 正文的「飞行实况」里： - attempt 1：S7 阻断后，控制面仍派出修复体。#45 已修，切片阻断时直接停飞。 - 计划修订之后：attempt 2/3 的 S7 被派进旧 worktree。ensureWorktree 见到路径已存在就原样复用，切片包、slices.json 与门禁判定的 owns 都是旧版本。 - attempt 2 与 3 来自两个会话：起飞前的并发检查用 $.agent.list()，只看得到本会话的 agent。 - 修复体：ensureWorktree(FIX) 复用了 attempt 1 从旧尖端切出的 worktree，它的全量 final 必然红。

用户在本 change 规划时定的两点（2026-10-11）： - 跨会话起飞默认拒飞，--takeover 显式接管； - 新派发遇到同名旧 worktree 时另起一棵，旧的原样保留。

相关事实： - 合回、解冲突、修复合回现在都把分支名写死为 flight/<change>/<S>、flight/<change>/<S>-resolve、flight/<change>/fix。 - 账本的 dispatch 事件允许表外字段（ledger.py 与 io.ts 都只校验必需字段）。 - 铁律 6：不删 worktree。

Goals / Non-Goals

Goals： - 续飞永远不会把执行体或修复体派进过期的现场； - 同一个 change 不会被两个会话同时驱动，除非人显式接管； - #46 评审留下的包络缺口闭合； - /pr-ship 的冲突检查如实。

Non-Goals： - 清理旧 worktree：清理仍是人的动作，交给用户执行（铁律 6）。 - 判断另一个会话是否还活着：插件没有这种能力，由人用 --takeover 表态。 - default 权限模式下 cd 前缀判 ask 还是 deny：仍待实测。

Decisions

函数

新增 io.freshWorktree(io, f, name, attempt)。

<主 worktree>/.claude/worktrees/flight-<change>-<name> 不存在 → 按 name 建，分支为 flight/<change>/<name>；
已存在 → 建 <name>-a<attempt>，分支为 flight/<change>/<name>-a<attempt>；
两者都已存在 → 报错（本片记 blocked infra）。
返回 { path, branch }。
新派发指

没有续接说明的执行体派发、每个 attempt 第一次派修复体、每次派解冲突 agent。

续接（带 continuation）复用上一个执行体 dispatch 记下的 worktree 与分支；那棵 worktree 已不存在时退回新派发。
dispatch 事件

多记一个表外字段 branch。旧账本的 dispatch 没有这个字段时，由 worktree 路径推出分支（flight-<change>-<name> → flight/<change>/<name>）。

否决

重置或删除旧 worktree。会丢掉旧现场里未提交的工作，也违反铁律 6。

计划指纹不同

上一个执行体 dispatch 所在 attempt 的 takeoff 指纹，与本次 takeoff 不同 → 一律新派发，不续接、不补跑门禁（regate）。旧现场是按旧计划做的。

指纹相同

行为不变，即上次已绿就 regate，否则带续接说明续接。

上一次被 blocked 的切片仍按新派发处理（现状如此）。
land.mergeSlice(…, branch)

合并、已合回判定、越界与空合回检查都改用传入的分支。

land.prepareResolve(…, { branch, attempt })

解冲突 worktree 同样按 D1 另起，合并传入的切片分支。

land.finishResolve(…, resolve)

用解冲突 dispatch 记下的 worktree 与分支。

land.mergeFix(…, branch)

用修复体 dispatch 记下的分支。

缺省（不传分支）时沿用旧的拼法，兼容旧账本。
控制面传入的分支取自本片最后一次门禁绿的那个 agent 的 dispatch。
没有 --takeover → 拒飞，回复
有 --takeover → 照常起飞，takeoff 事件多记表外字段 takeover: <原会话 id>。
前缀命令

words 判前缀（builtin、command、exec、env）时，对词先去一层引号，再取 basename。/usr/bin/env -u FOO git push 与 "exec" -a n git push 都按前缀剥掉，后面的 git 照常判定。

目录参数中的展开

resolveDir 对参数做一次去引号后，只要任意位置还有 $、反引号、' 或 "，就返回 null（无法判定）。cd、pushd、git -C、--git-dir、--work-tree、env -C 都走这里，一处改全覆盖。

拒绝理由

「无法判定」的拒绝理由改为「作用目录无法判定（目录栈旋转、相对路径无基准、变量或命令替换等）」。

退出 0

无冲突。

退出 1

有冲突，输出第一行之后、空行之前列出冲突文件，报告这些文件后停下交用户。

其他退出码

报告错误。

--takeover 的含义与适用场景；
新派发另起 worktree、旧现场保留，以及清理交给人。

Risks / Trade-offs

测量协议首飞

本 change 是测量协议上线后的第一次飞行。执行体须先让测试红并调用 measure，G5 按账本判定、不满足即判红。如果首飞暴露出测量协议本身的问题（误判红、测量超时等），如实记入 PR，不绕过门禁。

旧 worktree 越积越多

另起 worktree 不删旧的，清理靠用户（现在已有清理脚本的做法）。这是遵守铁律 6 的代价。

--takeover 依赖人的判断

人误接管时，原会话仍在跑的 agent 可能与新 attempt 并发。D1 让新派发另起 worktree，所以两边至少不会改同一棵树；续接的那片仍有风险，接管提示里写明「确认它已结束」。

天花板
目录参数里只要有引号字符就判为无法判定（去掉一层引号之后），宁可多拒；
兼容旧账本时，分支由 worktree 路径推出。
