# DRAFT. 多守门点的 review 编排采用水位线增量模型

- Status: accepted
- Date: 2026-08-25

## Context

intent-driven 工作流沿生命周期布了多个 code review 守门点：逐 task 守门（实现当下）、full review（change 收口）、`/pr-ship` 评审（送出时）、以及各自的复审轮。它们分三个 skill / command 独立演进，每个单独看都合理。

把范围放到一张表上对齐后暴露出结构性问题：这些守门点的 diff 范围是**包含关系**——`单 task 净 diff ⊂ change 累计 diff ≈ PR ↔ target diff`。同一份实现代码因此被同一个 `code-reviewer` agent 按同一套 rubric 全量重扫 3 次，测试纪律维度触及 4 次。文档里「靠不同 diff 范围区分，互补不重复」的说法与执行不符。

更深的成因是：**流程没有任何跨守门点的审查状态**。每次 review 都是 cold start，评审员既不知道哪段范围已被守门通过，也不知道哪些 finding 已被处理，只能全维度重扫。这不是某一个守门点的实现缺陷，而是编排层的缺失——只要继续按「每个守门点各自决定审什么」的方式新增守门点，重复就会持续增生。

需要一条跨后续变更都成立的编排原则，供以后新增 review 触发点时对齐，避免每次重新决策或再次叠加重复。

## Decision

采用**水位线（watermark）增量模型**作为多守门点 review 编排的默认结构，四条原则：

1. **一份代码只被全量审一次**。首次全量审发生在离代码最近的位置——逐 task 守门。此后任何守门点都只审「增量」或「上一次审不到的维度」，不重扫已审范围。
2. **审查状态显式落盘、跨守门点传递**。以 `openspec/changes/<change>/review-log.md` 记录已审 commit 区间、守门结论与未阻断的 deferred finding。它是人类可读的 markdown，随 change 归档，同时服务「机器判范围」与「人看审查深度」两个用途。
3. **守门点的范围由水位线决定，不由模型推断**。软判断（如「用户是否计划立即送出 PR」）一律改为硬判定：读水位线覆盖情况，或用一次明确问询取得用户决定。
4. **评审员的上报范围受模式约束**。评审任务声明模式（`full` / `integration` / `follow-up`）与已审范围；评审员不得重复上报该范围内已处理的 finding，但确认上游未闭环时仍可上报并标注。

配套的兜底原则：**读不到水位线时，一切回退到全量审**。水位线只能缩小「已被守门覆盖」那部分的范围，永远不能让未审代码蒙混过关。

本决策规约的是「谁审什么范围、状态怎么传」，**不触及**「怎么审」——分级 rubric、finding 格式、只读纪律仍归 `code-reviewer` agent 定义所有。

## Consequences

- **更易**：新增 review 触发点时有明确判据——先问「它审的范围与既有守门点是包含还是互补」，包含则接入水位线走增量，互补才独立成一道门。避免重复继续增生。
- **更易**：守门期间未阻断的 MEDIUM/LOW 首次有了确定的归宿与上浮路径，人类 reviewer 能看到 AI 的审查深度而非只看到一份结论。
- **更难**：任何新增守门点都必须显式声明自己的评审模式与已审范围，不能再「拿到 diff 就全量扫」。这是刻意增加的摩擦。
- **更难**：修复必须产出独立的 `fix:` commit 而非 `--amend`，牺牲「一 task 一 commit」的整洁性，换取修复增量区间可稳定圈定。
- **约束后续变更**：水位线的写入方必须唯一（逐 task 守门的主会话），读取方只读。若未来出现第二个写入方，需要重新评估本 ADR。
- **不影响**：串行（轻量）apply 模式、`/opsx-bulk-apply`、以及任何没有 review 记录的历史 change——它们走兜底分支，行为不变。
