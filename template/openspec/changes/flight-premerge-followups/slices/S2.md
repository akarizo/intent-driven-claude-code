## 做什么

### `core.ts`
1. `HaltKind` 加 `'premerge'`；`Action` 加 `{ kind: 'premerge' }`；`ev` 加 `premerge(b, { attempt, ok, ref, target, commit, conflicts, reason })`。
2. `closing()`：`const fin = last(ofA('final'))` 之后、原来 `if (!fin || …) return [{ kind: 'final' }]` 之前，**仅当 `!fin`** 时插入预合并判断（design D1）：
   - 本 attempt 没有 premerge → `[{ kind: 'premerge' }]`；
   - 最新 premerge `ok === true` → 照原逻辑 `[{ kind: 'final' }]`；
   - `ok !== true` → `halt('premerge', …)`：冲突为空时原因为「预合并失败：<reason>；处理后发 /flight resume <change>」，有冲突时为「预合并冲突：<文件列表>；人工在 change worktree 合并 <ref> 并提交后发 /flight resume <change>」（S4 会把有冲突的分支换成解冲突流程）。
   - 整合修复、修复轮之后重跑 final 的判断不动（已有 final，不会再预合并）。
3. 新导出纯函数 `planDefect(state: State): string | undefined`（design D6）：最新 attempt 有 kind 为 `blocked` 的 halt，且本 attempt 有 blocked 事件的 `reason` 同时含 `G5 measure` 与「在改生产代码之前就已通过」→ 返回该 reason 首行；否则 undefined。本片只实现并单测（`core.test.ts`），由 S4、S5 使用。

### `land.ts`
4. 新导出 `premergeTarget(io, f)`，按 design D2 第 1–8 步执行，返回 `{ ok, ref, target, commit, conflicts, reason }`；所有 git 都以 `-C f.changeTree` 运行。

### `landing.tsx`
5. `runLandingAction` 处理 `premerge`：先查停飞（同 reviewer 派发前的 `stoppedNow`），再调 `premergeTarget`，追加 `ev.premerge` 事件（字段原样）；不在这里写 halt（由下一轮 `next()` 给出）。
6. `wholeBase` / `reviewPlan`（design D3）：本 attempt 最新 `ok` 且 `target` 非空的 premerge 存在 → 起点取 `target`（`target === commit` 时照现状报「没有可审的改动」）；否则沿用 `merge-base <commit> <主检出 HEAD>`。需要账本时用调用方已读到的 state，不另读。

### `io.ts`
7. `EVENTS` 加 `premerge`（字段与 S1 接口摘要一致）；`OPTIONAL.halt.kind` 加 `premerge`。

### `orchestrator.tsx`
8. 若 `runAction` 对未知动作已交给 `runLandingAction`，则只需确认 premerge 走到那里；否则补一行转交。不在本片做 `/flight recheck`、续飞拒绝、解冲突（S4）。
