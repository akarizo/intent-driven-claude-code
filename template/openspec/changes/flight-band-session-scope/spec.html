Why · 01为何而做

批准带每次刷新都会遍历仓库的全部 worktree，把所有含 spec.html、tasks.md 仍有未勾选项的 change 都拿来评估，再显示 spec.html 最近修改的那一项（register.tsx 的 refresh / candidatesIn；原 spec flight-approval-ledger/specs/approval-band 就是这样规定的）。结果是：同一仓库里开的每个会话，看到的批准带完全一样，与这个会话在做什么无关；刚写好的提案还可能被别的 change 盖住。

用户要求：批准带只显示与当前会话相关的 change。

决策页：docs/flight-band-session-scope.html（主检出，未跟踪）。Q1、Q2、Q3、Q5 按推荐项；Q4 选 C（认领不跨进程保留）。

What · 02变更范围

  • 会话认领：插件为每个会话记一份认领的 change 名，只认两类机械事实，不让模型自述：
  • 写入：本会话的 Write / Edit / NotebookEdit / Bash 写入目标落在某个 change 目录内（主循环与子 agent 都算；口径与意图门禁相同）；只读不算。
  • 命令：人（终端、Remote Control、SDK）发的 /opsx-* 或 /flight 命令，参数里点名的 change。
  • 批准带只评估、只显示已认领的 change：未认领的不显示，也不再为它们计算指纹、读账本；没有已认领的待批准项时批准带不出现。本进程正在起飞 / 跑基线的项照旧显示。
  • 认领只在本进程内有效（Q4 C）：存于会话状态，热重载保留，进程重启后为空；之后发一次 /opsx-apply <name> 即可再认领。
  • 同一 change 可被多个会话认领，各自都显示（Q2 A）；重复起飞由现有的跨会话起飞守卫拦截。
  • 文档：opsx-apply / opsx-propose 的命令与 skill、README、docs/WORKFLOW_zh.md 写明「只显示本会话认领的 change」与认领方法。
  • BREAKING：原来能看到的、别的会话写的 change，现在要先在本会话发 /opsx-apply <name> 认领才显示。插件版本 0.11.0。
插件：template/plugins/flight/hooks/register.tsx：认领集合、两处记录、refresh 过滤；orchestrator.tsx 只导出 HOST_ORIGINS 与 originOf；types/index.d.ts 加会话状态 claims；tests/flight.test.tsx 的现有批准带用例在 Given 里补认领。不改：判定器（plan_fp.py、ledger.py、takeoff-gate.py）、账本事件、按键处理、起飞待命、跨会话起飞守卫。不建 ADR。安全面：只是显示过滤，隐藏是更安全的方向，不新增任何批准路径；批准仍只能由人按键写账本。

Specs · 04行为规范 (Gherkin)

flight-band-session-scope ADDED

Requirement: 批准带只评估本会话认领的 change

flight 插件 SHALL 为每个会话维护一份认领的 change 名集合，存于会话状态：热重载后保留，新进程里为空。刷新待批准列表时，遍历 worktree 与同名去重的规则不变，但 SHALL 只评估名字在认领集合里的 change：未认领的 change 不显示，也不为它计算指纹、不读它的账本。没有已认领的待批准项时，批准带 SHALL 不显示。本进程正在起飞或跑基线的项照旧显示。读取 change 目录（Read 工具、只读的 Bash 命令）SHALL NOT 认领。 Feature: 每个会话只看到自己在做的飞行计划

Scenario: band-hides-unclaimed

  • GIVEN主 worktree 里有待批准的 change demo：有 spec.html，tasks.md 有未勾选项，账本无批准
  • AND本会话没有写过 demo 的目录，也没有发过点名 demo 的命令
  • WHEN会话启动后绘制输入框上方区域
  • THEN批准带不显示：没有 demo，没有任何按钮
  • AND插件没有对 demo 的目录运行 plan_fp.py

Scenario: read-does-not-claim

  • GIVEN主 worktree 里有待批准的 change demo，会话已启动，批准带不显示
  • WHEN本会话用 Bash 运行 cat <demo 目录>/tasks.md 与 grep -n x <demo 目录>/proposal.md
  • AND主会话一轮结束
  • THEN批准带仍不显示

Requirement: 本会话写入 change 目录即认领

本会话发起的 Write / Edit / NotebookEdit / Bash 工具调用，写入目标（口径与意图门禁相同：Write / Edit 的 file_path、NotebookEdit 的 notebook_path、Bash 命令的写入目标）路径含 openspec/changes/<name>/ 或以 openspec/changes/<name> 结尾时，插件 SHALL 把 <name> 记入本会话的认领集合；archive 不算 change 名。主循环与子 agent 的调用都算。记录 SHALL NOT 阻止或改动这次工具调用；记录出错时工具调用照常进行。记录之后不立即重绘，主会话一轮结束时照常刷新。 Feature: 写提案的会话自然就能看到要批准的计划

Scenario: write-claims-change

  • GIVEN主 worktree 里有待批准的 change demo 与 beta，会话已启动，批准带不显示
  • WHEN本会话用 Write 写 <demo 目录>/proposal.md
  • AND主会话一轮结束
  • THEN批准带显示 demo 与「批准起飞」按钮，没有「另有」字样
  • AND本会话再用 Bash 运行 touch <beta 目录>/tasks.md、主会话一轮结束后，批准带显示「另有 1 个待批准」

Requirement: 人发的命令点名即认领

人（来源为终端、Remote Control 或 SDK）发出的 /opsx-* 或 /flight 命令，插件 SHALL 在命令执行之前，把参数里每个不以 - 开头的词记入本会话的认领集合；只有与真实 change 同名的词才会产生显示。其他来源（如插件代发）SHALL NOT 认领。认领集合因此变大、且批准带已启用时，插件 SHALL 在命令返回后立即刷新一次批准带，不等主会话一轮结束。 Feature: 别的会话写好的 change，在本会话发一次命令就能批准

Scenario: command-claims-change

  • GIVEN主 worktree 里有待批准的 change demo 与 beta，会话已启动，批准带不显示
  • WHEN插件以自己的名义（来源 plugin）发出 /flight status beta
  • THEN批准带仍不显示
  • WHEN人在终端（来源 composer）发出 /flight status demo，命令返回，期间没有主会话一轮结束
  • THEN批准带显示 demo 与「批准起飞」按钮，没有「另有」字样

flight-band-session-scope-docs ADDED

Requirement: 文档写明批准带只显示本会话认领的 change

opsx-apply 的命令与 skill、opsx-propose 的命令与 skill、README.md、docs/WORKFLOW_zh.md SHALL 写明批准带只显示本会话认领的 change，以及认领方法：本会话写过其目录，或人发的 /opsx-*、/flight 命令点名过它；只读不算；认领只在本进程内有效。opsx-propose 的命令与 skill 交接给人时，SHALL 把「批准带没出现」的处理写成先发 /opsx-apply <name>、仍不出现才是未装插件，不再直接断言「未装 flight 插件」。 Feature: 人知道批准带为什么没出现、怎样让它出现

Design · 05技术设计

Context

  • 现状：register.tsx 的 refresh（约第 229 行）对 git worktree list 列出的每个 worktree 调 candidatesIn（约第 96 行），收集全部「有 spec.html、tasks.md 仍有 - [ ]」的 change；dedupe 后逐个 evaluate：跑 plan_fp.py、ledger.py approved，再读账本判停飞。批准带显示可批准项里 spec.html 最新的一项。整个过程与会话无关。
  • 会话状态：band 已是 $.state 值（{ plugin: 'flight', key: 'band' }）。$.state 是宿主为本会话持有的值，热重载后保留；跨会话持久要另写 $.store（引擎类型文档 state 一节）。
  • hook 嵌套顺序：同一插件的注册「按顺序嵌套、先注册的在外层」（引擎类型文档 on 的说明）。register 先注册自己的 hook，最后一行才 registerOrchestrator(on)，所以 register.tsx 里的 hook 都在编排器外层。编排器对 /opsx-apply、/flight 自己作答、不调 next，内层的 hook 看不到这两条命令。
  • 写入口径：intent.ts 的 toolTargets(tool, e, cwd) 已给出意图门禁用的写入目标（Write / Edit 取 file_path、NotebookEdit 取 notebook_path、Bash 经 bashWriteTargets 解析重定向、tee、sed -i、cp / mv、touch / rm / mkdir 等）。它是纯函数，可以直接 import。
  • 来源：编排器的 HOST_ORIGINS = ['composer', 'bridge', 'sdk'] 与 originOf(e) 判断命令是否由人或宿主程序发出（约第 55、70 行），目前未导出。
  • 决策页：docs/flight-band-session-scope.html：Q1 写入 + 命令；Q2 多会话都显示；Q3 不相关的完全不显示；Q4 认领不跨进程（C）；Q5 0.11.0 BREAKING。

Goals / Non-Goals

Goals: - 批准带只评估、只显示本会话认领的 change。 - 认领判据全部来自插件看得到的工具调用与命令，零 token、不经模型自述。 - 提案会话不用额外操作就能看到自己的计划；别的会话写的 change，发一次 /opsx-apply <name> 就能认领。

Non-Goals: - 认领跨进程保留（Q4 选 C）。 - 多会话之间的归属互斥（Q2 选 A）。 - 改按键、账本、判定器、起飞待命、跨会话起飞守卫。 - 面板（Pane flight）与状态行：它们本来就只反映本进程的飞行。

Decisions

新 $.state 值 { plugin: 'flight', key: 'claims' }，类型 string[]，初值 []；写入一律经 update($, claims, fn)，只在集合真的变大时写。
session.start 只重置 band，不动 claims

热重载后认领还在；新进程里宿主给的初值为空。

否决的方案
模块变量

热重载即丢，开发插件时批准带会突然变空。

写 <git-common-dir>/flight/sessions/<id>.json（Q4 A）或 $.store（Q4 B）

用户选了不跨进程。

守卫 hook（on('tool.call', { tool: GUARDED_TOOLS }, …)，约第 595 行）在「不碰账本」的放行分支里，先 await 记录认领，再 next(e)
写入目标 = toolTargets(tool, e, await $.session.cwd())；
每个目标按 /openspec/changes/([^/]+)(\/|$)/ 取名，跳过 archive。
守卫 hook 已在编排器外层，编排器的意图门禁或包络拒绝这次调用，也不影响认领；.catch 照旧

认领出错时 next.called 为假，不碰账本就 next(e)。

不立即重绘

写入发生在一轮之内，主会话一轮结束时 turn.complete 照常刷新。子 agent 的写入同样要等主会话那一轮结束才刷新。

否决的方案

对命令文本做正则，看到 openspec/changes/<name> 就认领。这会把只读的 cat、grep 也算进去，排查类会话会把一堆旧 change 拉上来。

on('command.run', { command: /^(opsx-.+|flight)$/ }, …)，写在 register 里、registerOrchestrator(on) 之前。
originOf(e) 不在 HOST_ORIGINS 里 → 直接 next(e)，不认领。这两个名字从 orchestrator.tsx 导出，不另立同值常量，免得漂移。
参数按空白切词，不以 - 开头的词都记入集合。status、授权提交 这类词也会被记下，但只有与真实 change 同名才会显示，代价可以接受。
集合变大且批准带启用时，await next(e) 返回后 await refreshQuietly($)

本地命令不一定引出主会话的一轮，不能只靠 turn.complete。

时序

/opsx-apply demo 被拒（未批准）后，回复叫人「在批准带按『批准起飞』」，这时批准带已经刷新出 demo。

refresh 开头读 claims，交给 candidatesIn；candidatesIn 在 fs.list 之后，对不在集合里的目录名直接跳过，不读它的 tasks.md、不 stat spec.html。
dedupe、evaluate、进行中项的叠加都不变。进行中项本来就来自本进程的按键，一定已认领。
按键路径不变

只在 band.items 里找，指向未认领 change 的旧按钮照旧得到「已不在可批准列表」。

顺带的好处

不相关的 change 不再每轮跑 plan_fp.py 与 ledger.py。

现有批准带用例都假设「会话启动即显示」。在 Given 里，于 $.session.start(START) 之前，用 Write 工具调用认领该用例出现的 change 名

这时批准带尚未启用，认领不触发重绘，启动时的那次刷新与改前完全一样，plan_fp 的调用序号不变。断言不改。

测试世界要补两处

Write / Bash 的底层应答；git -C <tree> rev-parse --path-format=absolute --git-common-dir（意图门禁找判定器）以失败作答且不记入 log.git，免得 writes(log) 多出一项。

orchestrator.test.tsx 也加载整个插件

人发 /opsx-apply 时，命令认领会在返回后多刷新一次批准带。若有用例因此变红，只调整其 Given（例如先认领、或不启动会话），不改断言。

Risks / Trade-offs

[Bash 经解释器脚本写 change 目录（如 python3 x.py）认不出] → 与意图门禁同一上限；提案工件经 Write 写，mkdir -p 建目录也认得出，实际不受影响。
[认领不跨进程

进程重启或 --resume 进新进程后批准带为空] → 文档写明：发一次 /opsx-apply <name> 即可再认领。

[命令参数里的普通词也被记为认领名] → 只有与真实 change 同名才显示；集合只增不减，但只在本进程内，规模可忽略。
[两个会话都认领同一 change，两边都显示按钮] → 第二个会话起飞时，现有的「由另一个会话起飞，尚未落地或停飞」守卫照旧拦截。
[改动现有批准带用例的 Given 较多] → 机械改动

同一个 helper，放在 session.start 之前一行；断言一律不动，由全量 claude plugin test 兜底。

Migration Plan

  • 插件 0.11.0（BREAKING）。升级后，想在某个会话里批准别的会话写的 change，先在该会话发 /opsx-apply <name>。
  • 回滚：退回 0.10.3 即恢复全仓库显示。没有持久数据要清理。

Open Questions

  • 无。未发现需要 supersede 的 in-force ADR：DRAFT-approval-bound-to-plan-fingerprint 只规定批准证据是人按键写账本，不规定批准带的显示范围。
