Why · 01为何而做

/opsx-apply 被拒后必须人再发一句。原因有两个： - 它是插件处理的本地命令，输出不会开一轮模型对话； - 按铁律 7，模型没有起飞入口。

flight-unattended 的 attempt 3 起飞前就被拒了两次：一次「起飞异常（$.process.run(python3) aborted）」，一次「未提交的只有本 change 的工件」。attempt 1 还被「已暂存的删除让 git add 报错」拦过一次。

另外，#53 把批准带的续飞按钮降级成了「按下后预填，人回车」；文档却仍写「按下 = … + 续飞」。0.9.0 的批准带还会给已落地的旧 change 挂「续飞」。

决策见决策页 docs/flight-armed-takeoff.html。2026-10-13 用户逐项拍板，Q1–Q8 全按推荐，代替 grill-me 访谈。

What · 02变更范围

  • 起飞待命：人发出的起飞（/opsx-apply、/flight resume、批准带按键）被拒时，插件不丢掉这次意图，按拒绝原因分五类处理：
  • 等待：基线仍在跑；上一次的 agent 仍在运行。
  • 偶发：起飞异常；账本读不出；指纹算不出等。
  • 交模型：lint 红；基线缺失或中断；提交工件失败。
  • 人按一次键：未批准或计划已变；工件未提交。
  • 只能人：版本、跨会话、工件之外的改动等。
  • 批准带按下即起飞：
  • 「批准起飞」「批准修订并续飞」「续飞」都直接起飞，不再预填；
  • 已批准但还没起飞的 change 显示「起飞」；
  • 按键起飞一并提交本 change 的工件，说明行写明个数；
  • 起飞经 orchestrator.tsx 在自己的 hook 里造好的闭包 takeoffNow，不跨文件传 $。
  • BREAKING：首次起飞不再是「按键 + 回车 /opsx-apply」，按键即起飞。
  • 批准带停飞判定修正：同一 attempt 已落地就不算停飞；人工中止（abort）的停飞不显示「续飞」。
  • #53 遗留：
  • 诊断员的只读操作与评审员同规则升 allow；
  • 诊断员纳入看门狗；
  • 看门狗停飞后补停中途派出的 agent；
  • 计时器不重复处理；
  • 提交工件时已暂存的删除也能提交；
  • integ 提示词用例按 spec 原样的 Given；
  • freshWorktree 的五个候选名在规格里重述。
  • 文档：命令、skill、README、WORKFLOW、propose 交接都照实改；插件 0.10.0。
插件：template/plugins/flight/hooks/：新增 armed.ts；改 orchestrator.tsx、register.tsx、io.ts、land.ts；types/index.d.ts；测试 armed.test.ts、orchestrator.test.tsx、flight.test.tsx、io.test.ts、land.test.ts、prompts.test.ts；plugin.json 升到 0.10.0。判定器：不改。待命不进账本，只在偶发失败时追加既有的 diag 事件。文档：opsx-apply 命令与 openspec-apply-change skill；opsx-propose 命令与 openspec-propose skill（交接改为按键即起飞）；README.md、docs/WORKFLOW_zh.md。新 ADR 草案 DRAFT-flight-armed-takeoff：部分取代 DRAFT-flight-resume-from-band。起飞前置：主检出须快进到 7fd26b0 或更新，判定器要认识 heal / triage。插件 0.9.0 已装。

flight-armed-takeoff ADDED

| 类 | 回复文本（flight： 之后） | |---|---| | wait-baseline | 以「slice-gate preflight 未通过」开头且含「基线仍在跑」 | | wait-agents | 含「上一次飞行派出的 agent 仍在运行」 | | transient | 以「起飞异常」「账本读取失败」「提交遗留飞行记录失败」「计算计划指纹失败」「写 takeoff 事件失败」之一开头；或为「工作区不干净，不起飞：」紧跟换行（git status 本身失败） | | model | 以「提交工件失败」「slice-gate lint 未通过」「slice-gate preflight 未通过」之一开头（且不属上面的 wait-baseline） | | human-key | 含「未提交的只有本 change 的工件」；或以「起飞守卫未通过」开头且含「未批准」或「计划已变」 | | human | 其余全部，包括认不出的文本 |

Requirement: 待命的预算与过期

armed.ts 的 nextStep(arm, event, now) SHALL 先按以下规则判断是否放弃： - now - arm.since 超过 30 分钟（ARM_TTL_MS = 1800000）→ give-up，原因含「已过期」； - human-key、human 类 → 立即 give-up，原因含拒绝原文首行； - transient、model 类在 refused 事件上：已计入预算的重试满 3 次（ARM_BUDGET = 3）→ give-up，原因含「重试已用尽」； - transient 类在 refused 事件上，若上一次自动重试的结果也是 transient（transientAgain）→ give-up。

wait-baseline、wait-agents 的重试 SHALL NOT 计入预算，只受 30 分钟约束。

Feature: 用户定 Q6：最多 3 次、30 分钟内有效；Q8：偶发只重试一次。

Requirement: 各类待命在什么事件上推进

未放弃时，nextStep SHALL 按事件给出下一步： - wait-baseline：tick → retry； - wait-agents：agent-ended 或 tick → retry； - transient：refused → wait，ms 为 10000（TRANSIENT_DELAY_MS）；timer → retry； - model：refused → submit，正文由 modelPrompt(arm) 给出；main-turn 且 awaitingModel 为真 → retry； - 其余组合 → wait（不带 ms）。

modelPrompt(arm) SHALL 含：拒绝原文；「只修工作区与本 change 工件」；「改了计划需要人在批准带重新批准」；「不要发 /opsx-apply」。

Feature: 用户定 Q5：交给模型修；Q7：事件驱动 + 60 秒兜底。

Requirement: 待命按事件自动推进

插件 SHALL 在以下事件上对每个待命求 nextStep 并执行： - 60 秒兜底 tick（复用看门狗计时器）； - 本 change 的飞行 agent 结束（turn.complete 带 agentId）； - 主会话一轮结束（turn.complete 不带 agentId，由带 { turnId: /./ } matcher 的 hook 接收）； - clock.after 计时到。

执行规则： - retry：以原参数重新起飞；transient、model 类先把已计入预算的次数加一。又被拒时按新原文更新待命并以 refused 再求一次。 - submit：经 $.clock.after(0, …) 调用 $.prompt.submit，并把 awaitingModel 置真。SHALL NOT 在 command.run 的处理中调用 $.prompt.submit（引擎会拒绝）。 - wait：给出 ms 时起 $.clock.after(ms)，到点产生 timer。 - give-up：清除待命，并通知原因与做法。 - 重试成功（账本追加了 takeoff）时，SHALL 清除待命并通知「已起飞」。

Feature: 实测（CLI 2.1.296）：本地命令返回后用 clock.after(0) 提交，会起一轮模型对话，插件能看到它的 turn.complete；同一事件上第三个带 matcher 的 hook 可以共存。

flight-band-takeoff ADDED

Requirement: 批准带的显示规则

批准带 SHALL 对每个候选 change 按下表决定按钮，自上而下取第一条命中：

| 账本与指纹 | 按钮（key 前缀） | 说明行 | |---|---|---| | 最新 attempt 以 halt 结束（同 attempt 无 land，且 halt 的 kind 不是 abort），当前指纹 ≠ 最近批准 | 「批准修订并续飞」（replan:） | 含「提交本 change 的工件」「重跑基线」 | | 同上，当前指纹 = 最近批准 | 「续飞」（resume:） | — | | 最近一次 approve 晚于最近一次 takeoff（或从未起飞），且当前指纹 = 该 approve | 「起飞」（takeoff:） | 有未提交工件时为「按下会提交本 change 的 N 个工件并直接起飞」，否则为「按下直接起飞」 | | 当前指纹未批准 | 「批准起飞」（approve:） | 同「起飞」 | | 其余 | 不显示 | — |

io.ts 的 stoppedNow SHALL 在同一 attempt 同时有 land 与 halt 时返回 land。N 按 land.ts 的 classifyDirty 口径计。

Feature: 用户定 Q2、Q3；修 0.9.0 批准带给已落地的旧 change（落地后被补记 halt）挂「续飞」的缺陷（2026-10-13 实际发生，被判定器版本核对拦下）。

Requirement: 按钮按下即起飞

按下按钮 SHALL 先核对指纹与绘制时一致，然后按钮各自如下： - approve:：追加 approve，再在后台调用 takeoffNow([change, '授权提交'])； - takeoff:：不追加 approve，在后台调用 takeoffNow([change, '授权提交'])； - replan:：追加 approve，在后台运行 resumeFlight(…, {replan: true})； - resume:：不追加 approve，在后台运行 resumeFlight(…, {replan: false})。

resumeFlight 的 takeoff 依赖 SHALL 为 takeoffNow(args, {resume: true})。起飞回复的首行 SHALL 经 toast 与 ui.notify 告诉人。输入框 SHALL NOT 被预填。register.tsx SHALL NOT 把 $ 传给其他文件的函数。

Design · 05技术设计

Context

- 起因： - 起飞被拒后，人必须再发一句； - #53 把续飞降级成预填； - 0.9.0 批准带给已落地的旧 change 挂「续飞」：io.ts:48 的 stoppedNow 在同一 attempt 里让 halt 优先于 land，而 flight-envelope-followups、flight-hardening 落地后又被补记过 halt。 - 决策：docs/flight-armed-takeoff.html 的 Q1–Q8，用户 2026-10-13 全按推荐。 - 现状： - orchestrator.tsx 的 takeoff()（main 第 598 行起）有 20 个拒绝出口，全部返回文本；/opsx-apply 的 command.run 原样回复； - 批准带（register.tsx）按「批准起飞」后预填 /opsx-apply，按续飞按钮则经 resumeFlight 预填 /opsx-apply <c> 授权提交。 - 实测（CLI 2.1.296；临时 mod scratchpad/mods/armed-spike，不进仓库）： 1. A 文件的 session.start hook 里造闭包（捕获本文件的 $）存进模块变量，B 文件的 hook 调用它：claude plugin validate 通过，测试世界与真实无头运行都可用。 2. 在 command.run hook 里调用 $.prompt.submit 会被引擎拒绝，不 await 也一样。原文：「called from a command.run hook, it would wait on the turn this hook is holding; submit from a later event (turn.complete) (host check)」。 3. 在 command.run 里用 $.clock.after(0, …) 延后再提交：本地命令返回后起了一轮模型对话（origin 为 plugin），插件看到了这一轮主会话的 turn.complete（agentId 为空）。 4. 本地命令本身不产生 turn.complete。 5. 同一插件在 turn.complete 上可以有三个 hook：一个不带 matcher、一个 { agentId: /./ }、一个 { turnId: /./ }。第三个能看到主会话的轮次。 6. 测试世界：用 on('prompt.submit') 应答 { text } 就能看到提交的正文；mock.clock 的 advance 会触发 clock.after。 7. 测试与插件是隔离实例：测试 import 插件模块拿到的是另一份模块状态。所以闭包的效果只能经插件 hook（例如按键）观察。 8. 真实 git：删除已用 git rm 暂存时，git add -- <该路径> 报「pathspec did not match」；跳过它、只 add 其余路径，再 git commit -- <全部路径>，删除被正确提交，工作区干净。 - 约束： - 铁律 7：approve 只由按键写； - 铁律 10：起飞后的控制面异常照旧停飞； - 插件里 $ 不出文件； - 每插件一个 hooks 模块（register.tsx）。

Goals / Non-Goals

Goals - 人表达一次起飞意图（命令或按键）后，凡不需要人判断的拒绝，都由插件等待、重试或交给模型，不必人再发一句。 - 批准带三个按钮按下即起飞；已批准未起飞的 change 有「起飞」按钮。 - 关掉 #53 留下的文档、规格与可靠性缺口（Q1 A 的范围）。

Non-Goals - 不让模型能起飞：模型仍没有起飞入口，计划改了照旧要人按键。 - 不改判定器、不加账本事件类型：待命状态只在会话里。 - 不查 python3 aborted 的根因：本 change 只把它当偶发重试一次并留 diag（Q8）。 - 不处理 #53 其余 LOW（G9 误报、摘要口径、integ 缺 base 时 fail-closed 等）。

架构（C4 容器图 · Mermaid · 轻量 C4，与 flight-unattended 同口径）

  • 边界：
  • 待命全在插件内（orchestrator.tsx + armed.ts + 会话状态）；
  • 判定器与账本不改，只多一种 diag.where = 'takeoff' 的取值（diag 是既有事件，where 是自由文本）。
  • 职责：
  • armed.ts 只做纯判定，不碰 $；
  • orchestrator.tsx 负责执行（重试、提交、计时、通知、状态行）；
  • register.tsx 只管按键与显示，起飞经 takeoffNow。
  • 模型：只会收到插件提交的一轮「修工作区」，没有起飞入口；它改了计划，指纹就会变，下一次重试被起飞守卫拦下，变成「人按一次键」。
  • 假设：
  • 待命只对发出它的会话有效；会话结束即消失；
  • 跨会话起飞本来就会被拒。

Risks / Trade-offs

[拒绝文本改了，分类失效] → 认不出的一律归「只能人」

只是退化成通知，不会误重试。S4 的集成用例用真实拒绝文本走通 wait-baseline、transient、model 三条路，字样漂移会让它们变红。

[交模型烧 token] → 只在模型能修的三种拒绝上提交，计入 3 次预算；人随时可以 /flight abort <change> 取消。
[模型借「修工作区」改计划] → 指纹一变，起飞守卫就拒，必须人按键（铁律 7 不变）。正文也明示「改了计划需要人重新批准」。
[误按即起飞] → 按键前照旧核对指纹与绘制时一致；起飞后可以 /flight abort。说明行写明会提交几个工件。
[待命只在会话内] → 会话结束待命就没了，人回来重新发一次即可。这与跨会话拒飞的现有规则一致。
[S4 与 S5 并行] → 两片之间只经 takeoffNow 的签名耦合（S3 已定）。合回后的交互由 final 全量验证；0.9.0 的整合修复体可以处理跨片失配。
