Why · 01为何而做

#61 合入后（main ff19ecd，插件 0.11.0）复盘近三次落地，核实出 3 个结构性问题与 3 处小问题。人在 2026-10-14 的决策页 docs/flight-post-61-adjustments.html 里全选第一项，并要求合成一个 change。

| # | 问题 | 证据 | |---|---|---| | A | 预合并 main 让 final 与全量评审必然过期 | 落地是「final → land → 交接 pr-ship」，pr-ship 第 4 步才预合并；#59、#60、#61 预合并都有冲突，人合并后 ship 都判「final 过期 / 全量评审过期」→ draft，最后都由人跳过裁决合入。合并部分（含解冲突改的代码）既没跑 final 门禁，也没被独立评审 | | B | 计划错误导致的停飞仍给「续飞」 | flight-shelve-followups 的 S3 因 G5「在改生产代码之前就已通过」停飞；计划不改时结果确定，attempt 2、3 原因一字不差，S3 共耗 131 分钟。诊断员三次都说「改计划」，但按 design D6 只供展示 | | C | 插件 TS 测试的失败，全量门禁看不见 | assert_ts_passed 只核对点名用例，不看 claude plugin test 的结果；main 上 orchestrator.test.tsx 收尾留下未处理拒绝（no implementation for turn.step），插件测试报 1 fail，全量 pytest 却 631 全绿 | | D1 | 命令认领 hook 吞掉下游原始错误 | register.tsx:702：下游已执行且抛错时统一改答「flight：命令执行出错」，/opsx-propose 等命令的错误被记到 flight 头上（#61 评审 LOW） | | D2 | 改名行的拒绝出路说明不适用 | 「工件之外」拒绝信息建议把文件列进 artifact_files，但改名行无论是否声明都被拒（#60 规则） | | D3 | 历史 change 的 scenario 映射还写着改名前的测试函数名 | 不影响任何门禁（#61 评审 LOW）；人选「只记录、不改」 |

What · 02变更范围

  • 落地前预合并目标分支（A）：
  • 收口阶段、本 attempt 第一次 final 之前，控制面在 change worktree 把目标分支（origin/HEAD 指向的分支，解析不出用 main）合进 change 分支；
  • 无冲突 → 直接合并，记 premerge 事件；已包含 → 不合并只记账；没有 origin → 跳过并记账；拉取失败 → 停飞（kind premerge）；
  • 有冲突 → 派解冲突 agent 在独立 worktree 里解，收口跑 final 门禁，绿则 change 分支快进；解不开 → 停飞，人解完后 /flight resume；
  • final 与全量评审都在合并后的提交上做；全量评审的起点改为合入的目标提交，评审范围恰为本 change 的改动（含解冲突）。
  • 落地后重验 /flight recheck <change>（A）：落地后 HEAD 又有代码改动（例如人工预合并）时，另起一个 attempt，不派执行体，直接预合并 → final → 全量评审 → 落地 → 交接 pr-ship；final 仍新鲜时拒绝。
  • 计划需修订（B）：最新停飞里有切片因 G5「在改生产代码之前就已通过」被阻断时，计划不改就不许续飞：/flight resume 拒绝，批准带显示「计划需修订：<原因>」、不画「续飞」（仍可搁置）；改计划后照常出现「批准修订并续飞」。
  • 插件测试零失败（C）：tests/test_flight_plugin.py 增加对 claude plugin test 全部失败行的解析，全量 pytest 断言真实插件测试零失败；修掉 orchestrator.test.tsx 收尾的未处理拒绝。
  • 小修：D1 保留下游原始错误；D2 改名行给「git mv 回原名或自行提交」的出路；D3 记在 design，不改历史 change。
  • 文档：opsx-apply 命令与同名 skill 同改；flight:pr-ship 第 4 步说明飞行内已预合并、落地后再冲突用 /flight recheck。
  • ADR：新增 DRAFT-flight-premerge-before-final。
  • 插件 0.12.0。
  • 账本新增事件类型 premerge、停飞 kind premerge：升级插件须同步更新主检出的 .claude/hooks/（起飞时 checkJudges 要求判定器认识全部事件类型）。
  • 落地前会把目标分支合进 change 分支（只在本地 change worktree，不推送、不碰 main）。
判定器：template/.claude/hooks/ledger.py（premerge 事件、halt kind premerge）。插件：hooks/core.ts（收口加预合并、计划缺陷判定）、orchestrator.tsx（执行预合并、解冲突、/flight recheck、续飞拒绝、改名出路）、landing.tsx（全量评审起点）、land.ts（解冲突现场合并目标分支）、prompts.ts（解冲突提示）、io.ts（事件表）、register.tsx（批准带、认领 hook）、types/index.d.ts、.claude-plugin/plugin.json。文档：template/.claude/commands/opsx-apply.md、template/.claude/skills/openspec-apply-change/SKILL.md、template/plugins/flight/commands/pr-ship.md。ADR：template/openspec/adr/DRAFT-flight-premerge-before-final.md。测试：新增 6 个 pytest 文件；TS 用例追加在 orchestrator.test.tsx、flight.test.tsx；io.test.ts 事件清单、test_band_session_scope_docs.py 版本断言随之更新。

Specs · 04行为规范 (Gherkin)

flight-landing-premerge ADDED

Requirement: 账本认识预合并事件

账本 SHALL 认识 premerge 事件，必需字段 attempt（正整数）、ok（布尔）、ref、target、commit、reason（字符串）、conflicts（字符串数组）；停飞事件的可选 kind SHALL 接受 premerge。字段不合法时账本判损坏、原因点名字段。

Scenario: ledger-knows-premerge

  • GIVENdemo 的账本依次有一条合法的 premerge（ok 为 false、conflicts 为 ["a.py"]）与一条 kind 为 premerge 的 halt；other 的账本有一条 conflicts 为字符串 "a.py" 的 premerge
  • WHEN对 demo 与 other 分别运行 ledger.py show，再运行 ledger.py events
  • THENdemo 以 0 退出并打印这两条事件；other 以 4 退出，stderr 含「premerge 的 conflicts」
  • ANDevents 的输出含 premerge

Requirement: 落地前预合并目标分支

收口阶段、本 attempt 第一次 final 之前，控制面 SHALL 在 change worktree 预合并目标分支并记一条 premerge 事件，之后才跑 final： - 没有 origin 远端 → 跳过，ok 为真； - 目标 = origin/HEAD 指向的分支，解析不出用 origin/main；先 git fetch，失败 → ok 为假，停飞 kind premerge，原因含「拉取」与「/flight resume」； - 目标提交已是 HEAD 的祖先 → 不合并，ok 为真； - git merge-tree 判无冲突 → git merge --no-edit <目标>，ok 为真，commit 为合并后的 HEAD。 同一 attempt 之后再跑的 final（整合修复、修复轮之后）SHALL NOT 再预合并。

Scenario: premerge-clean-merges-then-final

  • GIVENdemo 已起飞，S1 已合回、评审无 CRITICAL/HIGH；origin/HEAD 指向 origin/main，origin/main 不是 HEAD 的祖先，merge-tree 判无冲突
  • WHENdrive 推进到收口
  • THENchange worktree 依次运行了 git fetch origin main、git merge --no-edit origin/main
  • AND账本里 ok 为 true 的 premerge 事件排在第一条 final 之前，final 之后照常派全量评审

Scenario: premerge-up-to-date-skips-merge

  • GIVEN同上，但 origin/main 已是 HEAD 的祖先
  • WHENdrive 推进到收口
  • THEN没有运行任何 git merge 合并 origin/main
  • AND账本有一条 ok 为 true、reason 含「已包含」的 premerge，随后有 final

Scenario: premerge-fetch-failure-halts

  • GIVEN同上，但 git fetch origin main 以 128 退出
  • WHENdrive 推进到收口
  • THEN账本有一条 ok 为 false、reason 含「拉取」的 premerge，随后是 kind 为 premerge 的 halt，原因含「/flight resume」
  • AND本 attempt 没有 final 事件

Requirement: 全量评审起点是合入的目标提交

本 attempt 有 ok 为真且 target 非空的 premerge 时，全量评审 SHALL 以该 target 为起点，SHALL NOT 用主检出 HEAD 求 merge-base。

Scenario: whole-review-base-is-target

  • GIVENdemo 收口时预合并成功，premerge 的 target 为 origin/main 的提交 T；主检出 HEAD 是另一个提交
  • WHENfinal 绿后派全量评审
  • THEN全量评审的 dispatch 事件 base 为 T

Requirement: 预合并冲突交解冲突 agent

预合并判出冲突时，控制面 SHALL 在独立的解冲突 worktree（从 change 分支尖端切出、在其中合并目标分支）派解冲突 agent，SHALL NOT 在 change worktree 留下合并现场。解冲突 agent 收口 SHALL 跑 final 门禁；绿则 change 分支快进到它的合并提交、记 merge（slice 为 premerge），再跑 final；收口未通过、未结束合并或快进失败 SHALL 停飞 kind premerge，原因列出冲突文件并提示人工合并后 /flight resume。

Scenario: premerge-conflict-dispatches-resolver

  • GIVENdemo 收口时 merge-tree 判 origin/main 与 HEAD 在 a.py 冲突；解冲突 agent 收口时 final 门禁绿
  • WHENdrive 推进，解冲突 agent 结束
  • THEN账本依次有：ok 为 false、conflicts 为 ["a.py"] 的 premerge；role 为 resolver、slice 为 premerge 的 dispatch（worktree 名含 premerge-resolve）；slice 为 premerge 的 merge（ok 为 true）；final
  • ANDchange worktree 从未运行 git merge --no-edit origin/main

Scenario: premerge-resolver-red-halts

  • GIVEN同上，但解冲突 agent 三次收口的 final 门禁都红
  • WHEN解冲突 agent 结束
  • THEN账本有 kind 为 premerge 的 halt，原因含 a.py 与「/flight resume」
  • AND本 attempt 没有 slice 为 premerge 的 merge，也没有 final

Requirement: 落地后重验

人发出的 /flight recheck <change>：最新 attempt 已落地，且判定器 slice-gate.py ship 的原因含「final 过期」或「全量评审过期」时，控制面 SHALL 另起一个 attempt，不派执行体，直接进入收口（预合并 → final → 全量评审 → 落地）；final 与全量评审仍新鲜时 SHALL 拒绝并回复「无需重验」；未落地时 SHALL 拒绝并提示用 /flight resume。

Scenario: recheck-after-land-reruns-final-and-review

  • GIVENdemo 的 attempt 1 已落地（S1 合回、评审、final、全量评审、land 齐全）；slice-gate.py ship 的 reasons 含「final 过期」
  • WHEN人发出 /flight recheck demo
  • THEN账本追加 attempt 2 的 takeoff，随后依次有 premerge、final、全量评审的 dispatch
  • ANDattempt 2 没有任何 role 为 executor 的 dispatch

Scenario: recheck-refused-when-fresh

  • GIVENdemo 的 attempt 1 已落地；slice-gate.py ship 的 reasons 为空
  • WHEN人发出 /flight recheck demo
  • THEN回复含「无需重验」
  • AND账本没有新的 takeoff

flight-plan-defect-halt ADDED

Requirement: 计划缺陷停飞不给续飞

最新 attempt 以 kind 为 blocked 的 halt 结束，且本 attempt 有切片的 blocked 原因同时含「G5 measure」与「在改生产代码之前就已通过」时，控制面 SHALL 判为计划缺陷，并在计划指纹与最新 takeoff 相同时不给续飞： - /flight resume <change> SHALL 拒绝、SHALL NOT 写 takeoff，回复含「计划需修订」与该原因首行，SHALL NOT 含「未批准」「计划已变」； - 批准带 SHALL 显示「计划需修订：<原因首行>」，SHALL NOT 显示「续飞」按钮，SHALL 仍显示「搁置」按钮。 计划指纹变化后，照现有规则显示「批准修订并续飞」。

Feature: flight-shelve-followups 的 S3 因同一条 G5 原因连停三次（attempt 2、3 由人按「续飞」触发），共耗 131 分钟。判据只看账本 blocked 原因文字（零 token），诊断员结论仍只供展示（design D6）。

Scenario: resume-refused-on-plan-defect

  • GIVENdemo 的 attempt 1 以 kind 为 blocked 的 halt 结束，S1 的 blocked 原因为「G5 measure: cap#s → tests/test_a.py::test_s 在改生产代码之前就已通过：若它描述的行为在 base 上本已成立，应在计划里标为护栏」；当前计划指纹等于 attempt 1 的 takeoff 指纹，起飞守卫放行
  • WHEN人发出 /flight resume demo
  • THEN回复含「计划需修订」与「在改生产代码之前就已通过」，不含「未批准」与「计划已变」
  • AND账本没有 attempt 2 的 takeoff

Scenario: band-shows-plan-defect-without-resume

  • GIVENgamma 的最新 attempt 以 kind 为 blocked 的 halt 结束，同 attempt 有一条 blocked，原因为上面的 G5 原文；计划未改（当前与最近批准都为 F）；本会话已认领 gamma
  • WHEN批准带刷新并绘制
  • THEN有含「计划需修订」的文字，没有 key 以 resume: 开头的按钮
  • AND有 key 为 shelve:gamma:<F> 的按钮

flight-small-fixes ADDED

Requirement: 命令认领 hook 保留下游原始错误

批准带对 /opsx-*、/flight 命令的认领 hook 在下游已执行且抛错时，回复 SHALL 含下游错误的首行，形如「flight：命令执行出错：<首行>」；SHALL NOT 只回笼统的「flight：命令执行出错」。下游未执行时照旧交给下游。

Feature: #61 评审 LOW：/opsx-propose 等 markdown 命令的错误被换成 flight 的笼统文字，错误被记到 flight 头上。测试里无法用「插件之下抛错的 hook」构造下游错误：引擎会跳过抛错的 hook（fail-open），落到下游无实现（2026-10-14 S5 实测）；因此以「插件之下没有实现」构造下游错误。

Scenario: claim-hook-keeps-downstream-error

  • GIVEN插件之下没有 /opsx-propose 的实现（下游以「no implementation for command.run」拒绝）
  • WHEN人发出 /opsx-propose demo
  • THEN回复含「flight：命令执行出错」与「no implementation for command.run」

Requirement: 改名行的拒绝出路

起飞因「工件之外的未提交改动」被拒时：工件之外的路径全是 porcelain 改名行（含 -> ）→ 回复 SHALL 给出「git mv 回原名，或自行提交这次改名」的出路，SHALL NOT 建议列进 artifact_files；混有其他路径时两条出路都给。

Feature: 改名行无论是否声明都被归为工件之外（#60），原先的「列进 artifact_files」对它不可行。

Scenario: rename-refusal-advice

  • GIVENdemo 已批准、账本为空；porcelain 只有 R <cd>/a.md -> <cd>/b.md 与 ?? <cd>/proposal.md
  • WHEN人发出 /opsx-apply demo 授权提交
  • THEN回复含「工件之外」、改名行原文与「git mv」
  • AND回复不含「artifact_files」；没有提交，账本没有 takeoff

flight-test-suite-hygiene ADDED

tests/test_flight_plugin.py SHALL 提供 suite_failures(text)：返回 claude plugin test 输出里每个 (fail) <名字> [ 行的名字（含文件级的 the file ran to its end）。全量 pytest SHALL 有一条断言真实插件测试的 suite_failures 为空。

Feature: assert_ts_passed 只核对点名用例在通过名单里；main 上插件测试报 1 fail（orchestrator.test.tsx 收尾的未处理拒绝 no implementation for turn.step），全量 pytest 仍全绿。

Scenario: suite-failures-parses-file-level-fail

  • GIVEN一段输出：(pass) a [1.00ms]、(fail) b [2.00ms]、(fail) the file ran to its end [0.00ms]、 1 pass、 2 fail

  • THEN返回恰为 ["b", "the file ran to its end"]

Scenario: plugin-suite-has-no-failures

  • GIVEN仓库中的 template/plugins/flight/
  • WHEN运行一次 claude plugin test 并对输出调用 suite_failures
  • THEN返回空列表

Design · 05技术设计

Context

Goals / Non-Goals

Goals： - 常规落地（目标分支无冲突或冲突可解）在合并后的提交上得到新鲜的 final 与全量评审，ship 可判 ready； - 计划缺陷停飞不再诱导无效续飞； - 插件 TS 测试的任何失败都会让全量 pytest 变红； - 每个行为都有 scenario 测试。

Non-Goals： - 不支持 pr-ship 指定的非缺省 target：飞行内只合 origin/HEAD 指向的分支；用别的 target 时照旧可能在 pr-ship 第 4 步冲突，按 /flight recheck 重验。 - 不让诊断员的结论参与判定：B 只看账本 blocked 原因文字（零 token），design D6 不变。 - 计划缺陷只认 G5「在改生产代码之前就已通过」：G7 映射类错误可能是执行体删了测试，不确定，不纳入。 - 不改历史 change 的 scenario 映射旧名（D3）：已完成 change 的 slices.json 里映射仍是改名前的测试函数名（例如 test_plugin_version_0_10_3），不影响任何门禁；约定：历史 change 的映射不随后续改名更新，以后若要对历史 change 重跑门禁再统一处理。本仓库没有独立的 backlog 文件，这条只记在这里。 - 不处理两个会话同时改同一 worktree、批准带刷新撞 index.lock：本次只观察到现象，未核实成因。

Risks / Trade-offs

[落地时 origin 不可达] → 停飞 kind premerge，人恢复网络后 /flight resume；只影响收口，切片成果都已合回。
[解冲突 agent 改坏他人代码] → 收口跑 final 门禁、随后全量评审覆盖目标提交以来的全部改动；仍不放心时人类 PR review 兜底。
[/flight recheck 发现 CRITICAL/HIGH] → 修复轮的修复体要改源码，而落地后 tasks.md 已全部勾选，意图门禁可能拦下修复体，结果是 fix 轮 blocked、落地为 draft 并写明原因；本 change 不放宽意图门禁。
[状态机加了一步，旧用例的事件序列变长] → S2 同片更新测试世界（fetch、symbolic-ref 应答，merge-base --is-ancestor 缺省成立即「已包含」）；断言事件序列的旧用例只允许在 final 之前插入一项 premerge。
[与 0.11.0 之前的判定器混用] → 起飞时 checkJudges 拒绝（判定器不认识 premerge），提示更新主检出。
[C 的根因与用例组合有关] → S6 排在最后一个 wave，在全部 TS 用例就位后定位；修不好就如实停在该片。
